第 19 章 · 补充篇

从源码到上线

前面的章节一直在用作者做好的镜像（nigelpoulton/k8sbook:1.0）。这一章换成你自己来： 拿仓库里的示例 Web 应用，写 Dockerfile → 构建镜像 → 推送到镜像仓库 → 部署到集群 → 改代码再滚动更新， 把一个应用从源代码一路送上 Kubernetes。

ⓘ 关于补充篇

本章不是原书内容。用到的应用源码来自仓库的 web-app/1.0/，为了让你可以随意修改，复制了一份到 extras/source-to-k8s/app/，并配了一个改进版的 Dockerfile；部署文件是 extras/source-to-k8s/deploy.yml。

⚠ 待验证：本章命令输出尚未在真实集群上运行核对

本章的示例文件已通过语法校验，但文中展示的命令输出是按 Docker 和 Kubernetes 的标准格式整理的，还没有逐条实际运行核对。 如果你实际看到的输出与文中不同，以你的环境为准。

本章目标

  • 读懂一个 Dockerfile，知道每条指令如何变成镜像的一层
  • 写出更适合 Kubernetes 的 Dockerfile：固定版本、利用缓存、非 root、正确处理退出信号
  • 理解镜像名的组成，构建、本地测试并推送镜像到 Docker Hub
  • 用自己的镜像部署 Deployment + Service，并完成一次「改代码 → 新版本 → 滚动更新 → 回滚」
  • 知道私有镜像仓库、CPU 架构不匹配等真实环境中的坑

全流程一览

你需要准备：

  • Docker（第 3 章装好的 Docker Desktop 即可）和一个 Kubernetes 集群；
  • 一个免费的 Docker Hub 账号（hub.docker.com），用来存放你的镜像。下文用 <your-dockerhub-id> 表示你的用户名。
💡 为什么要推到镜像仓库？

你在本机 docker build 出来的镜像只存在于你的电脑上。集群里的节点（哪怕是本机的 kind 节点，它们其实是独立的容器）要通过镜像仓库来拉取它。 推到 Docker Hub 这样的仓库，是在任何集群上都行得通的做法。

认识这个应用

这是一个只有几行代码的 Node.js Web 应用，用 Express 框架监听 8080 端口，用 Pug 模板渲染首页：

// Simple node.js web app for demonstrating containerizing apps
// For quick demo purposes only (not properly maintained)
'use strict';

var express = require('express'),
    app = express();

app.set('views', 'views');
app.set('view engine', 'pug');

app.get('/', function(req, res) {
    res.render('home.pug', {
  });
});

app.listen(8080);
module.exports.getApp = app;
package.json（依赖清单）
{
  "name": "container-web-test",
  "private": true,
  "version": "0.0.1",
  "main": "app.js",
  "dependencies": {
    "express": ">=4.21.2",
    "pug": ">=3.0.3"
  }
}
views/home.pug（首页模板）
html
  head
    title='K8s rocks'
    link(rel="stylesheet", href="...bootstrap.min.css")
  body
    div.container
      div.jumbotron
        h1(style="text-align:center;") Kubernetes rocks!
        p(style="text-align:center;") Version 1.0 - built and deployed by me.
ⓘ 一个好的细节

app.listen(8080) 没有指定地址，Node.js 默认监听所有网络接口（0.0.0.0）。 如果写成只监听 127.0.0.1，容器里自己访问没问题，但 Service 和其他 Pod 都连不上（第 17 章案例 7 提到的隐蔽坑）。

Dockerfile：把应用打包成镜像

先看原书 web-app/1.0/Dockerfile 的写法，它简单直观：

FROM node:current-alpine                 # 基础镜像：Alpine Linux + 最新版 Node.js
LABEL MAINTAINER=nigelpoulton@hotmail.com
COPY . /src                              # 把整个目录复制进镜像的 /src
RUN cd /src; npm install                 # 安装依赖
WORKDIR /src                             # 之后的命令和容器的工作目录
EXPOSE 8080                              # 声明应用监听的端口（只是文档作用）
CMD ["node", "./app.js"]                 # 容器启动时执行的命令

每条指令都是一层

改进版 Dockerfile

# Pin a specific major version instead of the moving "current" tag
FROM node:24-alpine

# tini runs as PID 1 and forwards SIGTERM to node, so Pods stop quickly
RUN apk add --no-cache tini

WORKDIR /src

# Copy the dependency list first: this layer is only rebuilt when package.json changes
COPY package.json ./
RUN npm install --omit=dev

# Then copy the rest of the source code
COPY . .

# Don't run as root (the node user ships with the official image)
USER node

EXPOSE 8080
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "app.js"]
改动为什么
node:24-alpine 代替 node:current-alpinecurrent 会随时指向新的大版本，今天和下个月构建出来的镜像可能不一样。固定大版本让构建可重复
先 COPY package.json 再 npm install利用构建缓存（图 19-2）
--omit=dev不安装开发依赖，镜像更小、攻击面更小
.dockerignore排除本地的 node_modules、.git 等，避免把不该带的东西复制进镜像、拖慢构建
USER node不以 root 运行（第 15 章），也能满足 PSA restricted 策略对 runAsNonRoot 的要求
tini 作为入口正确处理退出信号，见下文

为什么需要 tini：PID 1 与优雅退出

另一种做法是在应用代码里自己处理 SIGTERM：停止接收新连接、处理完进行中的请求再退出。这对真实的生产服务更好，tini 是不改代码时的简单方案。

推送成功后，在 Docker Hub 网页上能看到这个存储库。新建的存储库默认是公开的，任何人都能拉取——别把密码、密钥打进镜像（第 16 章 IBM 的教训）。

⚠ 用 Apple Silicon（M 系列芯片）的 Mac？

你构建出的镜像默认是 arm64 架构的。如果集群节点是 amd64（大多数云主机），Pod 会报 exec format error 并反复崩溃。 用 buildx 同时构建两种架构并直接推送： 

$ docker buildx build --platform linux/amd64,linux/arm64 \
  -t <your-dockerhub-id>/k8sbook-web:1.0 --push .

部署到 Kubernetes

部署文件把前面各章的最佳实践都用上了：就绪和存活探针（第 18 章）、资源配置、maxUnavailable: 0 的滚动更新（第 6 章）：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-web
spec:
  replicas: 3
  revisionHistoryLimit: 5
  minReadySeconds: 5
  selector:
    matchLabels:
      app: my-web
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0          # 更新过程中一个都不少
      maxSurge: 1                # 每次多起 1 个新的
  template:
    metadata:
      labels:
        app: my-web
    spec:
      containers:
      - name: web
        image: <your-dockerhub-id>/k8sbook-web:1.0     # ← 改成你的镜像
        ports:
        - containerPort: 8080
        readinessProbe:
          httpGet:
            path: /
            port: 8080
          periodSeconds: 5
        livenessProbe:
          tcpSocket:
            port: 8080
          periodSeconds: 10
          failureThreshold: 3
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            memory: 128Mi
---
apiVersion: v1
kind: Service
metadata:
  name: my-web
spec:
  type: LoadBalancer
  selector:
    app: my-web
  ports:
  - port: 8080
    targetPort: 8080

改代码，发布新版本

修改首页模板，比如把版本号改成 1.1：

        p(style="text-align:center;") Version 1.1 - now with a new headline!

$ cd app
$ docker build -t <your-dockerhub-id>/k8sbook-web:1.1 .      # 这次只有最后一层需要重建
$ docker push <your-dockerhub-id>/k8sbook-web:1.1
$ cd ..

然后修改 deploy.yml 里的镜像标签（1.0 → 1.1）再 apply——坚持声明式（第 6 章）：

$ sed -i 's/k8sbook-web:1.0/k8sbook-web:1.1/' deploy.yml
$ kubectl apply -f deploy.yml
deployment.apps/my-web configured

$ kubectl rollout status deploy/my-web
Waiting for deployment "my-web" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "my-web" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "my-web" rollout to finish: 1 old replicas are pending termination...
deployment "my-web" successfully rolled out

刷新浏览器，看到「Version 1.1」。发现新版本有问题？回滚（第 6 章），记得同时把 YAML 改回去：

$ kubectl rollout undo deploy/my-web
$ sed -i 's/k8sbook-web:1.1/k8sbook-web:1.0/' deploy.yml
★ 每个版本一个新标签，永远不要覆盖

如果你修改代码后仍然推送到 1.0 这个标签，Kubernetes 看到 YAML 没变化，不会做任何事；即使手动重建 Pod， 已经缓存了旧 1.0 的节点也可能继续使用旧镜像（默认 imagePullPolicy: IfNotPresent）。 同理，不要在生产中使用 latest：你无法从 YAML 看出跑的是哪个版本，也无法可靠地回滚。 更严格的做法是用镜像摘要（@sha256:…）部署。

使用私有镜像仓库

公司的镜像通常放在私有仓库里（第 16 章）。节点拉取私有镜像需要凭据，否则就是第 17 章案例 2 里的 pull access denied：

$ kubectl create secret docker-registry regcred \
  --docker-server=ghcr.io \
  --docker-username=<用户名> \
  --docker-password=<访问令牌>

    spec:
      imagePullSecrets:
      - name: regcred                  # 和 Pod 在同一个 Namespace
      containers:
      - name: web
        image: ghcr.io/your-org/k8sbook-web:1.1

小结

  • 把应用送上 Kubernetes 的标准流程：源码 + Dockerfile → docker build → docker push → kubectl apply。
  • Dockerfile 的每条指令是一层：变化少的放前面，充分利用缓存；固定基础镜像版本，非 root 运行，用 tini 或代码正确处理 SIGTERM。
  • 镜像要推到集群能访问的仓库；私有仓库用 imagePullSecrets；注意 CPU 架构匹配。
  • 每个版本使用新的标签，改 YAML 后 apply，由 Deployment 完成零停机滚动更新，必要时回滚。

动手练习

  1. 用 docker history <镜像> 分别查看原版和改进版 Dockerfile 构建出的镜像，比较层数和大小。
  2. 把改进版 Dockerfile 里的 ENTRYPOINT 行删掉重新构建，部署后执行 kubectl delete pod，用 time 比较删除所需时间。
  3. 给 app.js 加一个 /healthz 路由，把存活探针改成 httpGet /healthz，发布为 1.2 版本。
  4. 参考第 15 章，给 Deployment 加上 securityContext（runAsNonRoot: true、allowPrivilegeEscalation: false），部署到一个 enforce=restricted 的 Namespace 里，看看还缺哪些设置。
