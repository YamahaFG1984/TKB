第 2 章

Kubernetes 工作原理

这一章是全书的地图。我们会认识集群里的每一个主要部件，搞懂 Kubernetes 最核心的思想—— 声明式模型与期望状态，并初次见到 Pod、Deployment 和 Service 这三个后面天天打交道的对象。

本章目标

  • 区分控制平面节点和工作节点，说出各自运行哪些组件
  • 理解 API 服务器、etcd、调度器、控制器、kubelet、kube-proxy 分别干什么
  • 理解为什么 etcd 要用奇数个副本（脑裂问题）
  • 掌握期望状态 / 观测状态 / 调和这三个概念
  • 知道应用要怎样层层「包装」才能跑在 Kubernetes 上

从万米高空看 Kubernetes

Kubernetes 同时是两样东西：

  • 一个集群：由一个或多个节点（node）组成，为应用提供 CPU、内存等资源；
  • 一个编排器：把应用智能地部署到节点上，坏了修、忙了扩、要更新就滚动发布。

集群里有两种节点：

控制平面节点工作节点
职责实现 Kubernetes 的「智能」：暴露 API、调度、自愈、扩缩、发布……运行你的业务应用
操作系统必须是 LinuxLinux 或 Windows（一个集群可以混用）
数量至少 1 个；生产环境 3 或 5 个以实现高可用（HA）按业务需要
形态物理机、虚拟机、云主机都行；ARM 和 x86-64 都支持
💡 控制平面上能跑业务吗？

开发、测试环境里很常见。但生产环境通常只让业务跑在工作节点上，让控制平面节点把资源专心用在管理集群上。

控制平面：集群的大脑

控制平面是一组系统服务。最简单的集群只有一个控制平面节点，适合实验；生产集群应该运行 3 或 5 个，并分散到不同可用区。 通常每个控制平面节点都运行全部控制平面服务，这样任何一个挂了都不影响大局。

API 服务器：一切请求的前门

API 服务器是 Kubernetes 的前端，所有命令和请求都要经过它，连控制平面内部的服务之间也通过它通信。 它通过 HTTPS 暴露 RESTful API，每个请求都要经过认证和授权。部署或更新一个应用的过程是这样的：

集群存储（etcd）

集群存储保存着所有应用和集群组件的期望状态，是控制平面里唯一有状态的部分。 它基于分布式数据库 etcd，大多数集群在每个控制平面节点上跑一个 etcd 副本；变化特别频繁的大集群可能会单独部署一个 etcd 集群以获得更好性能。

⚠ 高可用 ≠ 备份

etcd 有多个副本只能防止「某台机器挂了」，防不了「误删了数据」——误删会被同步到所有副本。你仍然需要真正的备份与恢复方案。

为什么副本数要是奇数？——脑裂问题

当网络出故障把副本分成两半、彼此联系不上时，每一边都要判断自己是不是多数派（quorum）。只有多数派才能继续写入。

一旦发生脑裂，etcd 会进入只读模式：已经在跑的业务应用照常工作，但 Kubernetes 没法再扩缩或更新它们。 etcd 用 RAFT 共识算法保证多个来源同时写入时数据不会损坏。

控制器与控制器管理器

Kubernetes 的大部分智能由控制器（controller）实现，比如 Deployment 控制器、StatefulSet 控制器、ReplicaSet 控制器。 它们都以后台监视循环（watch loop）的形式运行，不停地把观测状态调和成期望状态。 用大白话说：你要 3 个副本，控制器就保证有 3 个健康的副本，不够就补，多了就删。 控制器管理器负责启动和管理这些控制器。

调度器

调度器监视 API 服务器上的新任务，并把它们分配给健康的工作节点：

过滤时会检查污点（taint）、亲和性与反亲和性规则、网络端口是否可用、CPU 和内存是否充足。 如果找不到合适节点，任务会被标记为 Pending；如果集群开启了节点自动扩缩，这个 Pending 任务会触发扩容，新节点加入后调度器再把任务分过去。

云控制器管理器

如果集群运行在 AWS、Azure、GCP、Civo 这类公有云上，它会运行一个云控制器管理器，把集群和云服务（云主机、负载均衡器、存储）打通。 比如应用申请一个负载均衡器，它就会去云上真的创建一个，并接到你的应用上。

工作节点：真正干活的地方

🤖

kubelet

主代理。监视 API 服务器上的新任务 → 交给运行时执行 → 把状态汇报回去。任务跑不起来时也只汇报，由控制平面决定怎么办。

📦

运行时

大多数新集群预装 containerd。负责拉取镜像、启动停止容器。OpenShift 用 CRI-O。Docker 运行时已不再支持。

🔀

kube-proxy

每个节点都跑一个，负责集群网络，并把流量负载均衡到本节点上的任务。

为 Kubernetes 打包应用

Kubernetes 能运行容器、虚拟机、Wasm 应用等等，但它们都必须先包进 Pod 才能运行。 书里用了一个快递的比喻：

📦 快递比喻

快递公司能寄书、衣服、食品、电器……只要你用它认可的包装和面单。打包好交给快递员后， 用哪架飞机、哪辆卡车、在哪个中转站交接，全是快递公司的事；它还提供查件、改地址、签收证明等服务。

Kubernetes 也一样：只要你把应用包进 Pod，它就负责选节点、接网络、挂存储这些复杂物流。 而保价、冷链、加急这类增值服务，就对应 Kubernetes 的控制器（比如 Deployment 提供自愈和扩缩）。

对应的 YAML 大概长这样（现在只是混个眼熟，第 6 章会逐行讲解）：

kind: Deployment          # 最外层：Deployment
spec:
  replicas: 10            # 要 10 个副本
  template:               # ↓ 下面是 Pod 模板
    spec:
      containers:         # ↓ Pod 里的容器
      - name: hello-pod
        image: nigelpoulton/k8sbook:1.0   # 容器里装的应用
        ports:
        - containerPort: 8080

声明式模型与期望状态

这是 Kubernetes 最核心的思想，建立在三个概念之上：

🎯

期望状态

你想要什么：用哪个镜像、几个副本、哪些端口……

🔍

观测状态

你实际有什么。也叫实际状态、当前状态，都是一个意思。

🔄

调和

让观测状态持续和期望状态保持一致的过程。

  1. 在 YAML 清单文件里描述应用的期望状态
  2. 把 YAML 提交给 API 服务器（最常用 kubectl 命令行工具），经过认证和授权
  3. Kubernetes 把它作为意图记录（record of intent）存进集群存储
  4. 某个控制器发现观测状态和新的期望状态不一致
  5. 控制器进行必要的变更来消除差异：调度 Pod、拉镜像、启动容器、接入网络……
  6. 控制器继续在后台运行，确保观测状态永远和期望状态一致

声明式 vs 命令式

命令式：告诉系统「怎么做」
# 一步一步来，每个平台写法都不一样
for node in node1 node2 node3; do
  ssh $node "docker pull app:2.0"
  ssh $node "docker stop app"
  ssh $node "docker run -d app:2.0"
  # 还要自己检查健康、处理失败、回滚……
done
声明式：告诉系统「要什么」
# 只改一行，剩下的交给 Kubernetes
spec:
  replicas: 10
  template:
    spec:
      containers:
      - image: app:2.0   # 原来是 1.0

Kubernetes 两种方式都支持，但更推荐声明式：YAML 文件可以放进 Git 做版本管理，而且自愈、自动扩缩、滚动更新都建立在声明式之上。 比如要升级镜像版本，命令式需要写复杂的脚本来管理、监控、健康检查整个过程；声明式只需改一行 YAML。

Pod

在 VMware 的世界里，调度的原子单位是虚拟机；在 Kubernetes 里，是 Pod。 最简单的情况是一个 Pod 里只有一个容器，所以我们有时会把 Pod 和容器混着说。但多容器 Pod 也有很强的用途：

  • 服务网格（service mesh）
  • 负责初始化环境的辅助服务
  • 和主应用紧密耦合的辅助功能，比如日志采集器

多容器 Pod 还能帮我们落实单一职责原则：主容器只管业务，加密、遥测这类事交给同一个 Pod 里的 sidecar。 只有在组件紧密耦合、需要共享内存或存储时才用多容器 Pod；其他情况都用单容器 Pod，通过网络松散地连接起来。

关于 Pod 的五条铁律

📍

同一 Pod 只在一个节点

Kubernetes 调度的是 Pod，不是单个容器。共享内存和网络没法跨节点。

⚖

启动是原子的

所有容器都跑起来，Pod 才算 Ready。两个容器只起来一个 = 没准备好。

📈

扩缩的单位是 Pod

扩容是加 Pod，缩容是删 Pod。不是往已有的 Pod 里加容器。

☠

Pod 会死

死了就被替换成一个全新的 Pod：新 ID、新 IP。所以应用要松耦合。

🧊

Pod 不可变

运行中的 Pod 不去修改。「更新 Pod」永远意味着删掉旧的、换上新的。

★ 不可变是一种思维转变

永远不要登录进一个 Pod 去改东西。需要更新时，换一个跑着新代码的新 Pod。 这对很多运维习惯是很大的转变，但它与现代工具和 GitOps 工作流非常契合：Git 里的 YAML 就是唯一的事实来源。

Deployment

虽然 Kubernetes 以 Pod 为单位工作，但你几乎总是通过更高层的控制器来部署 Pod，比如 Deployment、StatefulSet、DaemonSet（DaemonSet 见补充篇第 20 章）。 它们都是控制平面上的后台监视循环。Deployment 为无状态应用提供自愈、扩缩、滚动更新和版本回滚。

Service 与稳定的网络

前面说了 Pod 会死，而且被替换后 IP 会变。不光是故障，下面这些事件也会导致 IP 不停变化（IP churn）：

  • 发布新版本：新 Pod 替换旧 Pod，新 IP
  • 扩容：新增的 Pod 有新 IP
  • 缩容：已有 Pod 被删除

所以客户端没法可靠地直接连某个 Pod。Service 就是来解决这个问题的：

可以把 Service 想成有前端和后端：前端有稳定的 DNS 名字、IP 和端口，永远不会变； 后端通过标签（label）在一组动态变化的 Pod 之间做负载均衡，并始终只把流量发给健康的 Pod。 （Service 首字母大写，表示它是 Kubernetes 的 API 资源，区别于泛指的「服务」。）

小结

  • 控制平面是大脑：API 服务器（唯一入口）、etcd（唯一有状态的存储）、调度器、控制器管理器、云控制器管理器。生产环境跑 3 或 5 个节点。
  • 工作节点运行业务：kubelet（代理）、运行时（containerd）、kube-proxy（网络）。
  • Kubernetes 偏爱声明式：你描述期望状态，控制器不停地把观测状态调和过去。
  • 应用要包进 Pod 才能运行；Pod 是调度和扩缩的最小单位，会死、不可变。
  • Deployment 给 Pod 加上自愈、扩缩、滚动更新和回滚；Service 给一组 Pod 提供稳定的网络入口。
