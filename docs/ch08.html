第 8 章

Gateway API：把外部流量路由进集群

每个应用都开一个 LoadBalancer Service？云负载均衡器很贵，而且它只懂 TCP 端口，不懂 HTTP 路径和主机名。 Gateway API 是 Kubernetes 原生的解决方案：一个负载均衡器服务多个应用，支持按路径、请求头路由和按权重分流， 并且天生适配团队分工。它已经取代 Ingress 成为战略方向。

本章目标

  • 知道为什么 Ingress 被淘汰
  • 理解 Gateway API 的三大核心资源：GatewayClass、Gateway、HTTPRoute
  • 理解 Gateway 控制器如何「认领」GatewayClass 并部署 Gateway
  • 分清控制平面与数据平面、混合数据平面与全托管数据平面
  • 理解面向角色的设计，以及如何限制哪些路由能绑定到网关
  • 动手完成金丝雀分流（80/20）和跨 Namespace 路由两个实验

为什么不用 Ingress 了

Ingress 是 Gateway API 的前身，但它从来不是一个战略性项目，缺乏投入，最终在一堆安全隐患下年久失修。 SIG Network 小组和安全响应委员会宣布：最流行的实现 Ingress NGINX 将在 2026 年 3 月停止所有开发和缺陷修复。 现有部署还能继续工作，但你应该考虑迁移到 Gateway API。用过 Ingress 的话，你会在 Gateway API 里看到很多熟悉的概念。

🔍

懂协议

已支持 HTTP、HTTPS、gRPC，TCP 和 UDP 正在路上。

🔀

一个负载均衡器，按主机名、路径、请求头把流量分给不同应用。

⚖

轻松实现金丝雀发布、A/B 测试。

资源模型对应组织分工，并支持跨 Namespace 路由的多租户场景。

ⓘ Gateway API 只是一份规范

Kubernetes 本身没有默认实现，你需要自己安装一个。好在 Cilium、Envoy、Istio、NGINX、Traefik 等项目都有实现，安装简单，在大多数云和本地环境表现一致。 有些云平台会预装自己的实现，但它们是专有的，可能加深云厂商锁定。

全局视图

每一个 Gateway API 实现（implementation）都会安装三样东西：

  1. API 资源：GatewayClass（连接 Gateway 和控制器）、Gateway（创建负载均衡器）、HTTPRoute（添加路由逻辑）等；
  2. Gateway 控制器：监视新的 Gateway 并部署它们；
  3. 一个或多个 GatewayClass：把 Gateway 和正确的控制器关联起来。

实现分三个一致性等级：Conformant（完全一致）、Partially conformant（部分一致）和 Stale（过时）。 完全一致至少要支持 Gateway 和 HTTPRoute。本章以 Envoy Gateway 和 NGINX Gateway Fabric 为例，但原理和流程适用于所有实现。

Gateway 控制器与 GatewayClass

每个实现都有自己的控制器，负责 Gateway API 的控制平面：监视 API 服务器上的新 Gateway，并部署、更新或删除它们。 一个集群可以同时安装多个实现，所以 Gateway 通过 GatewayClass 指定由哪个控制器来管它。

以 Envoy Gateway 为例，安装是典型的三步：

  1. 安装 API 资源；
  2. 部署控制器：它以 Pod 形式运行在 envoy-gateway-system Namespace 里（前面有个 ClusterIP Service），完整控制器名是 gateway.envoyproxy.io/gatewayclass-controller，开始监视声明了这个名字的 GatewayClass；
  3. 创建一个 GatewayClass（比如叫 eg-external）声明这个控制器名。控制器看到后认领（claim）它，并开始监视引用 eg-external 的 Gateway。

GatewayClass

最简单的形式，就是给控制器的长名字起个好记的短名：

apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg-external        # Gateway 引用的友好名字
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller

GatewayClass 还能「编程」控制器的行为。比如同一个 Envoy 控制器，定义两个 GatewayClass：

apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg-internal
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
  parametersRef:                    # ┐ 引用一个名为 envoy-internal
    group: gateway.envoyproxy.io    # │ 的 EnvoyProxy 资源
    kind: EnvoyProxy                # │
    name: envoy-internal            # ┘
---
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: envoy-internal
spec:
  provider:
    type: Kubernetes
    kubernetes:
      envoyService:
        type: LoadBalancer
        annotations:
          networking.gke.io/load-balancer-type: "Internal"   # GKE 内部负载均衡器

被控制器认领的 GatewayClass 会显示 ACCEPTED = True；控制器名写错的则一直是 Unknown，等着永远不会来的控制器：

$ kubectl get gc
NAME          CONTROLLER                                      ACCEPTED
eg-internal   gateway.envoyproxy.io/gatewayclass-controller   True
fake          gateway.fake.io/made-up-provider                Unknown

Gateway：集群的入口

Gateway 代表外部客户端进入集群的入口。在云上部署一个 Gateway，你会得到一个云的互联网负载均衡器；在笔记本集群上通常得到一个本地 IP。 Gateway 是负载均衡器，listener（监听器）是它的接口。 

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: gtw-prod
spec:
  gatewayClassName: eg-external
  listeners:
  - name: http             # ┐ 接口 1：
    protocol: HTTP         # │ 监听发往 myapp.com
    hostname: "myapp.com"  # │ 的 HTTP 流量
    port: 8080             # ┘ 端口 8080
  - name: metrics          # ┐ 接口 2：
    protocol: HTTP         # │ 监听发往 myapp.com
    hostname: "myapp.com"  # │ 的 HTTP 流量
    port: 5005             # ┘ 端口 5005

混合数据平面：L4 负载均衡器 + L7 代理 Pod

部署上面这个 Gateway，你会得到一个混合数据平面：集群外的负载均衡器只做 L4 TCP 转发（只管端口）， 集群内的数据平面 Pod（这里是 Envoy）实现 L7 智能（协议、主机名、路径路由、加权分流）。

部署 Gateway 后幕后发生的事：

  1. 监视 eg-external 的 Envoy Gateway 控制器认领这个 Gateway；
  2. 控制器部署数据平面 Pod，并创建一个 LoadBalancer Service（端口与 Gateway 一致，选择器指向数据平面 Pod）作为「意图声明」；
  3. API 服务器校验并持久化这个 Service，Service 控制器为每个端口分配 NodePort；
  4. 每个节点上的 kube-proxy 编写本地转发规则，把打到 NodePort 的流量负载均衡到数据平面 Pod；
  5. 云控制器管理器向云平台申请一个互联网负载均衡器，转发到节点的 NodePort；创建完成后把公网 IP 回写到 Service。
apiVersion: v1
kind: Service
metadata:
  name: envoy-default-gtw-prod-f71aafc2
spec:
  type: LoadBalancer         # 触发创建云负载均衡器
  ports:
  - name: port-8080          # 对应 "http" listener
    port: 8080
    protocol: TCP
    targetPort: 8080
    nodePort: 31423          # Service 控制器随后补上
  - name: port-5005          # 对应 "metrics" listener
    port: 5005
    protocol: TCP
    targetPort: 5005
    nodePort: 30270
  selector:
    app.kubernetes.io/name: envoy
    gateway.envoyproxy.io/owning-gateway-name: gtw-prod

HTTPRoute：决定流量去哪

Gateway 的 listener 负责接收流量，HTTPRoute 负责决定流量去哪。 把路由逻辑（HTTPRoute）和基础设施（Gateway）解耦，是一个关键的设计决策：基础设施管理员部署设施，开发者给它编程。 

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: route-kits
spec:
  parentRefs:                # ┐ 绑定到 gtw-prod 的
  - name: gtw-prod           # │ http listener
    sectionName: http        # ┘
  hostnames:                 # ┐ 只处理发往
  - www.myapp.com            # ┘ www.myapp.com 的请求
  rules:
  - matches:                 # ┐
    - path:                  # │ 匹配 /kits 路径
        type: PathPrefix     # │
        value: /kits         # ┘
    backendRefs:
    - name: svc-kits         # ┐ 80% 的请求发给
      port: 8080             # │ svc-kits:8080
      weight: 8              # ┘
    - name: svc-kits-test    # ┐ 20% 的请求发给
      port: 8080             # │ svc-kits-test:8080
      weight: 2              # ┘

两层主机名过滤

匹配规则：AND 与 OR

同一个 match 块里的条件 = AND
matches:
- path:              # 路径是 /api
    type: PathPrefix
    value: /api
  method: GET        # 并且 是 GET 请求
多个 match 块 = OR
matches:
- path:              # 路径是 /api
    type: PathPrefix
    value: /api
- path:              # 或者 /apis
    type: PathPrefix
    value: /apis

spec.rules 可以按路径、请求头、HTTP 方法过滤。除了 HTTPRoute，Gateway API 还支持 GRPCRoute，并实验性地支持 TCPRoute、UDPRoute、TLSRoute。

把它们串起来

以 NGINX Gateway Fabric（默认控制器名 gateway.nginx.org/nginx-gateway-controller）为例：

apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: nginx                  # Gateway 引用的友好名字
spec:
  controllerName: gateway.nginx.org/nginx-gateway-controller
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: gtw-prod-4
spec:
  gatewayClassName: nginx      # 使用这个 GatewayClass
  listeners:
  - name: list-kits
    protocol: HTTP
    port: 8080
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: route-kits
spec:
  parentRefs:
  - name: gtw-prod-4           # 绑定到 gtw-prod-4 Gateway
    sectionName: list-kits     # 的 list-kits listener
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /kits           # /kits 路径的请求
    backendRefs:
    - name: svc-kits           # 发给 svc-kits Service 的 9000 端口
      port: 9000

面向角色的设计

Gateway API 的维护者从 Ingress 中吸取了很多教训，让资源可以映射到组织中的角色：

📝 一个真实的协作流程

你要上线一个新应用，用户通过 www.myapp.com/kits 的 8080 端口访问，你分到了新集群 asia-south-kube17 上的 ns-kits Namespace。 你把应用打包成 Deployment + ClusterIP Service，然后向 cluster-ops 团队申请一个监听 myapp.com:8080 的互联网负载均衡器。 这是新集群，cluster-ops 找 kube-infra 团队要 GatewayClass；kube-infra 安装公司认可的实现并告知 GatewayClass 名。 cluster-ops 在 ns-infra 里部署 Gateway，允许来自 ns-kits 的 HTTPRoute 绑定，并把 Gateway 和 listener 名告诉你。 最后你写一个 HTTPRoute 绑上去，把 www.myapp.com/kits 路由到你的 Service。分工清清楚楚。

控制平面、数据平面与两种实现形态

  • 控制平面：一个或多个 Gateway API 控制器 Pod，负责创建和配置数据平面。
  • 数据平面：处理真实流量，通常是「负载均衡器（L4）+ 一组数据平面 Pod（L7）」。

动手：安装 Gateway API 实现

云集群：安装 NGINX Gateway Fabric

NGINX Gateway Fabric 是完全一致的实现，在云上会为每个 Gateway 自动创建一个互联网负载均衡器。需要 kubectl 和 helm 命令行工具。

# 第 1 步：安装 Gateway API 资源（注意中间的管道符 |）
$ kubectl kustomize \
  "https://github.com/nginx/nginx-gateway-fabric/config/crd/gateway-api/standard?ref=v2.3.0" \
  | kubectl apply -f -

# 第 2 步：安装控制器，并创建名为 nginx 的 GatewayClass
$ helm install ngf oci://ghcr.io/nginx/charts/nginx-gateway-fabric \
  --version 2.3.0 \
  --namespace nginx-gateway \
  --create-namespace

$ kubectl get pods -n nginx-gateway

本地 KIND 集群：安装 Cloud Provider for KIND

这是一个尽力而为的社区项目，提供用于本地测试的最小实现。先获取二进制文件：

$ brew install cloud-provider-kind                          # Mac
$ go install sigs.k8s.io/cloud-provider-kind@latest         # 或者用 Go 编译（任意系统）
$ sudo install ~/go/bin/cloud-provider-kind /usr/local/bin

# 在一个新的终端窗口里运行，并保持它一直运行
$ sudo cloud-provider-kind --gateway-channel="standard"
🔮 控制器可以不在集群里？

动手：金丝雀分流（80/20）

部署同一应用的两个版本，用一个 Gateway 和一个 HTTPRoute 把 80% 的请求发给当前版本、20% 发给旧版本。命令都在 gateway-api/app-canary 目录下执行。

1. 部署两个应用

apiVersion: apps/v1
kind: Deployment
metadata:
  name: current
spec:
  replicas: 3                    # 两个应用都是 3 个副本
  selector:
    matchLabels:
      app: badge-lions
  template:
    metadata:
      labels:
        app: badge-lions
    spec:
      containers:
      - name: web-pod
        image: nigelpoulton/k8sbook:gtw-lion
        imagePullPolicy: Always
        ports:
        - containerPort: 8080    # 应用监听 8080
---
apiVersion: v1
kind: Service
metadata:
  name: svc-current
spec:
  type: ClusterIP
  selector:
    app: badge-lions
  ports:
    - name: httpd
      port: 8080                 # Service 监听 8080
      targetPort: 8080           # 发给应用的 8080

$ kubectl apply -f app.yml
service/svc-current created
deployment.apps/current created
service/svc-previous created
deployment.apps/previous created

$ kubectl get deploy
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
current    3/3     3            3           25s
previous   3/3     3            3           24s

2. 部署 Gateway

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: gtw-prod-1
spec:
  gatewayClassName: nginx       # 要和你的 GatewayClass 名一致！
  listeners:
  - name: list-safc
    protocol: HTTP              # 由数据平面 Pod 执行
    port: 8080                  # 由 L4 负载均衡器执行
    allowedRoutes:
      namespaces:
        from: Same              # 只允许同 Namespace 的 HTTPRoute 绑定
⚠ 先改 gatewayClassName

用 KIND 的话要改成 cloud-provider-kind。不确定就运行 kubectl get gc，用 NAME 列的值。

$ kubectl apply -f gtw.yml
gateway.gateway.networking.k8s.io/gtw-prod-1 created

$ kubectl get gtw
NAME         CLASS   ADDRESS        PROGRAMMED
gtw-prod-1   nginx   139.14.17.33   True

云上可能要等一两分钟才拿到 IP 并显示 PROGRAMMED。记下这个地址。

3. 部署 HTTPRoute

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: route-canary
spec:
  parentRefs:                  # ┐ 绑定到 gtw-prod-1
  - name: gtw-prod-1           # │ 的 list-safc listener
    sectionName: list-safc     # ┘
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /               # 根路径下的所有请求
    backendRefs:
    - name: svc-current        # 80% → svc-current:8080
      port: 8080
      weight: 80
    - name: svc-previous       # 20% → svc-previous:8080
      port: 8080
      weight: 20

$ kubectl apply -f route.yml
httproute.gateway.networking.k8s.io/route-canary created

$ kubectl get httproute
NAME           HOSTNAMES   AGE
route-canary               11s

两者都在 default Namespace，而 listener 允许同 Namespace 的路由绑定，所以绑定成功。浏览器打开 Gateway地址:8080，多刷新几次，大约 80% 的时候看到当前队徽。

💡 示例应用里的小心思

看 source/app-ship/server.js 会发现，作者把队徽图片用 base64 内联进 HTML。原因是：如果图片是单独的 PNG 请求， HTML 和图片可能被分别负载均衡到不同版本，就得配置会话保持（session persistence），而并非所有 Gateway API 实现都支持它。

⚠ 一定要通过 Kubernetes 删除 Gateway

如果集群在云上，直接删集群并不会删掉云负载均衡器，你会继续为它付费。

动手：跨 Namespace 的多租户路由

场景：公司有多个集群，需要强隔离的应用独占集群，其余应用在多租户集群上各占一个 Namespace。 现在要上线 shield 和 hydra 两个应用，通过 myapp.com:8080/shield 和 /hydra 访问，共享一个负载均衡器。

组织的 RBAC 分工（本实验不实际配置 RBAC，但 YAML 文件的拆分方式能直接对应）：

  • infra-admins：管理集群和 Gateway API 实现
  • cluster-ops：管理 Namespace 和 Gateway
  • shield-devs / hydra-devs：各自管理自己应用的 HTTPRoute、Deployment 和 Service

以下命令在 gateway-api/app-xnamespace 目录执行。

1. 创建 Namespace（cluster-ops）

apiVersion: v1
kind: Namespace
metadata:
  name: ns-infra
---
apiVersion: v1
kind: Namespace
metadata:
  name: ns-shield
  labels:
    gtw-prod-6: "yes"      # 用于允许 HTTPRoute 绑定到 Gateway
---
apiVersion: v1
kind: Namespace
metadata:
  name: ns-hydra
  labels:
    gtw-prod-6: "yes"      # 用于允许 HTTPRoute 绑定到 Gateway

$ kubectl apply -f ns.yml
namespace/ns-infra created
namespace/ns-shield created
namespace/ns-hydra created

2. 部署共享 Gateway（cluster-ops）

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: gtw-prod-6           # ┐ 在 ns-infra 里创建
  namespace: ns-infra        # ┘ 名为 gtw-prod-6 的 Gateway
spec:
  gatewayClassName: nginx    # 用别的实现记得改
  listeners:
  - name: http               # ┐ 名为 http 的 listener，
    hostname: "myapp.com"    # │ 监听发往 myapp.com
    protocol: HTTP           # │ 8080 端口的 HTTP 请求
    port: 8080               # ┘
    allowedRoutes:
      namespaces:
        from: Selector       # ┐ 只允许来自带有
        selector:            # │ gtw-prod-6=yes 标签的
          matchLabels:       # │ Namespace 的路由绑定
            gtw-prod-6: "yes"  # ┘

小结

  • Gateway API 取代 Ingress，成为把外部流量路由到 Kubernetes 应用的原生方案；它是一份规范，由 Cilium、Envoy、Istio、NGINX、Traefik 等项目实现。尽量选择 gateway-api.sigs.k8s.io 上列出的完全一致实现。
  • 安装一个实现 = API 资源 + 控制器 + GatewayClass。
  • GatewayClass 指定由哪个控制器管理 Gateway；Gateway 就是负载均衡器实例（每部署一个就多一个 LB）；HTTPRoute 实现高级路由，支持金丝雀、A/B 等发布模式。
  • 混合数据平面 = L4 负载均衡器 + 集群内 L7 代理 Pod；全托管数据平面由云平台包办但可能带来锁定。
  • 资源模型为 RBAC 而设计：Gateway 和路由规则分离，不同团队各管各的，并能控制哪些路由可以绑定到哪个 Gateway。
