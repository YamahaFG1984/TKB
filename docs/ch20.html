Job、CronJob 与 DaemonSet

Deployment 管的是「一直运行」的无状态服务，StatefulSet 管的是有状态应用。但还有三类同样常见的需求： 跑完就结束的任务、按时间表定期运行的任务，以及每个节点上都要有一份的后台程序。 它们分别由 Job、CronJob 和 DaemonSet 来管理。

ⓘ 关于补充篇

本章不是原书内容（原书只在第 2、4 章提到过这些对象的名字）。配套文件在仓库的 extras/workloads/ 目录。

⚠ 待验证：本章命令输出尚未在真实集群上运行核对

本章的示例 YAML 已通过语法校验，但文中展示的命令输出是按 Kubernetes 标准格式整理的，还没有在真实集群上逐条运行核对。 如果你实际看到的输出与文中不同，以你的集群为准。

本章目标

  • 根据应用类型选对工作负载控制器
  • 用 Job 运行一次性任务，掌握 completions、parallelism、backoffLimit 等参数
  • 用 CronJob 运行定时任务，读懂 cron 表达式和并发策略
  • 用 DaemonSet 在每个节点上运行一个 Pod，理解它与污点、容忍的关系

选对工作负载控制器

它们都是同一套架构：一个 API 资源 + 一个在控制平面上运行调和循环的控制器，最终都通过创建 Pod 来干活。

Job：跑完就结束

Deployment 里的 Pod 一旦退出，就会被重启或替换，因为它的目标是「一直有 N 个在运行」。 Job 的目标完全不同：确保有 N 个 Pod 成功完成。Pod 成功退出（退出码 0）后不会再被拉起，Job 记为完成。

最简单的 Job

apiVersion: batch/v1             # Job 在 batch API 组
kind: Job
metadata:
  name: pi
spec:
  backoffLimit: 4                # 失败重试最多 4 次
  ttlSecondsAfterFinished: 600   # 完成 10 分钟后自动删除 Job 和它的 Pod
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: pi
        image: perl:5.34
        command: ["perl", "-Mbignum=bpi", "-wle", "print bpi(2000)"]   # 计算圆周率到 2000 位

$ cd extras/workloads
$ kubectl apply -f job-pi.yml
job.batch/pi created

$ kubectl get jobs --watch
NAME   STATUS     COMPLETIONS   DURATION   AGE
pi     Running    0/1           10s        10s
pi     Complete   1/1           42s        42s

$ kubectl get pods -l job-name=pi
NAME       READY   STATUS      RESTARTS   AGE
pi-7xk2m   0/1     Completed   0          50s

$ kubectl logs job/pi | head -c 60
3.14159265358979323846264338327950288419716939937510582097

Pod 的状态是 Completed，而不是 Running。Job 会自动给它的 Pod 打上 job-name 标签，方便查找。 完成的 Pod 默认会保留下来供你查看日志，ttlSecondsAfterFinished 让它们在一段时间后被自动清理。

并行与多次完成

字段默认值含义

💡 restartPolicy 的两种选择
  • Never：失败后创建新的 Pod 重试，每次失败的 Pod 都留着，方便逐个看日志（上面的例子）。
  • OnFailure：在同一个 Pod 里重启容器，Pod 数量少，但旧的日志只能用 --previous 看最近一次。

重试之间同样有指数退避（10 秒、20 秒、40 秒……），和第 17 章的 CrashLoopBackOff 是一个道理。

$ kubectl delete -f job-pi.yml -f job-parallel.yml -f job-fail.yml    # 删除 Job 会连带删除它的 Pod

CronJob：按时间表运行

CronJob 按照 cron 表达式定期创建 Job。它和 Job、Pod 的关系，与 Deployment、ReplicaSet、Pod 的关系如出一辙：

cron 表达式

表达式含义
*/1 * * * *每分钟
0 * * * *每小时整点
0 3 * * *每天凌晨 3 点
0 9 * * 1每周一上午 9 点
0 0 1 * *每月 1 号零点
⚠ 时区

不设置时，时间按 kube-controller-manager 所在的时区解释，托管集群上通常是 UTC。 用 spec.timeZone（例如 "Asia/Shanghai"）明确指定，免得「凌晨 3 点的备份」实际在上午 11 点运行。

示例与关键字段

apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello-cron
spec:
  schedule: "*/1 * * * *"            # 每分钟
  timeZone: "Etc/UTC"
  concurrencyPolicy: Forbid          # 上一次还没跑完，就跳过这一次
  startingDeadlineSeconds: 30        # 错过预定时间 30 秒以上就不补跑
  successfulJobsHistoryLimit: 3      # 保留最近 3 个成功的 Job
  failedJobsHistoryLimit: 1          # 保留最近 1 个失败的 Job
  jobTemplate:                       # ↓ 以下就是一个 Job 的 spec
    spec:
      backoffLimit: 1
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: hello
            image: busybox:1.36
            command: ["sh", "-c", "date; echo hello from a CronJob"]
concurrencyPolicy上一次还在运行时，到了下一个时间点适合
Allow（默认）照常启动，两次同时运行彼此独立、可以重叠的任务
Forbid跳过这一次备份、数据同步等不能同时跑的任务
Replace停掉上一次，启动新的只关心最新一次结果的任务

$ kubectl get cronjob hello-cron

hello-cron   */1 * * * *   Etc/UTC    False     0        25s             3m

$ kubectl get jobs
NAME                  STATUS     COMPLETIONS   DURATION   AGE
hello-cron-29384510   Complete   1/1           4s         2m25s
hello-cron-29384511   Complete   1/1           3s         85s
hello-cron-29384512   Complete   1/1           4s         25s

$ kubectl logs job/hello-cron-29384512

hello from a CronJob

两个日常很有用的操作：

# 不等时间表，立刻手动触发一次（测试 CronJob 时特别方便）
$ kubectl create job hello-manual --from=cronjob/hello-cron

# 暂停 / 恢复调度（已经在跑的不受影响）
$ kubectl patch cronjob hello-cron -p '{"spec":{"suspend":true}}'
$ kubectl patch cronjob hello-cron -p '{"spec":{"suspend":false}}'

$ kubectl delete -f cronjob.yml
$ kubectl delete job hello-manual
ⓘ 任务要能重复执行

在少数情况下（比如控制器重启、节点故障），同一个时间点的任务可能被创建两次，也可能被跳过。 所以 CronJob 的任务最好是幂等的：重复执行一次也不会出错，比如「把今天的数据同步过去」而不是「把计数器加一」。

DaemonSet：每个节点一个

有些程序必须在每个节点上都运行一份：采集节点日志的代理、上报节点指标的监控代理、网络插件、存储插件…… DaemonSet 保证每个（符合条件的）节点上恰好运行一个它的 Pod：新节点加入时自动补上，节点移除时自动回收。 你其实早就在用了——很多集群里的 kube-proxy 和 CNI 网络插件就是以 DaemonSet 运行的。 

$ kubectl get daemonsets -n kube-system
NAME         DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR            AGE
kindnet      3         3         3       3            3           kubernetes.io/os=linux   2d
kube-proxy   3         3         3       3            3           kubernetes.io/os=linux   2d

（上面是 kind 集群的输出，你的集群里的名字可能不同，比如云上集群可能看到 Cilium、云厂商的存储插件等。）

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
spec:
  selector:
    matchLabels:
      app: node-agent
  updateStrategy:
    type: RollingUpdate            # 更新时逐个节点替换
    rollingUpdate:
      maxUnavailable: 1
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      tolerations:                 # 容忍控制平面节点的污点，也在那里运行
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: agent
        image: busybox:1.36
        command: ["sh", "-c", "while true; do echo \"agent running on node $NODE_NAME\"; sleep 30; done"]
        env:
        - name: NODE_NAME          # 把所在节点的名字注入环境变量
          valueFrom:
            fieldRef:
              fieldPath: spec.nodeName
        resources:
          requests:
            cpu: 10m
            memory: 16Mi
          limits:
            memory: 32Mi
ⓘ 两个新面孔
  • tolerations（容忍）：控制平面节点通常带有 node-role.kubernetes.io/control-plane:NoSchedule 污点，普通 Pod 不会被调度上去（第 2 章说过生产环境一般不在控制平面上跑业务）。日志、监控代理往往需要覆盖所有节点，所以加上对应的容忍。
  • fieldRef（Downward API）：把 Pod 自身的信息（这里是所在节点名）注入环境变量，应用不用访问 API 服务器就能知道自己在哪个节点上。

只在部分节点上运行

用第 4 章讲过的 nodeSelector 或节点亲和性，可以让 DaemonSet 只覆盖带特定标签的节点，比如只在有 GPU 的节点上运行 GPU 监控代理：

    spec:
      nodeSelector:
        hardware: gpu              # 只在带有 hardware=gpu 标签的节点上运行

$ kubectl label node desktop-worker hardware=gpu     # 给节点打标签，DaemonSet 会自动在它上面创建 Pod
$ kubectl label node desktop-worker hardware-        # 去掉标签，Pod 会被自动移除

$ kubectl delete -f daemonset.yml

小结

  • Job 确保 N 个 Pod 成功完成；completions 控制总量，parallelism 控制并发，backoffLimit 控制重试，ttlSecondsAfterFinished 负责自动清理。
  • CronJob 按 cron 表达式定期创建 Job；注意时区、并发策略和历史保留，任务尽量设计成幂等。
  • DaemonSet 在每个符合条件的节点上运行一个 Pod，新节点自动补上；常配合容忍和 nodeSelector 使用。
  • 五种工作负载控制器共享同一套「资源 + 控制器 + 调和循环」的架构，区别只在于它们维护的期望状态不同。
