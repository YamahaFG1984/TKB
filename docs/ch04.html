第 4 章

Pod

Kubernetes 上的每个应用都运行在 Pod 里：部署应用就是部署 Pod，扩容就是加 Pod，更新就是换上新 Pod。 所以这一章会把 Pod 讲得很细——先讲理论，再亲手部署单容器 Pod、init 容器和 sidecar 容器。

本章目标

  • 理解 Pod 为什么是一层抽象，它给应用增加了哪些能力
  • 掌握 Pod 的生命周期、重启策略，以及「Pod 不会被重启，只会被替换」
  • 认识 Pod 网络和 CNI 插件
  • 分清 init 容器和 sidecar 容器，并会写它们的 YAML
  • 熟练使用 kubectl get / describe / logs / exec / edit 观察 Pod
  • 理解资源 requests 和 limits

Pod 是一层抽象

Pod 把工作负载的细节抽象掉了：容器、虚拟机、Serverless 函数、Wasm 应用都可以跑在 Pod 里，而 Kubernetes 并不需要知道里面是什么。好处是双向的：

  • Kubernetes 只需专注于部署和管理 Pod，不必关心里面装的是什么；
  • 不同类型的工作负载可以在同一个集群里并肩运行，共享同一套声明式 API 和 Pod 带来的所有好处。

Pod 给应用增加了什么

🤝

资源共享

🧭

nodeSelector、亲和性、拓扑分布约束……

🩺

健康探针

让 Kubernetes 知道应用是否活着、能否接流量（详见第 18 章）。

🔄

重启策略

容器挂了要不要重启。

🛡

安全策略

💾

卷与终止控制

想看 Pod 支持的全部字段？用 kubectl explain，它是随身携带的 API 文档：

$ kubectl explain pods --recursive | more     # 超过 1000 行，空格翻页，q 退出
$ kubectl explain pod.spec.restartPolicy
KIND:       Pod
VERSION:    v1
FIELD:      restartPolicy <string>
DESCRIPTION:
    Restart policy for all containers within the pod.
    One of Always, OnFailure, Never. Default to Always.

共享的执行环境

同一个 Pod 里的所有容器共享 Pod 的执行环境。在底层，这对应着几种 Linux 内核命名空间：

Pod 与调度

同一个 Pod 的所有容器一定会被调度到同一个节点。但请记住：只有当容器需要共享资源（内存、卷、网络）时才放进同一个 Pod。 如果你只是希望两个工作负载落在同一个节点上，应该把它们放在不同的 Pod 里，再用下面的手段控制调度：

手段作用一句话理解
nodeSelector给出一组标签，只调度到拥有全部这些标签的节点最简单的「指定节点」
亲和性 / 反亲和性更强大的 nodeSelector：可以靠近或远离某些节点或 Pod，支持硬规则和软规则吸引 / 排斥
拓扑分布约束按可用区等「拓扑域」把 Pod 分散开，用于高可用、就近访问等别把鸡蛋放一个篮子
资源 requests / limits告诉调度器 Pod 需要多少 CPU 和内存每个 Pod 都应该设置

部署一个 Pod 的完整过程

Pod 的生命周期

Pod 被设计成会死的（mortal）和不可变的（immutable）：

  • 会死：失败或被删除的 Pod 不能被「重启」。控制器会用新 Pod 替换它，但这和修好原来那个不是一回事。
  • 不可变：部署后就不能修改。要改就新建一个、删掉旧的。需要保存数据？挂一个卷，把数据写进卷里，Pod 没了数据还在。
🔮 题外话：虚拟机恰恰相反

虚拟机被设计成可变且长生不死的：可以重启、改配置、甚至热迁移。这和 Pod 的设计目标完全相反， 所以 KubeVirt 要把 VM 包在一种改造过的 Pod（VMI）里，并用自定义控制器管理它。

重启策略：重启的是容器，不是 Pod

节点故障、节点维护驱逐、扩缩容、更新、回滚……这些情况下 Pod 都会被删掉并替换成新 Pod：同样的 spec，但新的 UID、新的 IP、没有任何旧状态。 Kubernetes 不会重启 Pod，但可以在同一节点上重启容器。这由本地 kubelet 执行，取决于 Pod 的 spec.restartPolicy：

策略含义适合
Always（默认）容器退出就重启长期运行：Web 服务器、数据库、消息队列
OnFailure只在以错误码退出时重启批处理任务：跑完就好，失败再来
Never从不重启失败了也无所谓的一次性任务

这个策略作用于 Pod 里的所有容器（init 容器除外）。

静态 Pod vs 控制器管理的 Pod

Pod 网络

每个集群都运行着一个 Pod 网络，所有 Pod 自动接入。它通常是一个横跨所有节点的扁平二层覆盖网络（overlay）， 让每个 Pod 都能直接和任何其他 Pod 通信，即使对方在另一个节点上。 Pod 网络由第三方插件通过 CNI（Container Network Interface）实现，在建集群时选定。撰写本书时最流行的是 Cilium。

⚠ 默认网络往往是「全开」的

新建的集群通常有一个几乎没有安全限制的 Pod 网络，这让 Kubernetes 好上手。但在生产环境，你应该用 NetworkPolicy（网络策略）等手段把它管起来。

多容器 Pod：init 与 sidecar

按微服务设计原则，每个容器应只有一个明确的职责（单一职责原则 / 关注点分离）。 例如「从仓库同步内容并以网页提供」有两个职责：同步、提供。大多数时候应用容器各自放在自己的 Pod 里、通过 Pod 网络通信； 但像这个例子，把两个容器放进同一个 Pod、通过共享卷交换数据，会更合适。Kubernetes 为多容器 Pod 提供两种主要模式：

init 容器

init 容器定义在 spec.initContainers 下。Kubernetes 保证它们在主容器之前启动并完成，而且只运行一次。典型用途：

  • 等某个远程 API 就绪后再启动主应用——把「轮询检查」的逻辑从主应用里拿出去；
  • 启动前一次性克隆远程仓库——服务器地址、证书、认证、校验这些复杂逻辑都不用塞进主应用。

可以有多个 init 容器，按清单中的顺序依次运行，全部成功后才启动主容器。init 容器失败会被重试；但如果 Pod 的 restartPolicy 是 Never，整个 Pod 就失败。 init 容器的局限是：它只能在主容器之前跑。需要和主容器同时运行的辅助功能，就要用 sidecar。

sidecar 容器

sidecar 的职责是在不修改应用容器的前提下给它增加功能：采集日志、同步远程内容、代理连接、处理数据、加密流量（服务网格）…… 老版本 Kubernetes 没有 sidecar 概念，只能用普通容器模拟，无法保证启动和退出顺序。从 v1.33 起 sidecar 是稳定特性，写法是： 放在 spec.initContainers 下，并给这个容器设置 restartPolicy: Always。这样 Kubernetes 保证它：

  1. 在主应用容器之前启动
  2. 与主应用容器一起持续运行
  3. 在主应用容器之后终止

动手：第一个 Pod 清单

以下命令都在仓库的 pods 目录下执行。先看 pod.yml：

apiVersion: v1
kind: Pod
metadata:
  name: hello-pod
  labels:
    zone: prod
    version: v1
spec:
  containers:
  - name: hello-ctr
    image: nigelpoulton/k8sbook:1.0
    ports:
    - containerPort: 8080
    resources:
      limits:
        memory: 256Mi
        cpu: "0.5"

这个 Pod 叫 hello-pod，带有两个标签（以后用来和 Service 连接）。它只有一个容器 hello-ctr， 使用 nigelpoulton/k8sbook:1.0 镜像，监听 8080 端口，最多使用 256Mi 内存和半个 CPU。

💡 清单即文档：Empathy as Code

YAML 文件是绝佳的文档：新同事读它们就能快速了解应用的基本功能和需求；运维团队能从中看到端口、CPU、内存等要求； 放进 Git 还能做版本管理和 diff。Nirmal Mehta 在 2017 年 DockerCon 上把这称为「代码化的同理心」。

部署并观察

$ kubectl apply -f pod.yml
pod/hello-pod created

$ kubectl get pods
NAME        READY   STATUS              RESTARTS   AGE
hello-pod   0/1     ContainerCreating   0          7s

输出说 created，但它可能还在拉镜像。等 READY 变成 1/1、STATUS 变成 Running，Pod 就在一个健康节点上跑起来了，并受该节点 kubelet 的监控。 Kubernetes 默认从 Docker Hub 拉镜像；要用别的镜像仓库，在镜像名前加上仓库地址即可。

观察 Pod 的五件利器

kubectl get

-o wide 多显示几列（IP、节点）；-o yaml 显示 Kubernetes 知道的关于这个对象的一切：

$ kubectl get pods hello-pod -o yaml
apiVersion: v1
kind: Pod
metadata:
  name: hello-pod
  namespace: default
spec:                        # ← 期望状态
  containers:
  - image: nigelpoulton/k8sbook:1.0
    imagePullPolicy: IfNotPresent
    name: hello-ctr
status:                      # ← 观测状态
  conditions:
  - lastTransitionTime: "2026-02-18T10:06:02Z"
    status: "True"
    type: Initialized
★ 输出为什么比我写的 17 行 YAML 多那么多？

两个来源：① 你没写的字段都被填上了默认值；② status 段是 Pod 的当前状态，本来就不在你的文件里。 spec 对 status，正是第 2 章「期望状态 vs 观测状态」的具体体现。

kubectl logs

kubectl logs <pod> 获取容器日志。对多容器 Pod，默认取第一个容器的日志， 要看别的容器就加 --container： 

$ kubectl logs logtest --container syncer

kubectl exec

在运行中的容器里执行命令，有两种用法：

远程执行一条命令
$ kubectl exec hello-pod -- ps
PID   USER     TIME  COMMAND
    1 root      0:00 node ./app.js
   18 root      0:00 ps
交互式会话（-it），像 SSH 登录
$ kubectl exec -it hello-pod -- sh
/src # apk add curl
/src # curl localhost:8080
<html><head><title>K8s rocks!</title>...
/src # env | grep HOSTNAME
HOSTNAME=hello-pod
/src # exit

格式是 kubectl exec <pod> -- <命令>，只能执行容器里装了的命令（所以一开始 curl 会报 executable file not found）。 -it 把你终端的标准输入输出接到容器上。

⚠ 在线改 Pod 是反模式

在运行的容器里装软件只是为了演示。真实环境中 Pod 应该是不可变的，要改就改镜像或 YAML，然后换新 Pod。

Pod 的主机名

Pod 的 metadata.name 会成为 Pod 内每个容器的主机名（上面 HOSTNAME=hello-pod 就是证明）。 所以 Pod 名应该是合法的 DNS 名：只用 a-z、0-9、连字符和点。

kubectl edit：验证不可变性

不可变性分两层：对象不可变（Pod 本身，Kubernetes 会阻止修改）和应用不可变（容器内部，Kubernetes 管不了，要靠你保证容器无状态）。试试： 

$ kubectl edit pod hello-pod

它会用默认编辑器（Mac/Linux 通常是 vi，Windows 是记事本）打开 Pod 的实时配置。试着改容器名、端口或资源值，保存退出， 你会收到 forbidden 的提示——这些字段不可变。（卡在 vi 里出不来？输入 :q! 回车。）

资源 requests 与 limits

resources:
  requests:        # 最小值：调度时使用
    cpu: 0.5
    memory: 256Mi
  limits:          # 最大值：kubelet 让运行时强制封顶
    cpu: 1.0
    memory: 512Mi
  • 调度器读取 requests，把 Pod 分配到资源足够的节点；找不到就 Pending，集群自动扩缩器（Cluster Autoscaler）会尝试加节点。
  • kubelet 预留 requests 的资源，并让运行时按 limits 设置上限。
  • 多容器 Pod：调度器把所有容器的 requests 加起来找节点。

动手：init 容器

apiVersion: v1
kind: Pod
metadata:
  name: initpod
  labels:
    app: initializer
spec:
  initContainers:               # ← init 容器
  - name: init-ctr
    image: busybox:1.28.4
    command: ['sh', '-c', 'until nslookup k8sbook; do echo waiting for k8sbook service; sleep 1; done; echo Service found!']
  containers:                   # ← 主应用容器
    - name: web-ctr
      image: nigelpoulton/web-app:1.0
      ports:
        - containerPort: 8080

init 容器不停地查一个叫 k8sbook 的 Service，找到才退出。部署并观察：

$ kubectl apply -f initpod.yml
pod/initpod created

$ kubectl get pods --watch
NAME      READY   STATUS     RESTARTS   AGE
initpod   0/1     Init:0/1   0          23s

Init:0/1 表示 init 容器还在跑，主容器没启动，kubectl describe 会显示整个 Pod 是 Pending。现在创建它要找的 Service：

apiVersion: v1
kind: Service
metadata:
  name: k8sbook
spec:
  selector:
    app: initializer
  ports:
    - port: 80
      targetPort: 8080
  type: ClusterIP

$ kubectl apply -f initsvc.yml
service/k8sbook created

$ kubectl get pods --watch
NAME      READY   STATUS            RESTARTS   AGE
initpod   0/1     Init:0/1          0          47s
initpod   0/1     PodInitializing   0          2m23s
initpod   1/1     Running           0          2m48s

init 容器看到 Service 后成功退出（exit code 0，状态 terminated），主容器随即启动。

动手：sidecar 容器

apiVersion: v1
kind: Pod
metadata:
  name: git-sync
  labels:
    app: sidecar
spec:
  initContainers:
  - name: ctr-sync
    restartPolicy: Always          # ← 就是这一行让它成为 sidecar
    image: k8s.gcr.io/git-sync:v3.1.6
    volumeMounts:
    - name: html
      mountPath: /tmp/git
    env:
    - name: GIT_SYNC_REPO
      value: https://github.com/nigelpoulton/ps-sidecar.git   # 改成你 fork 的地址
    - name: GIT_SYNC_BRANCH
      value: master
    - name: GIT_SYNC_DEPTH
      value: "1"
    - name: GIT_SYNC_DEST
      value: "html"
  containers:
  - name: ctr-web
    image: nginx
    volumeMounts:
    - name: html
      mountPath: /usr/share/nginx/
  volumes:
  - name: html
    emptyDir: {}
---
apiVersion: v1
kind: Service
metadata:
  name: svc-sidecar
spec:
  selector:
    app: sidecar
  ports:
  - port: 80
  type: LoadBalancer

需要 Kubernetes v1.33+ 和一个免费的 GitHub 账号。步骤：

  1. 打开 https://github.com/nigelpoulton/ps-sidecar，点 Fork 创建你自己的副本，复制它的 URL。
  2. 编辑 initsidecar.yml，把 URL 填进 GIT_SYNC_REPO。
  3. 部署：kubectl apply -f initsidecar.yml（会同时创建 Pod 和 Service）。
  4. 运行 kubectl get svc svc-sidecar，复制 EXTERNAL-IP 在浏览器打开（Docker Desktop 用 localhost），看到 This is version 1.0。
  5. 在你 fork 的仓库里修改 index.html 的 <h1> 并提交。
  6. 刷新网页，看到你的修改——证明 sidecar 一直在运行并同步内容。
$ kubectl get pods
NAME       READY   STATUS    RESTARTS   AGE
git-sync   2/2     Running   0          14s

$ kubectl describe pod git-sync
...

小结

  • Kubernetes 上一切应用都运行在 Pod 里；Pod 抽象了容器、Wasm、Serverless（Knative）、VM（KubeVirt）等工作负载。
  • Pod 是共享的执行环境（网络、卷、内存、进程树、主机名），并带来调度、探针、重启策略、安全策略等能力。
  • Pod 会死且不可变：Kubernetes 只会替换 Pod，而 kubelet 可以按 restartPolicy 重启容器。
  • 所有 Pod 接入一个由 CNI 插件实现的扁平 Pod 网络。
  • init 容器在主容器前跑完一次；sidecar 写在 initContainers 里并设 restartPolicy: Always，与主容器全程陪跑。
  • requests 用于调度和预留，limits 用于封顶；每个 Pod 都应该设置。
  • 实际工作中几乎总是通过 Deployment 等控制器来部署 Pod。

动手练习

  1. 部署 pod.yml，分别用 -o wide、-o yaml 查看，在 YAML 中找出 spec 和 status 的分界。
  2. 先部署 initpod.yml，观察 Init:0/1；等一分钟后再部署 initsvc.yml，用 --watch 看状态变化。
  3. 用 kubectl edit 尝试修改 hello-pod 的容器端口，记录报错信息。再试试修改它的标签（labels）——能改吗？想想为什么。
  4. 把 pod.yml 里的 memory 改成一个大得离谱的值（比如 500Gi）再部署，用 kubectl describe 看看 Events 里调度器说了什么。
