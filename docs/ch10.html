第 10 章

存储：PV、PVC 与 StorageClass

Pod 会死，容器里写的数据也会跟着消失。真实业务需要能长期保存的数据。 Kubernetes 的持久卷子系统能轻松对接各种外部存储系统，并借助它们提供备份恢复、复制、快照、加密等高级数据服务。

本章目标

  • 看懂存储的三层架构：存储提供方 → CSI 插件 → 持久卷子系统
  • 理解 PV、PVC、SC 各自的角色，以及动态供应的完整流程
  • 掌握访问模式（RWO / RWX / ROX）和回收策略（Delete / Retain）
  • 理解卷绑定模式 Immediate 与 WaitForFirstConsumer
  • 动手：用现成的 StorageClass 申请卷；创建自己的 StorageClass 并挂载到 Pod
⚠ 本章动手部分需要云集群

示例基于 Akamai 的 LKE，在其他云上不能直接运行，因为每个云都有自己的存储插件和配置项。 仓库的 storage/ 目录同时提供了 GKE 版本（gke-*.yml），用 GKE 的话换成对应文件即可。原理在各个云上都是相通的。

全局视图

Kubernetes 支持来自各种外部系统的块存储、文件存储和对象存储，它们可以在云上，也可以在你自己的机房里。

💾

PV：PersistentVolume

把一个外部卷「映射」进 Kubernetes。

🎫

PVC：PersistentVolumeClaim

一张「领用单」，授予 Pod 访问某个 PV 的权利。

🏭

SC：StorageClass

存储的「档位」，按需动态创建外部卷和 PV。

ⓘ 两条规则
  • Kubernetes 有机制防止多个 Pod 同时写同一个 PV；
  • 外部卷和 PV 是 1:1 的：不能把一个 50GB 外部卷切成两个 25GB 的 PV。

存储提供方与 CSI

外部存储系统通常称为提供方（provider）或供应器（provisioner）。每个提供方都提供自己的 CSI 插件（也叫驱动 driver）， 暴露后端的功能和配置项，一般以 Helm chart 或 YAML 安装器分发，装好后以 Pod 形式运行在 kube-system 里。 大多数云平台会预装自家存储服务的 CSI 插件；第三方存储需要手动安装。插件列表见 kubernetes-csi.github.io/docs/drivers.html。

  • 有些限制显而易见：集群在 Azure 上就没法挂 AWS EBS 卷；Pod 可能必须和存储在同一个地域或可用区。
  • 卷大小、保护级别、快照计划、复制、加密等，全都通过后端的 CSI 插件配置。各后端支持的功能不同，读插件文档是你的责任。
CSI 之前：in-tree（树内）
所有存储插件都写在 Kubernetes 主代码树里：被迫开源，更新和修复要跟着 Kubernetes 的发布节奏走，插件开发者和 Kubernetes 维护者都很痛苦。
CSI 之后：out-of-tree（树外）
CSI 是开源的业界标准接口。插件独立开发，不必开源，随时可以发布；理论上能在任何支持 CSI 的编排平台上运行。

现在要部署一个需要 100GB 加密闪存的应用：写一个 Pod，引用一个 PVC，PVC 从 sc-fast-encrypted 申请 100GB。 SC 控制器看到新 PVC，指示 CSI 插件在外部系统上创建 100GB 加密闪存卷；外部系统创建完成后通知插件，插件告知 SC 控制器，SC 控制器把它映射成新的 PV；Pod 通过 PVC 挂载使用这个 PV。

用 StorageClass 动态供应

StorageClass 属于 storage.k8s.io/v1 API 组，简写 sc。下面这个 SC 叫 fast-local，在 AWS 爱尔兰区域创建每 GB 10 IOPS 的加密 SSD 卷：

kind: StorageClass
apiVersion: storage.k8s.io/v1
metadata:
  name: fast-local
provisioner: ebs.csi.aws.com      # AWS EBS 的 CSI 插件
parameters:
  encrypted: true                 # 创建加密卷
  type: io1                       # AWS SSD 盘
  iopsPerGB: "10"                 # 性能要求
allowedTopologies:                # 卷和副本创建在哪里
- matchLabelExpressions:
  - key: topology.ebs.csi.aws.com/zone
    values:
    - eu-west-1a                  # AWS 爱尔兰区域
★ 关于 StorageClass 的四点
  1. StorageClass 不可变：部署后不能修改；
  2. metadata.name 要有意义，别人和其他对象都靠它引用这个档位；
  3. provisioner、plugin、driver 这几个词经常混用；
  4. parameters 块里是插件专属的配置，每个插件都不一样。

Pod → PVC → SC 的引用链

基本工作流：① 安装配置 CSI 插件 → ② 创建一个或多个 StorageClass → ③ 部署带 PVC 的 Pod，通过 SC 申请卷。三个对象可以写在同一个文件里，用 --- 分隔：

apiVersion: v1
kind: Pod                         # 1. Pod
metadata:
  name: mypod
spec:
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: mypvc            # 2. 通过名为 mypvc 的 PVC 申请卷
  containers: ...
---
apiVersion: v1
kind: PersistentVolumeClaim       # 3. 这就是 mypvc
metadata:
  name: mypvc
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 50Gi               # 4. 申请一个 50Gi 的卷……
  storageClassName: fast          # 5. ……基于 fast 这个 StorageClass
---
kind: StorageClass                # 6. 这就是 fast
apiVersion: storage.k8s.io/v1
metadata:
  name: fast
provisioner: pd.csi.storage.gke.io  # 7. 使用这个 CSI 插件
parameters:
  type: pd-ssd                    # 8. 创建这种类型的存储（GCP SSD）

💡 StorageClass 小结

StorageClass 代表存储档位，应用调用它来动态创建卷。它引用一个插件，并绑定到某个外部存储系统上的某类存储。 部署后，SC 控制器监视 API 服务器上引用它的新 PVC；每出现一个，就在外部系统上创建所需的卷，并映射成应用可以挂载的 PV。

动手：使用现有的 StorageClass

$ cd storage
$ kubectl get sc
NAME                           PROVISIONER               RECLAIMPOLICY   VOLUMEBINDINGMODE   ALLOWVOLUMEEXPANSION
linode-block-storage           linodebs.csi.linode.com   Delete          Immediate           true
linode-block-storage-retain (default)  linodebs.csi.linode.com   Retain    Immediate           true

LKE 预建了两个 SC，都通过 linodebs.csi.linode.com 插件供应，一个回收策略是 Delete，一个是 Retain。 标着 (default) 的是默认 SC：PVC 不指定 SC 时就用它。不同集群的默认 SC 可能不一样，所以重要的生产应用最好显式指定。 有的集群会预建很多 SC，比如 GKE Autopilot 区域集群就有 8 个，分别使用 Filestore（NFS）、Persistent Disk（块存储）和旧的树内插件。 

$ kubectl describe sc linode-block-storage
Name:                  linode-block-storage
IsDefaultClass:        No
Provisioner:           linodebs.csi.linode.com
Parameters:            <none>
AllowVolumeExpansion:  True
ReclaimPolicy:         Delete
VolumeBindingMode:     Immediate

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-test
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: linode-block-storage
  resources:
    requests:
      storage: 10Gi

$ kubectl get pv
No resources found

$ kubectl apply -f lke-pvc-test.yml
persistentvolumeclaim/pvc-test created

$ kubectl get pvc
NAME       STATUS   VOLUME                 CAPACITY   ACCESS MODES   STORAGECLASS
pvc-test   Bound    pvc-cc3dd8716c7d46c9   10Gi       RWO            linode-block-storage

$ kubectl get pv
NAME                   CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM      STORAGECLASS
pvc-cc3dd8716c7d46c9   10Gi       RWO            Delete           Bound    pvc-test   linode-block-storage

PVC 立刻就 Bound 了，因为这个 SC 的绑定模式是 Immediate：不等 Pod 来用，马上创建 PV 和后端卷。 打开 LKE 控制台的 Volumes 页，能看到一个同名的 10GB 卷。 

$ kubectl delete pvc pvc-test
persistentvolumeclaim "pvc-test" deleted

$ kubectl get pv            # 回收策略是 Delete，所以 PV 和 Linode 卷都被删了
No resources found

动手：创建并使用自己的 StorageClass

这次创建一个实现拓扑感知供应（topology-aware provisioning）的 SC，也叫按需供应：等到有 Pod 要用时才创建卷， 确保卷和 Pod 在同一个地域和可用区。 

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: block-wait-keep
provisioner: linodebs.csi.linode.com       # CSI 插件
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer    # 按需供应
reclaimPolicy: Retain                      # PVC 释放后保留卷

$ kubectl apply -f lke-sc-wait-keep.yml
storageclass.storage.k8s.io/block-wait-keep created

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: pvc-wait-keep
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  storageClassName: block-wait-keep

$ kubectl apply -f lke-pvc-wait-keep.yml
persistentvolumeclaim/pvc-wait-keep created

$ kubectl get pvc
NAME            STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
pvc-wait-keep   Pending                                      block-wait-keep

$ kubectl get pv
No resources found

PVC 处于 Pending，还没有 PV——它在等第一个使用者。现在部署使用它的 Pod：

apiVersion: v1
kind: Pod
metadata:
  name: volpod
spec:
  volumes:                         # ┐ 从名为 pvc-wait-keep 的 PVC
  - name: data                     # │ 创建一个叫 data 的卷
    persistentVolumeClaim:         # │
      claimName: pvc-wait-keep     # ┘
  containers:
  - name: ubuntu-ctr
    image: ubuntu:latest
    command:
    - /bin/bash
    - "-c"
    - "sleep 60m"
    volumeMounts:                  # ┐ 把 data 卷
    - mountPath: /data             # │ 挂载到 /data
      name: data                   # ┘

$ kubectl apply -f lke-app.yml
pod/volpod created

$ kubectl get pvc
NAME            STATUS   VOLUME                 CAPACITY   ACCESS MODES   STORAGECLASS
pvc-wait-keep   Bound    pvc-279f09e083254fa9   20Gi       RWO            block-wait-keep

$ kubectl get pv
NAME                   CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM           STORAGECLASS
pvc-279f09e083254fa9   20Gi       RWO            Retain           Bound    pvc-wait-keep   block-wait-keep

$ kubectl describe pod volpod
...
    Mounts:
      /data from data (rw)
Volumes:
  data:
    Type:       PersistentVolumeClaim (a reference to a PVC in the same namespace)
    ClaimName:  pvc-wait-keep
    ReadOnly:   false

回顾一下刚才发生了什么：

  1. 你创建了 StorageClass block-wait-keep，从 Linode 云供应块存储；
  2. SC 控制器开始监视引用这个 SC 的新 PVC；
  3. 你创建了 PVC，但因为是 WaitForFirstConsumer，没有立刻建卷；
  4. 你部署了一个使用该 PVC 申请 20GB 卷的 Pod；
  5. SC 控制器看到后，动态创建了 PV 和 Linode 云上的外部卷。

清理（五步，别漏）

$ kubectl delete pod volpod                       # 1. 删除使用 PVC 的 Pod
$ kubectl delete pvc pvc-wait-keep                # 2. 删除 PVC
$ kubectl delete pv pvc-279f09e083254fa9          # 3. 删除 PV（Retain 策略不会自动删）
#                                                   4. 到 Linode 控制台 Volumes 页手动删除同名卷
$ kubectl delete sc block-wait-keep               # 5. 删除 StorageClass
⚠ Retain 意味着「你来收拾」

删掉 Pod 和 PVC 后，PV 和外部卷仍然存在。第 4 步一定要在云控制台删除那个显示为未挂载（unattached）的卷，并确认名字和刚删的 PV 一致，否则会继续产生费用。

小结

  • Kubernetes 有强大的存储子系统，让应用能从各种外部提供方动态申请和使用存储。
  • 每个外部提供方都有自己的 CSI 插件，负责创建卷并呈现给 Kubernetes；托管集群通常预装了插件，以 Pod 形式运行在 kube-system。
  • StorageClass 映射到外部系统上的某类存储；SC 控制器以后台调和循环监视新 PVC，创建外部卷并映射成新 PV，Pod 再通过 PVC 挂载。
  • 访问模式：RWO / RWM / ROM；回收策略：Delete（默认，危险）/ Retain（安全，需手动回收）。
  • WaitForFirstConsumer 实现拓扑感知供应，保证卷和 Pod 在同一可用区。

动手练习

  1. 运行 kubectl get sc，找出你集群的默认 StorageClass，并用 kubectl describe sc 查看它的回收策略和绑定模式。
  2. 在 volpod 里执行 kubectl exec -it volpod -- bash -c "echo hello > /data/a.txt"，删掉 Pod 后用同一个 PVC 重新部署，看看文件还在不在。
  3. 思考：为什么块存储通常不支持 ReadWriteMany？如果多个 Pod 需要共享写同一份数据，你会选哪种存储？
