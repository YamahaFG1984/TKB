第 16 章

真实世界的 Kubernetes 安全

上一章用 STRIDE 做了威胁建模。这一章站在安全架构师的高度，看看在真实环境中落地 Kubernetes 时会遇到哪些安全挑战。 它不是照着做的菜谱，而是一张帮你思考的地图：软件交付流水线、工作负载隔离、身份与访问管理、安全监控与审计。

本章目标

  • 保护从开发者笔记本到生产服务器的软件供应链：镜像仓库、基础镜像、漏洞扫描、镜像签名
  • 理解集群级、节点级、运行时级和网络级的工作负载隔离选项
  • 把 Kubernetes 接入企业 IAM，管好 SSH 和高权限账号
  • 建立审计、监控和告警，知道迁移现有应用时的安全策略

软件交付流水线的安全

容器革新了构建、分发和运行应用的方式，但也让运行危险代码变得前所未有地容易。我们来看看如何保护把代码从开发者笔记本送到生产服务器的这条供应链。

镜像仓库

镜像存放在公共或私有的镜像仓库（registry）中，仓库又分成多个存储库（repository）。公共仓库在互联网上，推拉镜像最方便，但要格外小心：

  1. 你需要妥善保护存放在公共仓库上的镜像；
  2. 你不应该信任从公共仓库拉下来的镜像。
官方镜像（official）
通常由产品厂商提供，经过严格审核，应当遵循良好实践、定期扫描漏洞、包含最新补丁，有的甚至有厂商或仓库方支持。一般更安全，但仍要做尽职调查。
社区镜像（community）
没有经过严格审核，使用时要极其谨慎。

所以应该为开发者提供一套标准化的获取和使用镜像的方式，并让流程尽可能顺畅，免得开发者想绕过它。

使用经过批准的基础镜像

前期需要投入精力，但回报很多：

标准化

一套标准的驱动、已知的补丁、统一的审计设置。

减少蔓延

非官方的基础镜像更少，支持合同和供应商也可能更少。

简化测试和更新

只需针对少量已知基础镜像测试和打补丁。

简化排错

基础镜像数量有限且众所周知；开发者可以专注应用，不用操心 OS。

确实有特殊需求时，需要有良好的流程：弄清为什么现有批准镜像不能用；评估能否（以及是否值得）更新现有镜像来满足需求；评估引入全新镜像对支持的影响。 大多数情况下，应该更新现有基础镜像（比如加一个 GPU 驱动），而不是引入全新的镜像。

控制对镜像的访问

  • 安全又实用的做法：在自己的防火墙内托管私有镜像仓库，自己控制部署、复制和打补丁方式，按组织需要设计存储库和策略，并对接 Active Directory 等现有身份系统；
  • 做不到的话，可以把镜像放在公共仓库的私有存储库里，但要认真挑选服务商并正确配置；
  • 只托管经过信息安全团队审核、来源可信的批准镜像，并给存储库加访问控制；
  • 限制哪些集群节点能上互联网（镜像仓库可能就在互联网上）；如果要用公共仓库，把节点的互联网访问限制在仓库使用的地址和端口；
  • 在仓库上实施严格的 RBAC：例如开发者只能推拉 dev 和 test 存储库，运维团队才能推拉 production 存储库；甚至只允许构建节点或自动化构建系统推送到特定存储库。

把镜像从非生产推广到生产

开发环境规则少，开发者可以在里面实验，可能会用到最终想带进生产的非标准镜像。以下措施确保只有安全的镜像被批准进入生产：

漏洞扫描

排在首位的是漏洞扫描：在二进制层面扫描镜像，与已知漏洞（CVE）数据库比对。应该把它集成进 CI/CD 流水线， 并设定策略：包含某类漏洞（比如严重级别）的镜像自动构建失败并被隔离。好的扫描工具还允许高度定制策略—— 比如某个 Python 方法在 Common Name 含大量通配符时有 DoS 风险，但如果你根本不这么用，就希望把它标记为误报，而不是所有工具都支持这样做。

配置即代码也要审查

扫描应用代码已被广泛接受，但扫描 Dockerfile、Kubernetes YAML、Helm chart 等配置文件的做法还不够普及。 一个广为人知的教训：IBM 的一个数据科学实验把TLS 私钥嵌进了容器镜像，攻击者拉取镜像后就能获得托管容器节点的 root 权限。 如果当初对 Dockerfile 做一次安全审查，这完全可以避免。如今已有越来越多实现「策略即代码」的工具能自动化这类检查。

工作负载隔离

从集群级开始，到运行时级，再到集群外的网络防火墙，逐层来看。

集群级隔离

⚠ 开门见山

Kubernetes 不支持安全的多租户集群。隔离两个工作负载的唯一方法，是让它们运行在各自的集群、各自的硬件上。

划分集群的唯一手段是 Namespace，但它只是一种对资源分组、施加限制（limits）、配额（quotas）和 RBAC 规则的方式， 并不能阻止一个 Namespace 里被攻破的工作负载影响其他 Namespace。所以永远不要在同一个集群上运行敌对的工作负载。 Namespace 很有用，应该用——只是别把它当作安全边界。

节点隔离

有些应用需要非标准的权限，比如以 root 运行或执行非标准的系统调用。为它们单独建集群可能小题大做，但可以把它们圈在一小部分专用工作节点上， 让被攻破的工作负载只能影响同一节点上的其他工作负载。同时贯彻纵深防御：在这些节点上开启更严格的审计日志和运行时防护。 可以用标签、亲和性/反亲和性规则和污点（taint）把工作负载定向到特定节点。

运行时隔离

谈到工作负载隔离，赢家永远是虚拟机。但如今给容器加上 AppArmor、SELinux、seccomp、capabilities、用户命名空间等安全技术比以往容易得多， 大多数运行时和托管服务都提供了合理的默认配置（不过排错时仍可能很复杂）。可选的隔离方案汇总如下：

方案特点
虚拟机每个工作负载有专属内核，隔离极好，但相对慢、耗资源
命名空间容器共享宿主机内核，快而轻，但需要额外工作来增强隔离
每个容器跑在自己的虚拟机里试图兼得容器的灵活和 VM 的安全，但即使用轻量 VM 也失去了容器的大部分吸引力，不太流行
不同的 RuntimeClass全部以容器运行，把需要强隔离的工作负载调度到合适的运行时
Wasm 容器把 Wasm 应用打包进 OCI 容器，容器只用于打包和调度，运行时在默认拒绝的安全 Wasm 宿主中执行

网络隔离

防火墙是分层安全体系不可或缺的一环，目标是只放行经过授权的通信。Pod 网络由 CNI 插件实现，大体分两类：覆盖网络（overlay）和 BGP，它们对防火墙的影响很不一样。

✉ BGP 的比喻

你想给失联的老朋友寄生日贺卡，但不知道地址。你孩子的同学的父母还和这位朋友有联系。于是你把卡片交给孩子，孩子交给同学，同学交给父母，父母再转交给你的朋友。 BGP 路由就是这样通过一个互相帮忙找路的对等网络完成的。

  • 物理防火墙是专用网络硬件，通常由中心团队管理；主机防火墙是操作系统功能，通常由管理 OS 的团队负责。两者结合往往最安全，但如果物理防火墙的变更流程漫长复杂，可能跟不上 Kubernetes 的节奏。
  • 抓包：Pod IP 不仅可能被封装隐藏，还是动态的、会被回收复用（IP churn），单凭 IP 很难识别工作负载。抓包时能把 IP 关联到 Pod ID、Service 别名、容器 ID 等 Kubernetes 标识会非常有用。

身份与访问管理（IAM）

管理对集群节点的 SSH 访问

几乎所有 Kubernetes 管理都通过对 API 服务器的 REST 调用完成，用户很少需要 SSH 到节点。SSH 只应用于：

  • 无法通过 Kubernetes API 完成的节点管理工作；
  • 「打碎玻璃」式的紧急操作，比如 API 服务器宕机；
  • 深度排错。

多因素认证（MFA）

能力越大，责任越大。拥有 API 服务器 root 权限和集群节点 root 权限的账号极其强大，是攻击者和心怀不满的员工的首要目标，应该用 MFA 保护： 第一步验证你知道的（用户名和密码），第二步验证你拥有的（比如一次性密码）。装了 kubectl 的工作站和用户配置文件也要保护好。

安全监控与审计

没有系统是 100% 安全的，你应该始终为被入侵做好准备。入侵发生时，至少要能做到两件事：

  1. 发现入侵已经发生；
  2. 构建一条详细的、不可抵赖的事件时间线，回答发生了什么、如何发生、何时发生、是谁干的——极端情况下这些信息会被呈上法庭。

好的审计和监控还能帮你发现安全体系的薄弱点。没有健全的审计和监控，不要上线生产。

基线最佳实践

CIS 发布了 Kubernetes 安全基准，Aqua Security 的 kube-bench 可以对集群运行 CIS 检查并生成报告（无法检查托管服务的控制平面）。可在节点供应流程中运行，不合格就失败；也可作为事后对比的基线。

容器与 Pod 生命周期事件

Pod 来来去去，要配置日志保留，让已终止 Pod 的日志事后仍可查看。运行时也可能保留容器生命周期日志。

📸

取证检查点

CRIU（用户空间检查点/恢复）能悄悄捕获运行中容器的状态，在沙箱中恢复深入分析。撰写时在 Kubernetes 中是 alpha，只有 CRI-O 支持。

📝

应用日志

有的应用写到 stdout/stderr，日志工具能和容器日志一起采集；有的写到自定义位置的专有日志文件里。逐个应用调查清楚，别漏掉。

👤

用户操作

API 服务器请求都应记录。攻击者也可能 SSH 到控制平面直接操作对象甚至 etcd：限制 SSH、加 MFA、记录所有 SSH 活动并发送到安全的日志聚合器，甚至要求两名合格人员同时在场。

📊

管理日志数据

容器带来高应用密度，也带来海量日志和审计数据。需要专门的工具来存储、做主动分析和事后分析。

值得立即告警的安全事件

事件为什么要警惕
人类用户创建特权 Pod特权 Pod 往往能获得节点 root 权限，通常有策略禁止。极少数确实需要时，一般由使用 ServiceAccount 的自动化流程创建。
人类用户发起 exec 会话exec 提供类似 shell 的容器访问，通常只用于排错。非排错目的的 exec 要调查，并考虑删除相关容器以防篡改。

把现有应用迁移到 Kubernetes

真实案例：CVE-2019-5736

2019 年 2 月披露的 CVE-2019-5736 允许以 root 运行的容器进程获得工作节点及其上所有容器的 root 权限。 这个漏洞很危险，但本章（和上一章）讲过的这些做法，任何一项都足以阻止它：

小结

  • 交付流水线：保护镜像仓库、使用批准的基础镜像、扫描漏洞、审查配置文件、对镜像签名和验证。
  • 工作负载隔离：Namespace 不是安全边界；强隔离要独立集群；还可以用节点隔离、沙箱运行时、虚拟机；注意覆盖网络对防火墙的影响。
  • IAM：接入企业身份系统，限制 SSH，为高权限账号启用 MFA。
  • 监控与审计：没有它们不要上线；对特权 Pod、人工 exec、来自互联网的访问等事件立即告警。
  • 迁移现有应用时遵循「爬、走、跑」：先迁移，再加固。

动手练习

  1. 挑一个你常用的公共镜像，用 Trivy 或 Docker Scout 之类的工具扫描它，看看有多少已知漏洞、其中几个是严重级别。
  2. 在测试集群上运行 kube-bench（github.com/aquasecurity/kube-bench），挑三条失败项研究原因和修复方法。
  3. 回顾第 5 章的 shield 和 hydra：如果它们属于两个互不信任的客户，你会如何重新设计部署架构？
