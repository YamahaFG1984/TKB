第 1 章

Kubernetes 入门

「Kubernetes 是一个编排容器化云原生微服务应用的编排器。」——这句话里几乎每个词都是术语。 这一章就把它们一个个拆开，再讲讲 Kubernetes 从哪里来、为什么被称为「云的操作系统」。

本章目标

  • 用大白话解释编排、容器化、云原生、微服务四个词
  • 知道 Kubernetes 的来历，以及它和 Google、Docker、Borg 的关系
  • 理解 Kubernetes 为什么不再用 Docker 做运行时，而这又为什么不影响你用 Docker 打包应用
  • 理解「Kubernetes 是云的操作系统」这个比喻

把那句满是术语的话拆开

官方式的定义是：Kubernetes 是容器化云原生微服务应用的编排器。我们把它拆成四块来看：

编排（Orchestration）

编排器是一个负责部署应用并动态应对变化的系统。Kubernetes 能够：

  • 部署应用
  • 根据负载自动扩容、缩容
  • 东西坏了自动修复（自愈）
  • 执行滚动发布（rollout）和回滚（rollback）

最妙的是，这一切都不需要你插手。你只需要在开始时配置好，然后就可以坐下来，让 Kubernetes 施展魔法。 就像乐团的指挥：乐手（容器）各自演奏，指挥保证整体和谐。

容器化（Containerization）

容器化就是把应用和它的依赖打包成镜像（image），然后把镜像运行成容器（container）的过程。 你可以把容器看成「下一代虚拟机」：两者都是打包和运行应用的方式，但容器更小、更快、更容易搬家。

ⓘ 容器并没有完全取代虚拟机

在大多数环境里你会看到容器和虚拟机并肩运行——甚至 Kubernetes 的节点本身常常就是虚拟机。 但对新应用来说，容器已经是首选。

云原生（Cloud native）

云原生应用具备「云一样的特性」：自动扩缩、自愈、自动更新、可回滚等。 注意：把一个普通应用搬到公有云上跑，并不会让它变成云原生。云原生是应用的能力，不是它所在的地点。

微服务（Microservices）

微服务应用由许多小的、专门的、独立的部分组成，它们协同工作形成一个完整应用。 以一个电商应用为例，它有六个功能：网页前端、商品目录、购物车、身份认证、日志、商店。 把它做成微服务，就是把这六个功能各自当成一个小应用去设计、开发、部署和管理。

这样设计带来很大的灵活性：每个微服务可以有自己的开发小组和发布周期，还能独立扩缩容、独立更新。 最常见的做法是每个微服务部署成自己的容器，所以扩容某个部分就只是加减几个容器而已。

★ 现在，把那句话翻译成人话

「Kubernetes 是容器化云原生微服务应用的编排器」= Kubernetes 负责部署、扩缩、自愈、更新那些「把每个功能单独打包成容器」的应用。 如果还有点模糊，不用担心，后面每一章都会再详细讲一遍。

Kubernetes 从哪里来

Kubernetes 的诞生，部分是 Google 工程师对两件事的回应：AWS 和 Docker。

  • AWS 发明了现代云计算，整个行业都在追赶。Google 有自己的云，需要一种办法把 AWS 的价值「抽象掉」，让客户能轻松地从 AWS 搬到它的云上。
  • Docker 正在席卷世界，容器数量爆炸，用户急需一个管理它们的工具。
  • Google 自己的生产业务（搜索、Gmail）每周要跑数十亿个容器，积累了大量经验。

十多年后，Kubernetes 的核心价值仍然是 Google 和整个行业最需要的两件事：

  1. 抽象基础设施（比如 AWS 的各种细节）
  2. 让应用更容易迁移（今天在这朵云，明天换另一朵）

Kubernetes 和 Borg：「抵抗是徒劳的！」

Google 内部有两个工具 Borg 和 Omega，一直在编排它那数十亿个容器。 Kubernetes 不是 Borg 或 Omega 的开源版，更像是它们的「亲戚」——共享同样的 DNA 和家族史。

Kubernetes 和 Docker

早期所有版本的 Kubernetes 都用 Docker 作为容器运行时（runtime）——也就是负责创建、启动、停止容器的底层工具。后来发生了两件事：

  1. Docker 变得越来越臃肿，对 Kubernetes 来说功能过剩
  2. 大家造出了很多 Docker 的替代品

于是 Kubernetes 项目创建了 CRI（Container Runtime Interface，容器运行时接口），把运行时这一层做成可插拔的。 Kubernetes 1.24 正式移除了对 Docker 运行时的支持，从那以后大多数新集群默认使用 containerd（读作 “container-dee”）。

💡 那我还能用 Docker 吗？当然能

「Kubernetes 不再用 Docker 作运行时」不等于「Kubernetes 不能跑 Docker 打包的镜像」。 Docker、containerd 和 Kubernetes 都遵循 OCI（Open Container Initiative，开放容器倡议）标准， 所以你用 docker build 打出来的镜像，containerd 照样能跑。 你的开发流程完全不用变：用 Docker 构建，在 Kubernetes 上运行。

那 Docker Swarm 呢？

2016–2017 年，Docker Swarm、Mesosphere DCOS 和 Kubernetes 争夺容器编排的行业标准，最终 Kubernetes 胜出。 不过 Docker Swarm 仍在开发，在想要一个比 Kubernetes 简单的方案的小公司里依然受欢迎。

Kubernetes：云的操作系统

我们常把 Kubernetes 称为云的操作系统，因为它抽象掉不同云平台之间的差异，就像 Linux、Windows 抽象掉不同服务器之间的差异一样：

你在 Kubernetes 上调度应用时，不必关心它跑在 AWS、Azure、Civo、GCP 还是自家机房。这让 Kubernetes 成为以下场景的关键推手：

☁

混合云

一部分在公有云，一部分在自己机房，用同一套方式管理。

🌐

多云

同时用好几家云厂商，不被任何一家绑死。

🚚

云迁移

今天部署到一朵云，明天搬到另一朵云。

小结

  • Kubernetes 是由 Google 工程师基于多年超大规模运行容器的经验创建的，2014 年开源并捐给 CNCF，使用 Apache 2.0 许可证。
  • 它负责部署、扩缩、自愈、更新以容器形式打包的微服务应用。
  • 运行时通过 CRI 可插拔，主流是 containerd；Docker 构建的镜像遵循 OCI 标准，依然可以直接使用。
  • Kubernetes 抽象了底层基础设施，常被称为「云的操作系统」，是混合云、多云和云迁移的基础。

动手练习

  1. 挑一个你熟悉的应用（比如外卖 App），试着把它拆成 5～6 个微服务，并想一想：午高峰时哪几个服务最需要扩容？
  2. 用自己的话向一个不懂技术的朋友解释「声明一个目标，然后让系统自己维持它」和「一步一步下命令」有什么区别。（下一章会正式讲到这个概念。）
  3. 如果你装了 Docker，运行 docker run --rm hello-world，体会一下「镜像 → 容器」的过程。
