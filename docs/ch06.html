第 6 章

Deployment：扩缩、滚动更新与回滚

Deployment 是在 Kubernetes 上运行无状态应用最常用的方式。它给 Pod 加上了四种「超能力」： 自愈、扩缩、滚动更新、版本回滚。这一章先讲清背后的原理，再亲手做一次零停机升级和回滚。

本章目标

  • 理解 Deployment、ReplicaSet、Pod 三者的关系
  • 认识 HPA、VPA、Cluster Autoscaler 三种自动扩缩器
  • 彻底搞懂滚动更新的过程，以及 maxSurge、maxUnavailable、minReadySeconds
  • 理解标签选择器和 pod-template-hash 如何把对象串起来
  • 动手完成：创建 → 扩缩 → 滚动更新 → 暂停/恢复 → 回滚

Deployment 的原理

假设你要做一个 Web 应用，它需要高可用、能按需扩容、还要经常更新。你写好代码、打成容器、定义成 Pod， 但在交给 Kubernetes 之前，先把 Pod 包进一个 Deployment。 之后 Pod 挂了，Deployment 控制器替换它；流量涨了，部署更多相同的 Pod；要更新，就用新 Pod 替换旧 Pod。 再加一个购物车服务？同样再包一个 Deployment。每个微服务一个 Deployment。

和 Kubernetes 的其他功能一样，Deployment 由两部分组成：

  • 资源（resource）：定义在 apps/v1 API 里，描述对象支持哪些属性；
  • 控制器（controller）：运行在控制平面上的服务，监视 Deployment 并把观测状态调和成期望状态。

Deployment、ReplicaSet 与 Pod

其实自愈和扩缩是由幕后的另一种资源 ReplicaSet（简写 rs）提供的，Deployment 则在它之上增加滚动更新和回滚。 Pod 是在 Deployment YAML 里以 Pod 模板（Pod template）的形式内嵌定义的。

★ 只管 Deployment，别碰 ReplicaSet

提交这个 YAML 会创建一个 Deployment、一个 ReplicaSet 和两个 Pod。Pod 由 ReplicaSet 管理，ReplicaSet 又由 Deployment 管理。 但所有的管理操作都应该通过 Deployment 进行，永远不要直接修改 ReplicaSet 或 Pod。

关于扩缩：三种自动扩缩器

扩缩器做什么普及度
HPA 水平 Pod 自动扩缩按负载增减 Pod 数量大多数集群默认安装，广泛使用
CA 集群自动扩缩按需要增减节点，保证所有 Pod 都有地方跑默认安装，广泛使用
VPA 垂直 Pod 自动扩缩给运行中的 Pod 调整 CPU/内存默认不装；目前靠「删掉重建」实现，有干扰，用得较少

缩容同理：负载下降时 HPA 减少 Pod，可能触发 CA 移除节点；移除节点前，Kubernetes 会把上面的 Pod 驱逐，并在剩余节点上换成新 Pod。社区项目 karmada 甚至能跨多个集群扩缩应用。

一切围绕「状态」

再复习一次：期望状态是你想要的，观测状态是你实际有的，控制器负责调和二者。书中用了一个巧克力蛋糕的比喻：

声明式

「给我一个够十个人吃的巧克力蛋糕。」

只说目标，「怎么做」交给 Kubernetes。

命令式
开车去商店，买鸡蛋、牛奶、面粉、可可粉……开车回家，预热烤箱，混合原料，倒进模具。如果是热风烤箱烤 30 分钟，否则 40 分钟。定时，到点取出关烤箱，放凉，抹奶油……

命令式没有「期望状态」的概念，所以没有自愈；而且不同平台命令各异（containerd 和 CRI-O 的命令就不同），更容易出错。 在 Kubernetes 里，ReplicaSet 控制器作为后台调和循环运行：期望 10 个副本却只有 8 个——不管是因为故障还是因为扩容请求——它都会自动补上 2 个。 自愈、扩缩、发布、回滚，用的都是同一套调和机制。

滚动更新是怎么做到零停机的

零停机滚动更新（rollout）在应用满足两个条件时效果最好：

  1. 通过 API 松耦合：微服务之间只通过定义良好的 API 通信，更新一个不影响其他；
  2. 前后版本兼容：新旧版本可以同时为客户端提供服务。
🚗 汽车比喻

汽车对司机暴露的「API」是方向盘和踏板。只要这个 API 不变，你可以改发动机、换排气、装更大的刹车，司机都不用学新技能。

当你修改 Deployment 的 Pod 模板（比如换镜像版本）并重新提交时，Deployment 控制器会新建一个 ReplicaSet， 然后逐步增加新 ReplicaSet 的 Pod、减少旧 ReplicaSet 的 Pod，直到全部替换完成：

回滚

回滚就是反过来：把旧 ReplicaSet 调大，同时把当前的调小。因为旧 ReplicaSet 的配置一直保留着，所以回滚很容易。 你还可以精细控制发布节奏：插入延迟、控制速度、对新副本做健康探测。

动手：创建 Deployment

以下命令在仓库的 deployments 目录下执行。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-deploy             # Deployment 名字（必须是合法 DNS 名）
spec:
  replicas: 10                   # 要部署和管理的 Pod 副本数
  selector:
    matchLabels:
      app: hello-world           # 管理带这个标签的 Pod
  revisionHistoryLimit: 5        # 保留前 5 个版本的配置用于回滚
  progressDeadlineSeconds: 300   # 每个新副本有 5 分钟时间启动
  minReadySeconds: 10            # 一个副本就绪后等 10 秒再换下一个
  strategy:                      # 滚动更新的设置
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1          # 更新期间最多比期望少 1 个
      maxSurge: 1                # 更新期间最多比期望多 1 个
  template:                      # ↓ 以下是 Pod 模板
    metadata:
      labels:
        app: hello-world         # 必须和上面的 selector 匹配
    spec:
      containers:
      - name: hello-pod
        image: nigelpoulton/k8sbook:1.0
        ports:
        - containerPort: 8080
        resources:
          limits:
            memory: 128Mi
            cpu: 0.1
字段含义
apiVersion: apps/v1 + kind基于 apps/v1 API 中的 Deployment 资源创建对象
spec.replicasReplicaSet 控制器会创建 10 个 Pod 模板所描述的 Pod
spec.selectorDeployment 和 ReplicaSet 用这组标签判断「哪些 Pod 归我管」，必须和 spec.template.metadata.labels 匹配
revisionHistoryLimit保留的旧 ReplicaSet 数量。越多回滚选择越多，但太多会让对象膨胀
progressDeadlineSeconds每个新副本各自有 5 分钟窗口，超时则报告为停滞（stalled）
spec.templateDeployment 所管理的 Pod 的定义
$ kubectl apply -f deploy.yml
deployment.apps/hello-deploy created

$ kubectl get deploy hello-deploy
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
hello-deploy   10/10   10           10          20s

$ kubectl get rs
NAME                      DESIRED   CURRENT   READY   AGE
hello-deploy-6f4cfbc5b4   10        10        10      77s

注意 ReplicaSet 的名字 = Deployment 名 + 一串哈希。这个哈希是 Pod 模板（spec.template 以下所有内容）的加密哈希。 一旦你修改 Pod 模板，就会触发一次发布，并以新哈希创建一个新的 ReplicaSet。 

$ kubectl describe rs hello-deploy-6f4cfbc5b4
Name:           hello-deploy-6f4cfbc5b4
Selector:       app=hello-world,pod-template-hash=6f4cfbc5b4
Annotations:    deployment.kubernetes.io/desired-replicas: 10
                deployment.kubernetes.io/max-replicas: 11
                deployment.kubernetes.io/revision: 1
Controlled By:  Deployment/hello-deploy        # ← 它的「主人」
Replicas:       10 current / 10 desired
Pods Status:    10 Running / 0 Waiting / 0 Succeeded / 0 Failed

ReplicaSet 的观测状态也会汇总到 Deployment 的状态里，所以 describe deploy 和 describe rs 的输出很像。

访问应用

要从外面访问这些 Pod，需要一个 Service（下一章细讲）。lb.yml 定义了一个把流量发给 app=hello-world Pod 的 LoadBalancer Service：

apiVersion: v1
kind: Service
metadata:
  name: lb-svc
  labels:
    app: hello-world
spec:
  type: LoadBalancer
  ports:
  - port: 8080
    protocol: TCP
  selector:
    app: hello-world      # 把流量发给带这个标签的 Pod

$ kubectl apply -f lb.yml
service/lb-svc created

$ kubectl get svc lb-svc
NAME     TYPE           CLUSTER-IP       EXTERNAL-IP   PORT(S)
lb-svc   LoadBalancer   10.100.247.251   localhost     8080:31086/TCP

在浏览器打开 EXTERNAL-IP:8080（Docker Desktop 上是 localhost:8080）就能看到应用。

扩缩几乎是瞬间完成的；滚动更新则不是，下面就来看。

动手：滚动更新

rollout、release、零停机更新、滚动更新，说的都是一回事。再强调一遍：所有更新操作其实都是替换操作，因为 Pod 是不可变的。 作者已经把新版本推到了 Docker Hub：nigelpoulton/k8sbook:2.0。打开 deploy.yml，只改一行： 

      containers:
      - name: hello-pod
        image: nigelpoulton/k8sbook:2.0     # ← 1.0 改成 2.0

控制节奏的几个参数

设置含义
revisionHistoryLimit: 5保留前 5 次发布的配置，方便回滚
progressDeadlineSeconds: 300每个新副本 5 分钟内必须正常启动，否则视为失败（启动快一些当然没问题）
minReadySeconds: 10每个副本就绪后等 10 秒再继续，控制替换速度。等待越久越容易在全部替换成坏版本之前发现问题，真实环境要设得足够大
strategy.type: RollingUpdate逐步替换副本
maxUnavailable: 1任何时候最多比期望状态少 1 个 Pod
maxSurge: 1任何时候最多比期望状态多 1 个 Pod

Kubernetes 怎么知道要替换哪些 Pod？——标签！

Deployment 的 selector 和 Pod 模板的 labels 必须匹配，而且创建之后就不能再改。现在开始发布：

$ kubectl apply -f deploy.yml
deployment.apps/hello-deploy configured

$ kubectl rollout status deployment hello-deploy
Waiting for deployment "hello-deploy" rollout... 2 out of 10 new replicas...
Waiting for deployment "hello-deploy" rollout... 4 out of 10 new replicas...
^C

$ kubectl get deploy hello-deploy        # 11 = 10 + maxSurge
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
hello-deploy   11/10   4            11          7m58s

暂停与恢复

$ kubectl rollout pause deploy hello-deploy
deployment.apps/hello-deploy paused

$ kubectl describe deploy hello-deploy
Annotations:   deployment.kubernetes.io/revision: 2
Replicas:      10 desired | 4 updated | 11 total | 11 available | 0 unavailable
Conditions:
  Type           Status   Reason
  ----           ------   ------
  Available      True     MinimumReplicasAvailable
  Progressing    Unknown  DeploymentPaused
OldReplicaSets:  hello-deploy-6f4cfbc5b4 (7/7 replicas created)
NewReplicaSet:   hello-deploy-7564778d77 (4/4 replicas created)

$ kubectl rollout resume deploy hello-deploy
deployment.apps/hello-deploy resumed

暂停时能清楚看到：这是第 2 个版本（revision 2），旧 ReplicaSet 管着 7 个副本、新的管着 4 个。 如果发布过程中发生了扩容，Kubernetes 会把新增副本平衡分配到两个 ReplicaSet 上。 完成后刷新浏览器，会看到新版本的配色和文字。

动手：回滚

$ kubectl rollout history deployment hello-deploy
deployment.apps/hello-deploy
REVISION  CHANGE-CAUSE
1         <none>
2         <none>

$ kubectl get rs
NAME                      DESIRED   CURRENT   READY   AGE
hello-deploy-6f4cfbc5b4   0         0         0       10m
hello-deploy-7564778d77   10        10        10      9m34s

$ kubectl describe rs hello-deploy-6f4cfbc5b4
...
Replicas:       0 current / 0 desired
Pod Template:
  Containers:
   hello-pod:
    Image:      nigelpoulton/k8sbook:1.0     # ← 仍然记着旧版本

$ kubectl rollout undo deployment hello-deploy --to-revision=1
deployment.apps "hello-deploy" rolled back

$ kubectl rollout status deployment hello-deploy
Waiting for deployment "hello-deploy"... 6 out of 10 new replicas have been updated...
Waiting for deployment "hello-deploy"... 8 out of 10 new replicas have been updated...
Waiting for deployment "hello-deploy"... 9 of 10 updated replicas are available...
⚠ 回滚之后记得改 YAML

kubectl rollout undo 是命令式操作，方便应急，但事后一定要把源 YAML 也改回去，否则又会出现配置漂移。 另外回滚并不是瞬间完成的：它遵循和发布完全相同的规则，同样每次替换 2 个、每轮等 10 秒。

清理

$ kubectl delete -f deploy.yml
$ kubectl delete -f lb.yml

小结

  • Deployment 是管理无状态应用的首选，提供自愈、扩缩、滚动更新和回滚；它定义在 apps/v1 API 中，由控制平面上的控制器以调和循环实现。
  • 幕后由 ReplicaSet 负责维持 Pod 数量；但永远通过 Deployment 来管理，不要直接动 ReplicaSet。
  • 修改 Pod 模板会创建新的 ReplicaSet，新旧此消彼长完成滚动更新；旧 ReplicaSet 保留配置，用于回滚。
  • maxSurge / maxUnavailable 决定更新时的副本数范围，minReadySeconds 控制节奏。
  • 标签选择器 + pod-template-hash 决定对象之间的归属关系。
  • 坚持声明式：所有变更都改 YAML 再 kubectl apply。

动手练习

  1. 部署 deploy.yml 后，用 kubectl delete pod 随手删掉一个 Pod，立刻 kubectl get pods，观察 ReplicaSet 如何自愈。
  2. 把 maxSurge 改成 3、maxUnavailable 改成 0，再做一次从 1.0 到 2.0 的更新，观察 READY 列的最大值变化。
  3. 故意把镜像改成一个不存在的标签（如 k8sbook:9.9）再发布，观察 rollout status 卡在哪里，然后用 rollout undo 救回来。
  4. 运行 kubectl get pods --show-labels，找到每个 Pod 的 pod-template-hash，和 kubectl get rs 的名字对照。
