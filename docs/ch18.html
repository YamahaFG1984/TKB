探针、资源与自动扩缩

进程在跑，不等于应用健康；Pod 能调度上去，不等于资源够用。这一章补齐上生产前必须掌握的三件事： 用健康探针告诉 Kubernetes 应用的真实状态，用资源配置让调度和隔离可靠，用 HPA 让副本数跟着负载自动伸缩。

ⓘ 关于补充篇

本章不是原书内容。原书在第 4 章提到 Pod 支持「健康探针」，第 6 章讲了 HPA 的原理，这里把它们展开成可以动手的完整章节。 配套文件在仓库的 extras/probes/ 目录。下文的命令输出按 Kubernetes 标准格式整理，你的集群中名字、数值、时间会不同。

本章目标

  • 分清 startup、liveness、readiness 三种探针：各回答什么问题、失败后会发生什么
  • 会配置 httpGet / tcpSocket / exec 探针和它们的时间参数
  • 避开探针最常见的坑：存活探针检查依赖导致的连锁重启
  • 理解 CPU 与内存单位、限流与 OOM，以及 QoS 等级如何决定驱逐顺序
  • 用 LimitRange 和 ResourceQuota 给 Namespace 设默认值和总预算
  • 部署 metrics-server，用 HPA 让应用随 CPU 负载自动扩缩

为什么需要探针

没有探针时，Kubernetes 只知道一件事：容器的主进程还在不在。可是现实中有很多「进程活着，但应用不能用」的情况：

三种探针

探针回答的问题失败后什么时候运行
startupProbe 启动探针启动完成了吗？超过阈值仍未成功 → 重启容器只在启动阶段；成功一次后就不再运行
livenessProbe 存活探针还活着吗？需要重启吗？重启容器（由 kubelet 执行，受重启策略约束）启动探针成功后，整个生命周期周期性运行
readinessProbe 就绪探针现在能接流量吗？Pod 变成 NotReady，从 Service 的端点中移除，不重启启动探针成功后，整个生命周期周期性运行

探测方式

🌐

httpGet

向容器发 HTTP GET，状态码 200–399 算成功。Web 应用最常用。

🔌

tcpSocket

能建立 TCP 连接就算成功。适合数据库、消息队列等非 HTTP 服务。

⌨

exec

在容器里执行命令，退出码 0 算成功。灵活，但每次都要起进程，开销较大。

📡

grpc

调用标准的 gRPC 健康检查协议，适合 gRPC 服务。

时间参数

参数默认值含义
initialDelaySeconds0容器启动后等多久开始第一次探测
periodSeconds10每隔多久探测一次
timeoutSeconds1单次探测的超时时间，超时算失败
failureThreshold3连续失败多少次才判定为失败
successThreshold1失败后连续成功多少次才恢复（存活和启动探针必须是 1）

动手：存活探针

这个「应用」启动 30 秒后会把自己弄坏（删掉 /tmp/healthy），存活探针用 cat 检查这个文件：

apiVersion: v1
kind: Pod
metadata:
  name: liveness-exec
spec:
  containers:
  - name: ctr
    image: busybox:1.36
    command: ["sh", "-c", "touch /tmp/healthy; sleep 30; rm -f /tmp/healthy; sleep 600"]
    livenessProbe:
      exec:
        command: ["cat", "/tmp/healthy"]   # 文件在 → 退出码 0 → 健康
      initialDelaySeconds: 5
      periodSeconds: 5
      failureThreshold: 3

$ cd extras/probes
$ kubectl apply -f liveness-exec.yml

$ kubectl get pod liveness-exec --watch
NAME            READY   STATUS    RESTARTS      AGE
liveness-exec   1/1     Running   0             10s
liveness-exec   1/1     Running   1 (1s ago)    47s      # ← 30 秒坏掉 + 3 次 × 5 秒 ≈ 45 秒后被重启

$ kubectl describe pod liveness-exec
Events:
  Warning  Unhealthy  12s (x3 over 22s)  kubelet  Liveness probe failed: cat: can't open
           '/tmp/healthy': No such file or directory
  Normal   Killing    12s                kubelet  Container ctr failed liveness probe, will be restarted

重启后的容器又是一个全新的进程，/tmp/healthy 被重新创建，于是周而复始。这就是存活探针「坏了就重启」的自愈能力。

$ kubectl delete -f liveness-exec.yml

动手：就绪探针

三个 nginx 副本挂在一个 Service 后面。就绪探针用 httpGet / 检查首页，存活探针只检查 80 端口能否连上：

      containers:
      - name: nginx
        image: nginx:1.27
        readinessProbe:
          httpGet:
            path: /
            port: 80
          periodSeconds: 5
          failureThreshold: 2
        livenessProbe:
          tcpSocket:
            port: 80
          periodSeconds: 10
          failureThreshold: 3

$ kubectl apply -f readiness-http.yml
$ kubectl get pods -l app=web-probes
NAME                          READY   STATUS    RESTARTS   AGE
web-probes-7d9c5b8f6b-8kq2z   1/1     Running   0          30s
web-probes-7d9c5b8f6b-h4m7x   1/1     Running   0          30s
web-probes-7d9c5b8f6b-x2lpn   1/1     Running   0          30s

# 「弄坏」其中一个：删掉首页，nginx 会对 / 返回 403
$ kubectl exec web-probes-7d9c5b8f6b-8kq2z -- rm /usr/share/nginx/html/index.html

$ kubectl get pods -l app=web-probes
NAME                          READY   STATUS    RESTARTS   AGE
web-probes-7d9c5b8f6b-8kq2z   0/1     Running   0          2m      # ← 未就绪，但没有重启
web-probes-7d9c5b8f6b-h4m7x   1/1     Running   0          2m
web-probes-7d9c5b8f6b-x2lpn   1/1     Running   0          2m

$ kubectl describe pod web-probes-7d9c5b8f6b-8kq2z
Events:
  Warning  Unhealthy  5s (x3 over 15s)  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 403

$ kubectl get endpointslices -l kubernetes.io/service-name=web-probes -o yaml | grep -A3 addresses
  - addresses:
    - 10.244.1.12
    conditions:
      ready: false          # ← 这个端点被标记为未就绪，Service 不再把流量发给它

$ kubectl exec web-probes-7d9c5b8f6b-8kq2z -- sh -c 'echo ok > /usr/share/nginx/html/index.html'
$ kubectl get pods -l app=web-probes          # 几秒后重新变成 1/1

就绪探针与滚动更新

就绪探针还有一个关键作用：滚动更新（第 6 章）只有在新 Pod 就绪后才会继续删除旧 Pod。 没有就绪探针时，容器一启动就被认为「可用」，哪怕应用还在初始化，旧 Pod 就已经被换掉了，用户会看到一阵报错。 配好就绪探针（再加上 minReadySeconds），零停机发布才名副其实。 

$ kubectl delete -f readiness-http.yml

动手：启动探针

有的应用启动很慢（比如 Java 应用要预热一分钟）。如果只配存活探针，它可能还没启动完就被判定「死了」而重启，然后再次启动、再次被杀，永远起不来。 过去的做法是把 initialDelaySeconds 设得很大，但这会让真正卡死时发现得也很慢。启动探针是更好的方案： 

    command: ["sh", "-c", "echo warming up...; sleep 40; touch /tmp/started; echo ready; sleep 3600"]
    startupProbe:
      exec:
        command: ["cat", "/tmp/started"]
      periodSeconds: 5
      failureThreshold: 12        # 最多给 12 × 5 = 60 秒启动时间
    livenessProbe:                # 启动成功后才开始运行，可以设得很灵敏
      exec:
        command: ["cat", "/tmp/started"]
      periodSeconds: 10
      failureThreshold: 3
    readinessProbe:
      exec:
        command: ["cat", "/tmp/started"]
      periodSeconds: 5

$ kubectl apply -f startup-probe.yml
$ kubectl get pod slow-start --watch
NAME         READY   STATUS    RESTARTS   AGE
slow-start   0/1     Running   0          5s
slow-start   0/1     Running   0          40s
slow-start   1/1     Running   0          45s      # ← 启动探针成功，Pod 就绪，RESTARTS 仍是 0

$ kubectl delete -f startup-probe.yml

探针的常见坑

坑后果建议
存活探针检查数据库等依赖依赖一抖，所有副本一起重启，故障被放大存活探针只检查进程自己；依赖问题交给就绪探针或应用内重试
存活和就绪用同一个接口、同样的阈值本该「暂停接流量」的情况变成了重启分开接口（如 /healthz 和 /ready），存活探针的阈值更宽松
timeoutSeconds 保持默认 1 秒CPU 被限流或 GC 时探针超时，误判失败给探针留余量，比如 2–5 秒
用超大的 initialDelaySeconds 应付慢启动运行中卡死后要很久才发现改用启动探针
exec 探针执行很重的命令每隔几秒起一个进程，浪费资源优先用 httpGet / tcpSocket
完全不配探针卡死的 Pod 一直「Running」；发布时流量打到没准备好的 Pod至少给对外服务配就绪探针

资源：requests 与 limits 再深入

第 4 章讲过：requests 是下限，调度器据此挑节点并预留；limits 是上限，运行时据此封顶。这里补充几个容易踩坑的细节。

单位

CPU

1 = 1 个 vCPU / 核

500m = 0.5 核（m 表示千分之一，读作 millicores）

100m = 0.1 核，是很常见的起步值

内存

128Mi = 128 × 1024 × 1024 字节（二进制单位）

128M = 128 × 1000 × 1000 字节（十进制单位）

两者差约 5%，统一使用 Mi / Gi；小心别把 128m（千分之 128 字节！）当成 128Mi

超出 limits 会怎样

  • CPU 超限 → 限流（throttling）：CPU 是可压缩资源，进程不会被杀，只是被分到的时间片变少，表现为变慢、探针超时。
  • 内存超限 → OOMKilled：内存不可压缩，超过就被内核杀掉，退出码 137（第 17 章案例 4）。
💡 一种常见的设置思路

很多团队的做法是：内存的 requests 和 limits 设成相同或接近（内存超了就会被杀，可预测性最重要）； CPU 设好 requests，limits 设得宽松一些甚至不设（避免不必要的限流）。这不是唯一正确答案，要结合你的应用和集群策略来定， 但无论怎样，requests 一定要设——调度、QoS、HPA 都依赖它。

QoS 等级与驱逐顺序

Kubernetes 根据每个 Pod 的 requests 和 limits，自动给它分配一个 QoS（服务质量）等级：

QoS 等级条件节点内存紧张时
Guaranteed每个容器都设了 CPU 和内存的 requests 与 limits，且 requests = limits最后才被驱逐
Burstable至少一个容器设了 requests 或 limits，但不满足 Guaranteed其次，用量超出 requests 越多越先被驱逐
BestEffort所有容器都没设任何 requests 和 limits最先被驱逐
$ kubectl apply -f qos.yml
$ kubectl get pods -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
NAME             QOS
qos-besteffort   BestEffort
qos-burstable    Burstable
qos-guaranteed   Guaranteed

$ kubectl delete -f qos.yml

LimitRange 与 ResourceQuota：给 Namespace 定规矩

每个 Pod 都靠开发者自觉设置资源不太现实。Namespace 级别有两个工具：

apiVersion: v1
kind: LimitRange
metadata:
  name: container-defaults
  namespace: res-demo
spec:
  limits:
  - type: Container
    defaultRequest:         # 没写 requests 时的默认值
      cpu: 100m
      memory: 128Mi
    default:                # 没写 limits 时的默认值
      cpu: 500m
      memory: 256Mi
    max:                    # 单个容器的上限
      cpu: "1"
      memory: 512Mi
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-budget
  namespace: res-demo
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 2Gi
    limits.cpu: "4"
    limits.memory: 4Gi
    pods: "10"

$ kubectl apply -f limits-quota.yml

# 不写任何资源配置，看看 LimitRange 自动填了什么
$ kubectl run demo --image=nginx:1.27 -n res-demo
$ kubectl get pod demo -n res-demo -o jsonpath='{.spec.containers[0].resources}'
{"limits":{"cpu":"500m","memory":"256Mi"},"requests":{"cpu":"100m","memory":"128Mi"}}

# 超过单容器上限会被直接拒绝
$ kubectl run greedy --image=nginx:1.27 -n res-demo --overrides='{"spec":{"containers":[{"name":"greedy","image":"nginx:1.27","resources":{"limits":{"cpu":"2"}}}]}}'
Error from server (Forbidden): pods "greedy" is forbidden: maximum cpu usage per Container is 1, but limit is 2

# 看看预算用了多少
$ kubectl describe quota team-budget -n res-demo
Name:            team-budget
Namespace:       res-demo
Resource         Used   Hard
--------         ----   ----
limits.cpu       500m   4
limits.memory    256Mi  4Gi
pods             1      10
requests.cpu     100m   2
requests.memory  128Mi  2Gi

$ kubectl delete -f limits-quota.yml       # 删除 Namespace 会连带删除里面的一切

HPA：按负载自动扩缩

第 6 章介绍过 HorizontalPodAutoscaler（HPA）：它根据指标自动调整 Deployment 的副本数。下面看看它具体怎么算、怎么用。

★ HPA 的 CPU 百分比是相对 requests 计算的

averageUtilization: 50 指的是「平均用量达到 requests 的 50%」。所以被 HPA 管理的容器必须设置 CPU requests， 否则 HPA 无法计算，会显示 <unknown>。

准备：安装 metrics-server

HPA 和 kubectl top 都依赖 metrics-server。很多云上托管集群已经预装；Docker Desktop 等本地集群通常需要自己装：

$ kubectl top nodes                  # 报错 "Metrics API not available" 说明还没装
$ kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 本地集群（kind / Docker Desktop）的 kubelet 证书通常不受信任，需要额外加一个参数
$ kubectl patch deployment metrics-server -n kube-system --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'

$ kubectl top nodes                  # 等一两分钟，能看到 CPU 和内存用量就好了
NAME                    CPU(cores)   CPU(%)   MEMORY(bytes)   MEMORY(%)
desktop-control-plane   180m         4%       820Mi           10%
desktop-worker          60m          1%       410Mi           5%
⚠ --kubelet-insecure-tls 只用于本地实验

它会跳过对 kubelet 证书的校验。生产集群应该配置正确的证书，而不是关掉校验。

动手：让 HPA 扩起来

示例基于 Kubernetes 官方的 HPA 演练：hpa-example 镜像每收到一个请求就做一段 CPU 密集计算。

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:                  # 管理哪个对象
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50     # 目标：平均 CPU 用量 = requests 的 50%
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 120   # 缩容前观察 2 分钟，防止来回抖动（默认 5 分钟）

$ kubectl apply -f hpa.yml
$ kubectl get hpa php-apache
NAME         REFERENCE               TARGETS       MINPODS   MAXPODS   REPLICAS   AGE
php-apache   Deployment/php-apache   cpu: 0%/50%   1         10        1          60s

# 在另一个终端里制造负载：不停地请求这个服务
$ kubectl run load-generator --rm -it --image=busybox:1.36 --restart=Never -- \
  /bin/sh -c "while sleep 0.01; do wget -q -O- http://php-apache; done"

# 回到第一个终端观察
$ kubectl get hpa php-apache --watch
NAME         REFERENCE               TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
php-apache   Deployment/php-apache   cpu: 0%/50%     1         10        1          2m
php-apache   Deployment/php-apache   cpu: 250%/50%   1         10        1          3m
php-apache   Deployment/php-apache   cpu: 250%/50%   1         10        5          3m
php-apache   Deployment/php-apache   cpu: 68%/50%    1         10        5          4m
php-apache   Deployment/php-apache   cpu: 52%/50%    1         10        7          4m

负载上来后 CPU 冲到 250%，HPA 计算 ⌈1 × 250 / 50⌉ = 5，副本数直接变成 5；之后继续微调，直到平均值接近 50%。 在负载终端里按 Ctrl+C 停止，再观察约两分钟（稳定窗口），副本数会逐步降回 1。 

$ kubectl describe hpa php-apache        # Events 里能看到每次扩缩的原因
Events:
  Normal  SuccessfulRescale  3m  horizontal-pod-autoscaler  New size: 5; reason: cpu resource
          utilization (percentage of request) above target

$ kubectl delete -f hpa.yml

使用 HPA 的注意事项

  • 别和 YAML 里的 replicas 打架：HPA 会修改 Deployment 的副本数。如果你之后再 kubectl apply 一个写着 replicas: 1 的文件，又会把它改回去。启用 HPA 后，常见做法是从 Deployment 清单里去掉 replicas 字段。
  • 扩容要快，缩容要稳：默认缩容有 5 分钟稳定窗口，避免流量稍降就缩、一涨又扩的抖动；behavior 字段可以精细调节。
  • 新 Pod 要能快速就绪：配合本章前面的就绪探针，新副本准备好之前不会接流量。
  • 不止 CPU：autoscaling/v2 支持内存以及自定义指标、外部指标（比如队列长度），后者需要额外安装指标适配器。
  • 和其他扩缩器配合：Pod 放不下时由 Cluster Autoscaler 加节点（第 6 章）；VPA 调整单个 Pod 的资源，一般不要和基于同一指标的 HPA 同时使用。

小结

  • startupProbe 给慢启动应用争取时间；livenessProbe 失败会重启容器；readinessProbe 失败会把 Pod 移出 Service 流量，但不重启。
  • 存活探针只检查进程自身，别依赖外部服务；探针超时和阈值要留余量。
  • CPU 超限被限流，内存超限被 OOMKill；内存统一用 Mi/Gi。
  • QoS 等级（Guaranteed / Burstable / BestEffort）由 requests 和 limits 决定，影响节点紧张时的驱逐顺序。
  • LimitRange 给容器补默认值和上限，ResourceQuota 限制整个 Namespace 的总量。
  • HPA 依赖 metrics-server 和 CPU requests，按「当前副本数 × 当前指标 / 目标指标」计算副本数。

动手练习

  1. 把 liveness-exec.yml 的存活探针改成就绪探针，重新部署，对比 RESTARTS 和 READY 两列的变化。
  2. 去掉 startup-probe.yml 里的 startupProbe，同时把存活探针的 failureThreshold 改成 1，观察这个慢启动应用会发生什么。
  3. 给第 6 章的 deployments/deploy.yml 加上就绪探针，再做一次从 1.0 到 2.0 的滚动更新，用 kubectl get pods --watch 观察新 Pod 的 READY 何时变成 1/1。
  4. 在 HPA 实验中把 averageUtilization 改成 80，重新施加负载，比较最终的副本数。
