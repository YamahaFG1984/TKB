第 9 章

服务发现深入

一个繁忙的集群上跑着成百上千个微服务。应用 A 怎么找到应用 B？答案是 服务发现： Kubernetes 自动把每个 Service 的名字登记到集群 DNS，再让每个容器都去问这个 DNS。 这一章把「名字 → IP → Pod」这条链路的每一环都拆开看，最后教你怎么排查 DNS 问题。

本章目标

  • 理解服务注册表（集群 DNS）由哪些对象组成
  • 理解服务注册和服务发现都是自动的，以及各自的步骤
  • 读懂容器里的 /etc/resolv.conf
  • 搞懂没有路由的 ClusterIP 是怎么把流量送到 Pod 的
  • 掌握 FQDN 格式，跨 Namespace 访问 Service
  • 学会排查集群 DNS 故障

铺垫：应用之间通过 Service 通信

大多数应用都躲在自己的 Service 后面，拥有可靠的名字和 IP。所以本章说「应用 A 要找应用 B」，指的是找应用 B 前面的那个 Service。 应用要给别的应用发请求，需要两样东西：

  1. 知道对方的名字（即对方 Service 的名字）——开发者负责；
  2. 把名字转换成 IP 地址——Kubernetes 负责。

服务注册表：集群 DNS

服务注册表的工作是维护一份「Service 名字 → IP」的清单。每个 Kubernetes 集群都内置一个集群 DNS作为服务注册表。 它本身就是一个 Kubernetes 原生应用：由一个 Deployment（通常叫 coredns 或 kube-dns）管理的两个或更多 Pod，前面有一个永远叫 kube-dns 的 Service。

这些对象都带有 k8s-app=kube-dns 标签，用它就能找到：

$ kubectl get pods -n kube-system -l k8s-app=kube-dns
NAME                       READY   STATUS    RESTARTS   AGE
coredns-76f75df574-d6nn5   1/1     Running   0          6h55m
coredns-76f75df574-n7qzk   1/1     Running   0          6h55m

$ kubectl get deploy -n kube-system -l k8s-app=kube-dns
NAME      READY   UP-TO-DATE   AVAILABLE   AGE
coredns   2/2     2            2           6h55m

$ kubectl get svc -n kube-system -l k8s-app=kube-dns
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)                  AGE
kube-dns   ClusterIP   10.96.0.10   <none>        53/UDP,53/TCP,9153/TCP   6h55m

Pod 通常使用 registry.k8s.io/coredns/coredns 镜像。Service 名字永远是 kube-dns，但 IP 每个集群不同。

服务注册：全自动

服务注册分三步：

  1. 给 Service 起个名字——开发者；
  2. 给 Service 分配一个 IP——Kubernetes；
  3. 把名字和 IP 登记到集群 DNS——Kubernetes。

例如你把新应用部署在一个叫 valkyrie-web 的 Service 后面，Kubernetes 会确保名字唯一，自动分配 ClusterIP，并把它登记到集群 DNS。 之所以是自动的，是因为集群 DNS 本身就是一个监视 API 服务器上新 Service 的控制器。你的应用里完全不需要写任何注册逻辑。

服务发现：把名字变成 IP

假设集群里有两个应用：

应用Service 名ClusterIP
enterpriseent192.168.201.240
cerritoscer192.168.200.217

enterprise 要访问 cerritos，开发者需要把 cer 这个名字配置进 enterprise。剩下的事 Kubernetes 来做： 它会自动配置每个容器的 /etc/resolv.conf，填上集群 DNS 的 IP，并加上搜索域（search domain）。 

$ cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10        # 集群内部 DNS（kube-dns Service）的 ClusterIP
options ndots:5

可以验证：resolv.conf 里的 nameserver 正是 kube-dns Service 的 ClusterIP。

ClusterIP 路由：没有路的 IP 怎么走？

拿到 ClusterIP 后还有最后一个谜题：ClusterIP 位于一个叫服务网络（service network）的特殊网络上，而到这个网络根本没有路由！

ⓘ 术语：默认网关

系统不知道把流量发往哪里时，就发给默认网关；默认网关再转给下一个设备，希望它知道该怎么走。

容器的默认网关把流量交给所在节点，节点也没有到服务网络的路由，于是又发给自己的默认网关——这就让节点内核处理了这个流量，魔法就在这里发生。 每个节点上运行的 kube-proxy 是一个监视 Service 和 EndpointSlice 的控制器，它在内核里写好规则，把发往 ClusterIP 的流量拦截下来，重定向到某个健康 Pod 的 IP。

★ 一句话串起整条链路

应用请求 cer → 容器按 resolv.conf 问集群 DNS → 拿到 ClusterIP → 发往 ClusterIP（没有路由，走默认网关） → 节点内核按 kube-proxy 的规则改写成 Pod IP → 到达 cerritos 的某个 Pod。

服务发现与 Namespace

每个对象都在集群的地址空间里有个名字。这个地址空间是一个 DNS 域，叫集群域（cluster domain），大多数集群是 cluster.local。 Namespace 把这个地址空间再划分开：

对象名在同一 Namespace 内必须唯一，但不同 Namespace 之间可以重名。所以可以在同一集群的 dev 和 prod 里跑两套完全相同的配置。 规则很简单：同一 Namespace 内用短名字，跨 Namespace 必须用 FQDN。

动手：同 Namespace 与跨 Namespace 访问

service-discovery/sd-example.yml 定义了两个 Namespace、两个同名 Deployment、两个同名 Service，以及只在 dev 里的一个 jump Pod：

apiVersion: v1
kind: Namespace
metadata:
  name: dev
---
kind: Deployment
apiVersion: apps/v1
metadata:
  name: enterprise
  namespace: dev
spec:
  selector:
    matchLabels:
      app: enterprise
  replicas: 2
  template:
    metadata:
      labels:
        app: enterprise
    spec:
      terminationGracePeriodSeconds: 1
      containers:
      - image: nigelpoulton/k8sbook:text-dev    # prod 里用 text-prod
        name: enterprise-ctr
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: ent
  namespace: dev                                # prod 里有一个同名的
spec:
  ports:
  - port: 8080
  selector:
    app: enterprise
---
apiVersion: v1
kind: Pod
metadata:
  name: jump
  namespace: dev
spec:
  terminationGracePeriodSeconds: 5
  containers:
  - image: ubuntu
    name: jump
    tty: true
    stdin: true
💡 示例应用长什么样

镜像 k8sbook:text-dev 的源码在仓库的 web-app/text/main.go：一个极简的 Go Web 服务器， 在 8080 端口返回 Hello from the DEV Namespace! 和自己的主机名（也就是 Pod 名），正好用来判断请求到底落在了哪个 Namespace 的哪个 Pod 上。 

$ kubectl apply -f sd-example.yml
namespace/dev created
namespace/prod created
deployment.apps/enterprise created
deployment.apps/enterprise created
service/ent created
service/ent created
pod/jump created

$ kubectl get all --namespace dev
$ kubectl get all --namespace prod

登录 dev 里的 jump Pod，看看它的 resolv.conf：

$ kubectl exec -it jump --namespace dev -- bash
root@jump:/# cat /etc/resolv.conf
search dev.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

root@jump:/# apt-get update && apt-get install curl -y

root@jump:/# curl ent:8080
Hello from the DEV Namespace!
Hostname: enterprise-76fc64bd9-lvzsn

root@jump:/# curl ent.prod.svc.cluster.local:8080
Hello from the PROD Namespace!
Hostname: enterprise-5cfcd578d7-nvzlp

root@jump:/# exit

注意搜索域的第一项是 dev.svc.cluster.local——容器所在的 Namespace。所以短名字 ent 被补全成 dev 里的 Service； 要访问 prod 的，就得写完整的 FQDN。

排查服务发现问题

集群 DNS 的关键组件都在 kube-system 里，并带有 k8s-app=kube-dns 标签：

$ kubectl get deploy -n kube-system -l k8s-app=kube-dns
$ kubectl get pods -n kube-system -l k8s-app=kube-dns

$ kubectl logs coredns-76f75df574-n7qzk -n kube-system
maxprocs: Leaving GOMAXPROCS=8: CPU quota undefined
.:53
[INFO] plugin/reload: Running configuration SHA512 = 1b226df7...
CoreDNS-1.13.1
linux/arm64, go1.25.2, 1db4568

$ kubectl get svc kube-dns -n kube-system
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)                  AGE
kube-dns   ClusterIP   10.96.0.10   <none>        53/UDP,53/TCP,9153/TCP   7h5m

$ kubectl get endpointslice -n kube-system -l k8s-app=kube-dns
NAME             ADDRESSTYPE   PORTS        ENDPOINTS                AGE
kube-dns-jb72g   IPv4          9153,53,53   10.244.1.9,10.244.1.14   7h5m
⚠ IP 必须对得上

kube-dns Service 的 ClusterIP 必须和所有容器 /etc/resolv.conf 里的 nameserver 一致，否则容器会把 DNS 查询发错地方。

用 dnsutils Pod 深入测试

启动一个带 ping、curl、dig、nslookup 等工具的排障 Pod（jessie-dnsutils 是常用选择）：

$ kubectl run -it dnsutils \
  --image registry.k8s.io/e2e-test-images/jessie-dnsutils:1.7

# nslookup kubernetes
Server:     10.96.0.10
Address:    10.96.0.10#53

Name:       kubernetes.default.svc.cluster.local
Address:    10.96.0.1

kubernetes 这个 Service 每个集群都有（它把 API 服务器暴露给所有 Pod），是测试 DNS 的好目标。 前两行应该是集群 DNS 的 IP，后两行是 kubernetes Service 的 FQDN 和 ClusterIP（可以用 kubectl get svc kubernetes 核对）。 如果出现 nslookup: can't resolve kubernetes，说明 DNS 有问题，一个简单的修复办法是删掉 coredns Pod，让 Deployment 重建它们： 

$ kubectl delete pod -n kube-system -l k8s-app=kube-dns
pod "coredns-76f75df574-d6nn5" deleted
pod "coredns-76f75df574-n7qzk" deleted

清理

$ kubectl delete pod dnsutils
$ kubectl delete -f sd-example.yml

小结

  • Kubernetes 用内部的集群 DNS做服务注册表：一个监视新 Service 并自动登记名字和 IP 的原生应用（coredns Pod + kube-dns Service）。
  • 每个节点的 kubelet 把所有容器配置成使用集群 DNS 做服务发现（/etc/resolv.conf）。
  • 集群 DNS 把 Service 名解析成 ClusterIP——服务网络上的稳定虚拟 IP。这个网络没有路由，但 kube-proxy 让每个节点把 ClusterIP 流量重定向到 Pod 网络上的 Pod IP。
  • 同 Namespace 用短名字，跨 Namespace 用 <名字>.<namespace>.svc.cluster.local。

动手练习

  3. 把 dev 里的 enterprise 缩容到 0（kubectl scale deploy enterprise -n dev --replicas 0），DNS 还能解析出 ent 吗？curl 呢？想想 DNS 和 EndpointSlice 分别负责什么。
