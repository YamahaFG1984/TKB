排错实战

学会部署只是第一步，真正的日常是「为什么它没跑起来」。这一章把初学者最常遇到的故障—— Pending、ImagePullBackOff、CrashLoopBackOff、OOMKilled、Service 不通、PVC 卡住、发布卡住—— 逐个故意制造出来，再一步步查出原因、修好它。

ⓘ 关于补充篇

第 17、18 章不是原书内容，是本教程为初学者补充的实战章节，用到的概念都在前 16 章讲过。 配套的故障示例在仓库的 extras/troubleshooting/ 目录，每个文件都是故意写错的。 下文中的命令输出是按 Kubernetes 的标准格式整理的示例，你的集群里名字、IP、时间会不同，个别措辞也可能随版本略有差异。

⚠ 待验证：本章命令输出尚未在真实集群上运行核对

本章的示例 YAML 已通过语法校验，但文中展示的命令输出是按 Kubernetes 标准格式整理的，还没有在真实集群上逐条运行核对。 如果你实际看到的报错措辞、状态变化或数值与文中不同，以你的集群为准。

本章目标

  • 掌握排错「三板斧」：get → describe（看 Events）→ logs
  • 看到 Pod 状态就能判断问题出在生命周期的哪一步
  • 独立排查 7 类最常见的故障，并知道怎么修
  • 按固定顺序排查「Service 访问不通」
  • 会用 logs --previous、kubectl debug、临时 Pod、port-forward 等工具

排错心法

Kubernetes 的故障看起来五花八门，但排查思路几乎总是一样的：先看状态，再看事件，最后看日志。 状态告诉你「卡在哪一步」，事件告诉你「Kubernetes 认为出了什么事」，日志告诉你「应用自己说了什么」。 

$ kubectl get pods -o wide                       # 状态总览
$ kubectl describe pod <pod>                     # 详情 + Events（看最底部）
$ kubectl logs <pod> [-c 容器名]                 # 当前容器的日志
$ kubectl logs <pod> --previous                  # 上一次（已崩溃）容器的日志
$ kubectl get events --sort-by=.lastTimestamp    # 整个 Namespace 的事件，按时间排序
$ kubectl events --for pod/<pod>                 # 较新的 kubectl：只看某个对象的事件
⚠ Events 只保留大约一小时

事件默认只保存一段时间（通常 1 小时）。出了问题要尽早 describe；需要长期留存的话，得把事件导出到日志系统。

从状态判断问题出在哪一步

回忆第 4 章的部署流程：调度 → 拉镜像 → 创建容器 → 运行 → 就绪。每一种常见错误状态，都对应其中某一步失败了：

准备工作：所有示例都在仓库的 extras/troubleshooting 目录下执行。

$ cd extras/troubleshooting

案例 1：Pending —— 没有节点放得下

    resources:
      requests:
        cpu: "64"          # 要 64 个 CPU 核
        memory: 500Gi      # 和 500G 内存

$ kubectl apply -f 01-pending.yml
pod/tb-pending created

$ kubectl get pods
NAME         READY   STATUS    RESTARTS   AGE
tb-pending   0/1     Pending   0          45s

$ kubectl describe pod tb-pending
...
Node:             <none>                  # ← 还没被分配到任何节点
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  45s   default-scheduler  0/3 nodes are available: 3 Insufficient cpu,
           3 Insufficient memory. preemption: 0/3 nodes are available: 3 No preemption victims
           found for incoming pod.

Node: <none> 和 FailedScheduling 说明问题出在调度这一步：调度器在过滤阶段（第 2 章）就把所有节点都排除了。 消息会逐条告诉你每个节点被排除的原因：

FailedScheduling 里的提示含义怎么办
Insufficient cpu / memory节点剩余资源小于 Pod 的 requests调小 requests，或加节点（开启集群自动扩缩时会自动加）
had untolerated taint {...}节点有污点，Pod 没有对应的容忍加 tolerations，或调度到别的节点
didn't match Pod's node affinity/selectornodeSelector / 亲和性规则没有节点满足检查节点标签：kubectl get nodes --show-labels
pod has unbound immediate PersistentVolumeClaimsPod 用的 PVC 还没绑定到 PV见案例 6
💡 看看节点还剩多少

kubectl describe node <节点> 里的 Allocated resources 一节列出了节点上所有 Pod 的 requests 总和。调度器看的是 requests，而不是实际用量。

$ kubectl delete -f 01-pending.yml

案例 2：ImagePullBackOff —— 镜像拉不下来

$ kubectl apply -f 02-imagepull.yml          # image: nginx:9.99.99（不存在的标签）

$ kubectl get pods --watch
NAME           READY   STATUS             RESTARTS   AGE
tb-imagepull   0/1     ContainerCreating  0          1s
tb-imagepull   0/1     ErrImagePull       0          3s
tb-imagepull   0/1     ImagePullBackOff   0          15s

$ kubectl describe pod tb-imagepull
Events:
  Type     Reason   Age   From     Message
  ----     ------   ----  ----     -------
  Normal   Pulling  20s   kubelet  Pulling image "nginx:9.99.99"
  Warning  Failed   18s   kubelet  Failed to pull image "nginx:9.99.99": ... failed to resolve
           reference "docker.io/library/nginx:9.99.99": docker.io/library/nginx:9.99.99: not found
  Warning  Failed   18s   kubelet  Error: ErrImagePull
  Normal   BackOff  5s    kubelet  Back-off pulling image "nginx:9.99.99"
  Warning  Failed   5s    kubelet  Error: ImagePullBackOff

ErrImagePull 是「这次拉失败了」，ImagePullBackOff 是「失败了好几次，kubelet 正在等待一段越来越长的时间后再试」。 关键是看 Failed to pull image 后面的原因：

报错里的关键词常见原因
not found / manifest unknown镜像名或标签拼错了，或者那个标签根本不存在
pull access denied / unauthorized私有仓库，Pod 没有配置 imagePullSecrets
no match for platform in manifest镜像没有当前节点 CPU 架构（amd64/arm64）的版本
i/o timeout / dial tcp节点访问不了镜像仓库（网络、DNS、代理、防火墙）
toomanyrequests触发了 Docker Hub 的匿名拉取频率限制

修复：改成正确的标签（比如 nginx:1.27）再 apply。注意 Pod 的大部分字段不可变，但镜像恰好是少数允许修改的字段之一，所以直接 apply 新镜像就行。

$ kubectl delete -f 02-imagepull.yml

案例 3：CrashLoopBackOff —— 应用反复崩溃

    command: ["sh", "-c", "echo 'connecting to database db:5432...'; sleep 3; echo 'FATAL: database not reachable' >&2; exit 1"]

$ kubectl apply -f 03-crashloop.yml

$ kubectl get pods
NAME           READY   STATUS             RESTARTS      AGE
tb-crashloop   0/1     CrashLoopBackOff   3 (25s ago)   80s

CrashLoopBackOff 不是错误本身，而是一个「症状」：容器启动 → 退出 → kubelet 按重启策略（默认 Always，第 4 章）重启它 → 又退出…… 每次重启前等待的时间会翻倍，最长 5 分钟：

真正的原因要在两处找：退出码和上一次的日志。

$ kubectl describe pod tb-crashloop
...
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1                 # ← 应用自己以错误码 1 退出
      Started:      ...
      Finished:     ...
    Restart Count:  3
Events:
  Warning  BackOff  10s (x6 over 75s)  kubelet  Back-off restarting failed container ctr in pod ...

$ kubectl logs tb-crashloop               # 当前这次可能还没输出或刚重启
$ kubectl logs tb-crashloop --previous    # ← 看「上一次」崩溃时的日志
connecting to database db:5432...
FATAL: database not reachable

常见退出码

退出码含义排查方向
0正常结束进程跑完就退出了：长期服务不该退出，检查启动命令；一次性任务应该用 Job（重启策略也别用 Always）
1 等应用自己报错退出看 logs --previous：配置错误、依赖连不上、参数不对……
126 / 127命令不能执行 / 找不到command 写错，或镜像里没有这个程序（比如精简镜像里没有 sh）
137被 SIGKILL 杀死（128+9）最常见是内存超限 → 案例 4；也可能是存活探针失败后被重启（第 18 章）
143收到 SIGTERM 后退出（128+15）正常的关闭流程，比如滚动更新、删除 Pod
💡 容器一启动就崩，没法 exec 进去怎么办？

临时把启动命令改成 ["sleep", "3600"]，Pod 就会稳定运行，然后 kubectl exec -it 进去手动执行原来的启动命令， 看看环境变量、配置文件、网络连通性到底哪里不对。查清后记得改回来。也可以用后面介绍的 kubectl debug。 

$ kubectl delete -f 03-crashloop.yml

案例 4：OOMKilled —— 内存超限被杀

    command: ["sh", "-c", "tail /dev/zero"]    # 不停地往内存里缓存数据
    resources:
      requests:
        memory: 32Mi
      limits:
        memory: 64Mi                            # 上限 64Mi

$ kubectl apply -f 04-oomkilled.yml

$ kubectl get pods
NAME           READY   STATUS      RESTARTS     AGE
tb-oomkilled   0/1     OOMKilled   1 (3s ago)   10s

$ kubectl describe pod tb-oomkilled
    Last State:     Terminated
      Reason:       OOMKilled        # ← 关键字
      Exit Code:    137

修复思路：

  • 先确认应用正常情况下需要多少内存（kubectl top pod，需要 metrics-server），把 limits 设得留有余量；
  • 如果内存随时间不断上涨直到被杀，多半是内存泄漏，调大 limit 只能推迟问题；
  • JVM、Node.js 等运行时要让它们感知容器的内存上限（比如调整堆大小参数），否则它们可能按宿主机内存来分配。
ⓘ OOMKilled 和「被驱逐」不是一回事

OOMKilled 是容器超过自己的 limit。还有一种情况是节点整体内存紧张，kubelet 主动驱逐（Evicted）一些 Pod 腾地方， 这时 Pod 状态是 Evicted，describe node 会看到 MemoryPressure。谁先被驱逐由 QoS 等级决定，见第 18 章。 

$ kubectl delete -f 04-oomkilled.yml

案例 5：CreateContainerConfigError —— 配置缺失

$ kubectl apply -f 05-config-missing.yml     # 引用了不存在的 ConfigMap app-config

$ kubectl get pods
NAME        READY   STATUS                       RESTARTS   AGE
tb-config   0/1     CreateContainerConfigError   0          12s

$ kubectl describe pod tb-config
Events:
  Warning  Failed  5s (x3 over 12s)  kubelet  Error: configmap "app-config" not found

镜像已经拉好了，但 kubelet 在创建容器时要把 ConfigMap 的值注入环境变量（第 11 章），找不到就停在这一步。 同类问题还有：ConfigMap 存在但缺少某个键（couldn't find key log-level in ConfigMap）、Secret 不存在、ConfigMap 和 Pod 不在同一个 Namespace。 修复：创建它，Pod 会自动继续启动。 

$ kubectl create configmap app-config --from-literal log-level=debug
$ kubectl get pods
NAME        READY   STATUS    RESTARTS   AGE
tb-config   1/1     Running   0          50s

$ kubectl logs tb-config
LOG_LEVEL=debug

$ kubectl delete -f 05-config-missing.yml
$ kubectl delete configmap app-config
💡 可选的配置

如果某个配置项确实可有可无，可以在 configMapKeyRef 里加 optional: true，找不到时容器照常启动，环境变量为空。

案例 6：PVC 一直 Pending

$ kubectl apply -f 07-pvc-pending.yml       # storageClassName: does-not-exist

$ kubectl get pvc,pod
NAME                           STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS
persistentvolumeclaim/tb-pvc   Pending                                      does-not-exist

NAME             READY   STATUS    RESTARTS   AGE
pod/tb-pvc-pod   0/1     Pending   0          20s

$ kubectl describe pvc tb-pvc
Events:
  Warning  ProvisioningFailed  5s (x3 over 20s)  persistentvolume-controller
           storageclass.storage.k8s.io "does-not-exist" not found

$ kubectl describe pod tb-pvc-pod
Events:
  Warning  FailedScheduling  20s  default-scheduler  0/3 nodes are available:
           pod has unbound immediate PersistentVolumeClaims. ...

Pod 的问题其实来自 PVC，所以要顺着引用链往下查：Pod → PVC → StorageClass → CSI 插件（第 10 章）。PVC 卡住的常见原因：

现象原因
storageclass ... not foundSC 名字写错，或集群上没有这个 SC（换云/换本地集群时最常见）
waiting for first consumer to be created before binding不是错误！SC 是 WaitForFirstConsumer 模式，有 Pod 使用后才会创建卷
waiting for a volume to be created ... by external provisioner 很久不动CSI 插件没装、没运行，或云端配额不足——去 kube-system 查插件 Pod 的日志
没写 storageClassName 且一直 Pending集群没有默认 SC：kubectl get sc 看有没有 (default)
$ kubectl get sc                     # 看看集群里有哪些 SC，哪个是默认
$ kubectl delete -f 07-pvc-pending.yml

修复：把 storageClassName 改成 kubectl get sc 里存在的名字。注意 PVC 的 storageClassName 创建后不能修改，要删掉重建。

案例 7：Service 访问不通

这是最让新手抓狂的一类：Pod 明明都是 Running，就是访问不到。诀窍是沿着流量路径一段一段排查，每一段都有对应的检查命令：

部署示例：一个健康的 Deployment，前面有两个各有毛病的 Service。

kind: Service
metadata:
  name: svc-typo
spec:
  selector:
    app: wbe              # ← 拼错了，Pod 的标签是 app: web
---
kind: Service
metadata:
  name: svc-wrongport
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 8080      # ← nginx 实际监听的是 80

$ kubectl apply -f 06-service.yml

# 起一个临时 Pod 当「客户端」，退出后自动删除
$ kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- sh
/ # nslookup svc-typo                  # ① DNS 正常，能解析出 ClusterIP
/ # wget -qO- -T 3 svc-typo            # 不通
/ # wget -qO- -T 3 svc-wrongport       # 也不通：Connection refused
/ # exit

DNS 没问题，那就往下查 ③ 端点：

$ kubectl get endpointslices -l kubernetes.io/service-name=svc-typo
NAME             ADDRESSTYPE   PORTS     ENDPOINTS   AGE
svc-typo-8xk2p   IPv4          <unset>   <unset>     2m        # ← 一个 Pod 都没有！

$ kubectl describe svc svc-typo | grep -i -E "selector|endpoints"
Selector:          app=wbe
Endpoints:

$ kubectl get pods --show-labels
NAME                      READY   STATUS    LABELS
tb-web-6d4b9c8f7c-2xqlk   1/1     Running   app=web,pod-template-hash=6d4b9c8f7c
tb-web-6d4b9c8f7c-k9mzp   1/1     Running   app=web,pod-template-hash=6d4b9c8f7c

选择器 app=wbe 和 Pod 标签 app=web 对不上，端点自然为空。再看 svc-wrongport：

$ kubectl get endpointslices -l kubernetes.io/service-name=svc-wrongport
NAME                  ADDRESSTYPE   PORTS   ENDPOINTS                AGE
svc-wrongport-7fq9d   IPv4          8080    10.244.1.5,10.244.2.7    2m   # 有 Pod，但端口是 8080

# 绕过 Service，直接连 Pod，确认应用到底在哪个端口
$ kubectl port-forward deploy/tb-web 8888:80
Forwarding from 127.0.0.1:8888 -> 80
# 另开一个终端：curl localhost:8888 能看到 nginx 欢迎页 → 应用在 80 端口

端点有了，但端口是 8080，而 nginx 只监听 80。修复：svc-typo 的选择器改成 app: web，svc-wrongport 的 targetPort 改成 80，重新 apply。

⚠ 另外两个隐蔽的坑
  • 应用只监听 127.0.0.1：在容器里 curl localhost 能通，但从别的 Pod 访问不通。应用要监听 0.0.0.0。
  • NetworkPolicy：如果集群里有网络策略默认拒绝流量，以上全部正确也会不通，用 kubectl get networkpolicy -A 看看。
$ kubectl delete -f 06-service.yml

排错工具箱

kubectl debug：给运行中的 Pod 挂一个调试容器

很多生产镜像非常精简，连 sh、curl 都没有，kubectl exec 进去什么也干不了。kubectl debug 可以往运行中的 Pod 里临时加一个临时容器（ephemeral container）：

$ kubectl debug -it <pod> --image=busybox:1.36 --target=<容器名>
/ # wget -qO- localhost:80        # 同一个 Pod，共享网络，可以直接访问应用端口
/ # ps                            # 有 --target 时能看到应用容器的进程

# 复制一个 Pod 出来调试（比如改掉一直崩溃的启动命令），不影响原 Pod
$ kubectl debug <pod> -it --copy-to=<pod>-debug --container=<容器名> -- sh

# 调试节点：在节点上起一个特权 Pod，宿主机文件系统挂在 /host
$ kubectl debug node/<节点名> -it --image=busybox:1.36

节点出问题时

$ kubectl get nodes
NAME              STATUS     ROLES    AGE   VERSION
desktop-worker    NotReady   <none>   2d    v1.35.1

$ kubectl describe node desktop-worker
Conditions:
  Type             Status   Reason
  ----             ------   ------
  MemoryPressure   False    KubeletHasSufficientMemory
  DiskPressure     True     KubeletHasDiskPressure          # ← 磁盘快满了
  PIDPressure      False    KubeletHasSufficientPID
  Ready            False    KubeletNotReady

NotReady 通常意味着 kubelet 联系不上控制平面，或者节点资源告急。磁盘满常见于镜像和日志堆积。云上的节点可以直接回收重建；自建集群则要登录节点查看 kubelet 和容器运行时的日志。

对象删不掉，一直 Terminating

$ kubectl get pod <pod> -o jsonpath='{.metadata.finalizers}'   # 有 finalizer 在等某个控制器收尾吗
$ kubectl delete pod <pod> --grace-period=0 --force            # 最后手段：强制删除
⚠ 强制删除要谨慎

强制删除只是从 API 里抹掉记录，并不保证节点上的容器真的停了。对 StatefulSet 的 Pod 尤其危险：可能出现两个同名 Pod 同时写一个卷（第 12 章讲过的数据损坏风险）。 Namespace 卡在 Terminating 往往是里面某个资源的 finalizer 在等一个已经被卸载的控制器，应先找到并处理那个资源。

小结

  • 排错三板斧：get 看状态，describe 看事件，logs（必要时 --previous）看应用输出。
  • 状态对应生命周期：Pending → 调度；ImagePullBackOff → 拉镜像；CreateContainerConfigError → 创建容器；CrashLoopBackOff/OOMKilled → 运行；Running 但 0/1 → 就绪。
  • CrashLoopBackOff 是症状，原因看退出码和上一次的日志；137 多半是 OOM。
  • Service 不通按 DNS → Service → 端点 → Pod 就绪 → 端口逐段查，最常见的是选择器和标签不匹配、targetPort 写错。
  • 发布卡住先 rollout undo 止血，再查新 Pod；精简镜像用 kubectl debug 排查。
