第 12 章

StatefulSet：给有状态应用稳定的身份

本章所说的有状态应用，是指会创建并保存有价值数据的应用：数据库、键值存储、需要记住客户端会话的应用…… 它们需要的不是「一群可互换的副本」，而是「每个副本都有固定的名字和自己的数据」。这正是 StatefulSet 的用武之地。

本章目标

  • 说出 StatefulSet 相比 Deployment 多出的三项能力
  • 理解 Pod 命名规则、有序创建/删除，以及 Pod 与卷的绑定
  • 理解 headless Service 与 governing Service，以及每个 Pod 的 DNS 名
  • 动手部署 StatefulSet，并验证对等发现、扩缩、Pod 故障和节点故障的行为
  • 知道删除 StatefulSet 前要先缩容到 0

StatefulSet 与 Deployment

二者有很多共同点：都是 Kubernetes API 资源，都遵循标准的控制器架构（调和观测状态与期望状态的控制循环），都管理 Pod，都提供自愈、扩缩、滚动更新。 但 StatefulSet 多了三项 Deployment 没有的能力：

例如，StatefulSet 的某个 Pod 失败后，替代它的新 Pod 会有相同的 Pod 名、相同的 DNS 主机名，并连接相同的卷——即使新 Pod 被调度到另一个节点上。 被缩容删掉、后来又扩容回来的 Pod 也一样。下面是一个最简单的 StatefulSet： 

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: tkb-sts
spec:
  selector:
    matchLabels:
      app: mongo
  serviceName: "tkb-sts"
  replicas: 3
  template:
    metadata:
      labels:
        app: mongo
    spec:
      containers:
      - name: ctr-mongo
        image: mongo:latest
      ...

Pod 命名

格式是 <StatefulSet 名>-<整数>，整数是从 0 开始的序号（index ordinal）。上例会得到 tkb-sts-0、tkb-sts-1、tkb-sts-2。 Pod 名是 StatefulSet 启动、自愈、扩缩、删除 Pod 以及连接卷的核心。StatefulSet 名还会用来构造每个副本的 DNS 名，所以别用奇怪的字符。

有序创建与删除

这和 Deployment 很不同：Deployment 通过 ReplicaSet 控制器同时启动所有 Pod，可能产生竞争条件。 另外，StatefulSet 控制器自己完成自愈和扩缩，架构上也不同于 Deployment（后者依赖 ReplicaSet 控制器）。

删除 StatefulSet 的两点注意

  1. 删除 StatefulSet 对象不会有序地终止它的 Pod。所以删除前先缩容到 0！
  2. 可以用 terminationGracePeriodSeconds 进一步控制 Pod 终止，常见做法是至少设 10 秒，让应用有时间刷新缓冲区、安全提交还在进行中的写入。

StatefulSet 与卷

卷是 StatefulSet Pod 粘性 ID 的重要组成部分。StatefulSet 控制器创建 Pod 时，也会创建它们需要的卷，并给卷起特殊的名字，把它们和正确的 Pod 关联起来：

虽然卷和特定副本关联，但它们仍通过常规的 PVC 机制与 Pod 解耦，拥有独立的生命周期：Pod 失败或被终止时，卷不受影响， 替代 Pod 可以重新连上幸存的卷和数据，即使它被调度到别的节点。缩容同理：被删的 Pod 的卷还在，之后扩容时新 Pod 会接回原来的卷。 如果你不小心删了一个 StatefulSet Pod（尤其是最后一个副本），这个行为能救命！

故障处理

最简单的是 Pod 故障：5 个副本的 tkb-sts 中 tkb-sts-3 挂了，控制器启动一个同名新 Pod 并连上幸存的卷。 节点故障更复杂，一些老版本需要人工干预——因为 Kubernetes 很难判断节点是真的挂了还是只是暂时重启。 如果它替换了 Pod 后「故障」节点又恢复了，就会有两个一模一样的 Pod 写同一个卷，导致数据损坏。新版本在这方面已经好很多。

网络身份与 headless Service

有些外部应用需要反复连接同一个 Pod。普通 Service 会在一组 Pod 之间负载均衡，这不合适。 StatefulSet 使用一种特殊的 Service——headless Service（无头服务），它为每个 StatefulSet Pod 创建可预测的 DNS 名， 应用可以查询 DNS（服务注册表）拿到完整的 Pod 列表，然后直接连接特定的 Pod。 

apiVersion: v1
kind: Service              # Service
metadata:
  name: mongo-prod
spec:
  clusterIP: None          # 让它成为 headless Service
  selector:
    app: mongo
    env: prod
---
apiVersion: apps/v1
kind: StatefulSet          # StatefulSet
metadata:
  name: sts-mongo
spec:
  serviceName: mongo-prod  # governing Service（主管服务）
  • headless Service：一个没有 ClusterIP（spec.clusterIP: None）的普通 Service 对象；
  • governing Service：在 StatefulSet 的 spec.serviceName 里引用它，它就负责这个 StatefulSet 的 DNS 子域。

二者结合后，Service 会为每个匹配标签选择器的 Pod 创建 DNS SRV 和 A 记录。注意：开发者需要让应用主动去查询 DNS 才能用上这些记录。

动手：部署 StatefulSet

示例在 LKE 和本地 Docker Desktop 多节点集群上测试过。命令都在 statefulsets 目录执行。你将依次部署：① StorageClass ② headless Service ③ StatefulSet（也可以用 app.yml 一次部署全部）。

1. StorageClass

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: block                              # PVC 会引用这个名字
provisioner: linodebs.csi.linode.com       # LKE 块存储 CSI 插件
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
reclaimPolicy: Delete
⚠ 不是 LKE？

Docker Desktop 多节点（kind）集群请改用 dd-kind-sc.yml，它使用 rancher.io/local-path 供应器，创建的 SC 名叫 flash， 所以还要把 sts.yml 里的 storageClassName 从 block 改成 flash。 其他云：要么自己为你的云创建一个名叫 block 的 SC，要么改用集群已有的 SC 并修改 storageClassName。 

$ kubectl apply -f lke-sc.yml
storageclass.storage.k8s.io/block created

$ kubectl get sc
NAME    PROVISIONER               RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION
block   linodebs.csi.linode.com   Delete          WaitForFirstConsumer   true

2. governing headless Service

# 为 StatefulSet Pod 提供 DNS 名的 headless Service
apiVersion: v1
kind: Service              # 普通的 Kubernetes Service
metadata:
  name: dullahan           # 名字里只用合法的 DNS 字符
  labels:
    app: web
spec:
  ports:
  - port: 80
    name: web
  clusterIP: None          # 让它成为 headless Service
  selector:
    app: web

$ kubectl apply -f headless-svc.yml
service/dullahan created

$ kubectl get svc
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)   AGE
dullahan   ClusterIP   None         <none>        80/TCP    31s

3. StatefulSet

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: tkb-sts                    # 所有副本和卷的名字都以它为基础
spec:
  replicas: 3                      # 部署 3 个副本
  selector:
    matchLabels:
      app: web
  serviceName: "dullahan"          # 指定 governing Service
  template:
    metadata:
      labels:
        app: web
    spec:
      terminationGracePeriodSeconds: 10
      containers:
      - name: ctr-web
        image: nginx:latest
        ports:
        - containerPort: 80
          name: web
        volumeMounts:              # ┐ 挂载这个卷
        - name: webroot            # │
          mountPath: /usr/share/nginx/html   # ┘
  volumeClaimTemplates:            # ┐ 为每个 Pod 动态创建一个卷
  - metadata:                      # │
      name: webroot                # │
    spec:                          # │
      accessModes: [ "ReadWriteOnce" ]       # │
      storageClassName: "block"    # │ 通过 block 这个 StorageClass
      resources:                   # │
        requests:                  # │
          storage: 1Gi             # ┘ 仓库里是 1Gi（书中示例为 10Gi）
🏷

replicas: 3

按顺序创建 tkb-sts-0/1/2，每个 Running 且 Ready 后才启动下一个。

🌐

serviceName

指定 governing Service，它为副本创建 DNS SRV 记录，负责 StatefulSet 的 DNS 子域。

💾

volumeClaimTemplates

为每个 Pod 动态创建一个独立的 PVC，并给它们起好能互相关联的名字。

$ kubectl apply -f sts.yml
statefulset.apps/tkb-sts created

$ kubectl get sts --watch
NAME      READY   AGE
tkb-sts   0/3     14s
tkb-sts   1/3     30s
tkb-sts   2/3     60s
tkb-sts   3/3     90s

$ kubectl get pvc
NAME                STATUS   VOLUME            CAPACITY   MODES   STORAGECLASS   AGE
webroot-tkb-sts-0   Bound    pvc-1146...f274   1Gi        RWO     block          100s
webroot-tkb-sts-1   Bound    pvc-3026...6bcb   1Gi        RWO     block          70s
webroot-tkb-sts-2   Bound    pvc-2ce7...e56d   1Gi        RWO     block          40s

每隔约 30 秒多一个副本——这就是控制器在逐个启动。PVC 的 AGE 也正好相差 30 秒，每个都是和对应的 Pod 一起创建的。

测试对等发现

Kubernetes 按如下规则构造 StatefulSet Pod 的 DNS 名：

部署一个预装了 dig 的 jump Pod 来验证：

apiVersion: v1
kind: Pod
metadata:
  name: jump-pod
spec:
  terminationGracePeriodSeconds: 1
  containers:
  - image: registry.k8s.io/e2e-test-images/jessie-dnsutils:1.7
    name: jump-ctr
    tty: true
    stdin: true

$ kubectl apply -f jump-pod.yml
$ kubectl exec -it jump-pod -- bash

root@jump-pod:/# dig SRV dullahan.default.svc.cluster.local
;; QUESTION SECTION:
;dullahan.default.svc.cluster.local. IN SRV

;; ANSWER SECTION:
dullahan.default.svc.cluster.local. 30 IN SRV ... tkb-sts-1.dullahan.default.svc.cluster.local.
dullahan.default.svc.cluster.local. 30 IN SRV ... tkb-sts-0.dullahan.default.svc.cluster.local.
dullahan.default.svc.cluster.local. 30 IN SRV ... tkb-sts-2.dullahan.default.svc.cluster.local.

;; ADDITIONAL SECTION:
tkb-sts-0.dullahan.default.svc.cluster.local. 30 IN A 10.60.0.5
tkb-sts-2.dullahan.default.svc.cluster.local. 30 IN A 10.60.1.7
tkb-sts-1.dullahan.default.svc.cluster.local. 30 IN A 10.60.2.12

root@jump-pod:/# exit

问 dullahan.default.svc.cluster.local（QUESTION）会得到三个 Pod 的 DNS 名（ANSWER，SRV 记录），以及这些名字对应的 IP（ADDITIONAL，A 记录）。 比如一个 MongoDB 副本集的成员，就能用这种方式找到彼此。

扩缩 StatefulSet

把 sts.yml 里的 replicas 从 3 改成 2，重新 apply：

$ kubectl apply -f sts.yml
statefulset.apps/tkb-sts configured

$ kubectl get pods
NAME        READY   STATUS    RESTARTS   AGE
tkb-sts-0   1/1     Running   0          12h
tkb-sts-1   1/1     Running   0          12h

$ kubectl get pvc          # 三个 PVC 都还在
NAME                STATUS   VOLUME            CAPACITY   MODES   STORAGECLASS
webroot-tkb-sts-0   Bound    pvc-5955...d71c   1Gi        RWO     block
webroot-tkb-sts-1   Bound    pvc-d62c...v701   1Gi        RWO     block
webroot-tkb-sts-2   Bound    pvc-2e2f...5f95   1Gi        RWO     block

再把 replicas 改回 3 并 apply，然后验证新的 tkb-sts-2 挂上了原来的卷：

$ kubectl apply -f sts.yml
$ kubectl describe pod tkb-sts-2 | grep ClaimName
    ClaimName:  webroot-tkb-sts-2
知识点说明
失败时暂停缩容如果有 Pod 处于失败状态，Kubernetes 会暂停缩容操作，以保护应用的韧性和数据完整性。
podManagementPolicy默认 OrderedReady（逐个启停）。改成 Parallel 会像 Deployment 一样并行创建/删除（例如 2→5 立刻建 3 个），但命名规则不变，且只影响扩缩，不影响发布和回滚。
滚动更新修改镜像版本后 apply，控制器从最高序号开始逐个替换，每个新 Pod Ready 后才替换下一个。详见 kubectl explain sts.spec.updateStrategy。

测试 Pod 故障与节点故障

Pod 故障

$ kubectl delete pod tkb-sts-0
pod "tkb-sts-0" deleted

$ kubectl get pods --watch
NAME        READY   STATUS              RESTARTS   AGE
tkb-sts-0   1/1     Running             0          12h
tkb-sts-1   1/1     Running             0          12h
tkb-sts-2   1/1     Running             0          10m
tkb-sts-0   0/1     Terminating         0          12h
tkb-sts-0   0/1     Pending             0          0s
tkb-sts-0   0/1     ContainerCreating   0          0s
tkb-sts-0   1/1     Running             0          8s

$ kubectl describe pod tkb-sts-0 | grep ClaimName
    ClaimName:  webroot-tkb-sts-0

新 Pod 名字相同，连接的也是原来的 PVC。

节点故障

先看看副本分布在哪些节点：

$ kubectl get pods -o wide
NAME        READY   STATUS    AGE   IP           NODE
tkb-sts-0   1/1     Running   11m   10.2.0.132   lke343745-544835-5547cbe00000
tkb-sts-1   1/1     Running   12h   10.2.0.3     lke343745-544835-1fbc7b870000
tkb-sts-2   1/1     Running   21m   10.2.1.7     lke343745-544835-2b6286320000

模拟节点故障：

  • LKE：控制台 → Kubernetes → 你的集群 → Node Pool，对运行着某个副本的节点点 Recycle（删除并替换该节点）。
  • Docker Desktop 多节点（kind）：Containers 页面里删除与工作节点同名的容器（如 desktop-worker2）。之后要删掉并重建集群才能恢复 3 个节点；单节点（kubeadm）集群无法做这个实验。
$ kubectl get pods -o wide --watch
NAME        READY   STATUS              AGE    IP           NODE
tkb-sts-0   1/1     Running             14m    10.2.0.132   lke343745...cbe00000
tkb-sts-0   1/1     Terminating         14m    10.2.0.132   lke343745...cbe00000
tkb-sts-0   0/1     Completed           14m    10.2.0.132   lke343745...cbe00000
tkb-sts-0   0/1     Pending             0s     <none>       <none>
tkb-sts-0   0/1     Pending             0s     <none>       lke343745...7b870000
tkb-sts-0   0/1     ContainerCreating   0s     <none>       lke343745...7b870000
tkb-sts-0   1/1     Running             111s   10.2.0.4     lke343745...7b870000

Kubernetes 发现节点消失后终止原 Pod，副本数从 3 降到 2，控制器随即创建新的 tkb-sts-0；调度器把它放到幸存节点上，释放旧的卷挂载后重新绑定 PVC，最终回到 3 个副本。 注意：即使 LKE 用新节点替换了被回收的节点，Kubernetes 也不会自动把已有副本重新平衡到新节点上。

删除 StatefulSet 与清理

$ kubectl scale sts tkb-sts --replicas=0     # 先缩容到 0，保证有序关闭
statefulset.apps/tkb-sts scaled

$ kubectl get sts tkb-sts
NAME      READY   AGE
tkb-sts   0/0     13h

$ kubectl delete sts tkb-sts
$ kubectl delete pod jump-pod
$ kubectl delete svc dullahan
$ kubectl delete pvc webroot-tkb-sts-0 webroot-tkb-sts-1 webroot-tkb-sts-2
$ kubectl delete sc block
⚠ 别忘了卷

删除 StatefulSet 不会删除 PVC。删除 PVC 会（因为 reclaimPolicy: Delete）连带删除 PV 和云端存储；如果用的是你自己的 SC，请到存储后端确认外部卷确实被删了，否则会持续产生费用。

小结

  • StatefulSet 用于部署和管理有状态应用，提供 Deployment 没有的三项能力：可预测且持久的 Pod/DNS 名、持久的卷绑定、有序的启停。
  • Pod 名为 <sts 名>-<序号>，按序逐个创建，缩容从最高序号逆序进行；滚动更新也从最高序号开始。
  • volumeClaimTemplates 为每个 Pod 创建独立的 PVC；缩容不删 PVC，替换或扩回的 Pod 会接回原来的卷。
  • headless Service（clusterIP: None）作为 governing Service，为每个 Pod 注册 DNS 记录，实现对等发现。
  • 删除 StatefulSet 前先缩容到 0。
