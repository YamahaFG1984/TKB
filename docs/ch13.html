API 安全与 RBAC

Kubernetes 以 API 为中心，所有操作都要经过 API 服务器。这一章跟随一个典型的 API 请求， 看它如何依次通过认证（authN）、授权（authZ）和准入控制（admission control）三道关卡。 重点是 Kubernetes 最常用的授权模块——RBAC。

本章目标

  • 画出一个 API 请求经过的安全检查流程
  • 理解 Kubernetes 认证可插拔、没有内置用户数据库
  • 掌握 RBAC 的四个对象：Role、RoleBinding、ClusterRole、ClusterRoleBinding
  • 会写 rules：verbs、apiGroups、resources，以及它们与 HTTP 方法的对应
  • 拆解 Docker Desktop 如何让你成为集群管理员
  • 分清变更型（mutating）和验证型（validating）准入控制器

✈ 乘飞机的比喻

到机场后先出示护照证明身份（认证）；系统查你是否买了这趟航班的座位（授权）； 然后安检再执行航空公司的规定，比如限制手提行李、禁止携带酒和武器（准入控制）。全部通过后，你才能坐下起飞。

认证（authN）

认证就是证明你是谁，简写 authN（读作 “auth en”）。所有发往 API 服务器的请求都带有凭据，认证层负责验证它们，失败就返回 HTTP 401。

  • 认证层是可插拔的：客户端证书、webhook、对接 Active Directory、云 IAM 等都很常见；
  • Kubernetes 没有内置的用户数据库，它强制你使用外部系统，避免再造一个身份孤岛；
  • 开箱即用时大多数集群支持客户端证书，但生产环境应该对接云或企业的身份管理系统。很多托管服务会自动对接底层云的 IAM。

查看当前的认证配置

第 3 章讲过的 kubeconfig 文件就是认证凭据所在：

apiVersion: v1
kind: Config
clusters:                        # 定义一个或多个集群及其证书
- cluster:
    server: https://<API 服务器地址>:443          # 集群的 URL
    certificate-authority-data: LS0tLS1C...LS0tCg==   # 集群 CA 的公钥
  name: prod-shield              # 名为 prod-shield 的集群
users:                           # 定义一个或多个用户及凭据
- name: njfury                   # 名为 njfury 的用户
  user:
    as-user-extra: {}
    token: eyJhbGciOiJSUzI1NiIsImtpZCI6IlZwMzl...SZY3uUQ   # 用户的凭据
contexts:                        # context = 集群 + 用户
- context:
    cluster: prod-shield         # 发往这个集群
    user: njfury                 # 以这个用户身份认证
    namespace: default
  name: shield-admin
current-context: shield-admin    # kubectl 使用的 context

用户的令牌通常是由集群 CA（或集群信任的 CA）签发的 X.509 证书。集群的认证模块负责判断请求是否真的来自 njfury；如果对接了外部 IAM，就交给那个系统去判断。

授权（authZ）：RBAC

授权紧跟在认证之后，简写 authZ（读作 “auth zee”）。授权也是可插拔的，一个集群可以同时运行多个授权模块——只要任一模块批准，就跳过其余模块直接进入准入控制。 最常用的模块是 RBAC（Role-Based Access Control，基于角色的访问控制），它关乎三件事：

★ 默认拒绝，只有允许规则

RBAC 是最小权限、默认拒绝的系统：一切都先锁死，你需要创建「允许」规则来逐步打开。 Kubernetes 不支持拒绝规则，只支持允许规则——这看似小事，却让实现和排错简单得多。

Role 与 RoleBinding

Role 定义一组权限，RoleBinding 把它绑定给用户。只定义 Role 什么也不会发生，必须绑定才生效。

Role：定义权限
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: shield
  name: read-deployments
rules:
- verbs: ["get", "watch", "list"]  # 允许的动作
  apiGroups: ["apps"]              # ┐ 针对这类
  resources: ["deployments"]       # ┘ 资源
RoleBinding：授予用户
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-deployments
  namespace: shield
subjects:
- kind: User
  name: sky                  # 已认证用户的名字
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: read-deployments     # 把这个 Role 绑给上面的用户
  apiGroup: rbac.authorization.k8s.io

细看 rules

rules 由三个属性组成：verbs（允许的动作）、apiGroups 和 resources（动作作用于哪些对象）。

apiGroupresourceKubernetes API 路径
""pods/api/v1/namespaces/{namespace}/pods
""secrets/api/v1/namespaces/{namespace}/secrets
"storage.k8s.io"storageclass/apis/storage.k8s.io/v1/storageclasses
"apps"deployments/apis/apps/v1/namespaces/{namespace}/deployments

空字符串 "" 表示核心 API 组，其他组要写成带双引号的字符串。Kubernetes 的动词和 HTTP 方法一一对应，体现了 API 的 REST 本质：

Kubernetes 动词HTTP 方法常见响应
createPOST201 Created，403 Access Denied
get、list、watchGET200 OK，403 Access Denied
updatePUT200 OK，403 Access Denied
patchPATCH200 OK，403 Access Denied
deleteDELETE200 OK，403 Access Denied
$ kubectl api-resources --sort-by name -o wide
NAME          APIGROUP   KIND         VERBS
deployments   apps       Deployment   [create delete ... get list patch update watch]
pods                     Pod          [create delete ... get list patch update watch]
secrets                  Secret       [create delete ... get list patch update watch]
services                 Service      [create delete get list patch update watch]

星号 * 代表全部。下面这个 Role 允许对所有 API 组的所有资源做所有动作——仅作演示，别这么写：

rules:
- verbs: ["*"]         # 所有动作
  resources: ["*"]     # 所有资源
  apiGroups: ["*"]     # 所有 API 组

集群级：ClusterRole 与 ClusterRoleBinding

定义权限授予权限
命名空间级RoleRoleBinding
集群级（作用于所有 Namespace）ClusterRoleClusterRoleBinding

它们在同一个 API 子组里，YAML 结构几乎一样。一个很强大的模式是：用 ClusterRole 在集群级定义一次角色，再用多个 RoleBinding 把它绑到具体的 Namespace。

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole              # 集群级角色
metadata:
  name: read-deployments       # 注意：没有 metadata.namespace
rules:
- verbs: ["get", "watch", "list"]
  apiGroups: ["apps"]
  resources: ["deployments"]

真实案例：Docker Desktop 如何让你成为管理员

大多数集群都预建了一些角色和绑定。下面以 Docker Desktop 多节点集群为例，拆解它如何通过 ClusterRole 和 ClusterRoleBinding 给你集群管理员权限（其他集群做法略有不同，但原理类似）。

$ kubectl config view
users:
- name: docker-desktop                       # 只是个友好名字
  user:
    client-certificate-data: DATA+OMITTED    # 真正的用户名藏在这个证书里
    client-key-data: DATA+OMITTED

用下面这串命令把证书里的用户名和组解出来（需要类 Linux 系统和 jq，并确保当前 context 是 Docker Desktop）：

$ kubectl config view --raw -o json \
  | jq ".users[] | select(.name==\"docker-desktop\")" \
  | jq -r '.user["client-certificate-data"]' \
  | base64 -d | openssl x509 -text | grep "Subject:"
        Subject: O=kubeadm:cluster-admins, CN=kubernetes-admin
ⓘ 客户端证书怎么编码身份

用户名放在 CN（Common Name），所属组放在 O（Organization）。证书由集群 CA 签发，所以一定能通过认证。

$ kubectl describe clusterrole cluster-admin

$ kubectl get clusterrolebindings | grep cluster-admin

准入控制

准入控制在认证和授权都成功之后立即运行，它关乎策略。Kubernetes 支持两类准入控制器：

$ kubectl describe pod kube-apiserver-desktop-control-plane \
  --namespace kube-system | grep admission
      --enable-admission-plugins=NodeRestriction

Docker Desktop 集群只启用了 NodeRestriction。真实的生产集群会运行多得多的准入控制器，例如 AlwaysPullImages（变更型）会把所有新 Pod 的 spec.containers.imagePullPolicy 设为 Always，强制每个节点都从镜像仓库拉取镜像、不使用本地缓存——这要求所有节点都有拉取镜像的有效凭据。

小结

  • 所有发往 API 服务器的请求都带有凭据，并且必须依次通过认证、授权、准入控制；客户端与 API 服务器之间用 TLS 加密。
  • 认证层验证身份，可插拔；大多数集群支持客户端证书，但生产环境应使用企业级 IAM。Kubernetes 没有内置用户库。
  • 授权层检查已认证的请求是否有权执行操作，最常用的是 RBAC：默认拒绝、只有允许规则，由 Role / RoleBinding / ClusterRole / ClusterRoleBinding 四个对象组成。
  • 准入控制在授权之后执行策略：验证型不合规就拒绝，变更型可以修改请求使其合规。

动手练习

  1. 用 kubectl auth can-i create deployments -n shield 和 kubectl auth can-i '*' '*' 看看你当前的身份有哪些权限。
  2. 创建 shield Namespace，部署本章的 read-deployments Role 和 RoleBinding，然后用 kubectl auth can-i list deployments -n shield --as sky 验证 sky 的权限；再试试 delete。
  3. 运行 kubectl get clusterroles，找到 view、edit、admin 这几个内置 ClusterRole，用 kubectl describe 比较它们的区别。
