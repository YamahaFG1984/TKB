第 15 章

用 STRIDE 给 Kubernetes 做威胁建模

安全比以往任何时候都重要。在动手加固之前，先系统地想一想：攻击者可能从哪里下手？ 威胁建模就是识别薄弱环节、从而采取预防和缓解措施的过程。这一章用流行的 STRIDE 模型逐一审视 Kubernetes。

本章目标

  • 说出 STRIDE 六类威胁分别是什么
  • 对每类威胁，知道 Kubernetes 中有哪些对应的防护手段
  • 掌握 Pod 的 securityContext 常用安全设置
  • 用 Pod Security Standards（PSS）和 Pod Security Admission（PSA）统一执行 Pod 安全策略

STRIDE 模型

STRIDE 提供了一种结构化的评估方式，但没有哪个模型能保证覆盖所有威胁。本章不求面面俱到，而是给你思路、带你上路。

S · 仿冒（Spoofing）

仿冒就是假装成别人，以获得额外的权限。

保护与 API 服务器的通信

Kubernetes 由很多小组件组成：API 服务器、控制器管理器、调度器、集群存储，以及节点上的 kubelet 和容器运行时。每个都有自己的权限，仿冒其中任何一个都可能出问题。 Kubernetes 要求所有组件通过加密签名的证书相互认证（mTLS），并会自动轮换证书。但要注意：

  1. 典型安装会自动生成一个自签名 CA 给所有组件签发证书。有总比没有强，但单靠它不足以应对生产环境；
  2. mTLS 的安全性取决于签发证书的 CA。CA 一旦被攻破，整个 mTLS 层就形同虚设，务必保护好 CA！

保护 Pod 之间的通信

除了仿冒集群访问，还可能出现一个 Pod 仿冒另一个 Pod。每个 Pod 都关联一个 ServiceAccount 作为身份，ServiceAccount 令牌会以 Secret 的形式自动挂载进每个 Pod。注意两点： ① 这个令牌可以访问 API 服务器；② 大多数 Pod 根本不需要访问 API 服务器。所以对不需要的 Pod，关掉自动挂载： 

apiVersion: v1
kind: Pod
metadata:
  name: service-account-example-pod
spec:
  serviceAccountName: some-service-account
  automountServiceAccountToken: false      # ← 就是这一行

确实需要访问 API 服务器的 Pod，可以用投射卷（projected volume）给令牌设置过期时间和受众，限制它的有效期和可用范围：

apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  containers:
  - image: nginx
    name: nginx
    volumeMounts:
    - mountPath: /var/run/secrets/tokens
      name: vault-token
  serviceAccountName: my-pod
  volumes:
  - name: vault-token
    projected:
      sources:
      - serviceAccountToken:
          path: vault-token
          expirationSeconds: 3600     # ← 1 小时后过期
          audience: vault             # ← 只对 vault 有效

T · 篡改（Tampering）

篡改是以恶意方式修改某样东西，从而造成拒绝服务（让资源不可用）或权限提升（获得额外权限）。 篡改往往很难完全避免，所以常见对策是让篡改变得显而易见——就像非处方药包装上的防拆封条。

可能被篡改的 Kubernetes 组件：etcd；API 服务器、控制器管理器、调度器、etcd、kubelet 的配置文件；容器运行时二进制；容器镜像；Kubernetes 二进制。

例如，用 Linux 审计守护进程监控对 docker 二进制的访问及属性修改：

$ auditctl -w /usr/bin/docker -p wxa -k audit-docker

防止篡改运行中的应用

把 Pod 的文件系统设为只读，可以保证文件系统不可变：

apiVersion: v1
kind: Pod
metadata:
  name: readonly-test
spec:
  securityContext:
    readOnlyRootFilesystem: true   # 只读的根文件系统
    allowedHostPaths:              # 让这个挂载点
    - pathPrefix: "/test"          # 下面的一切
      readOnly: true               # 都是只读的

R · 抵赖（Repudiation）

抵赖是制造怀疑；不可抵赖（non-repudiation）则是提供证据——在信息安全里，就是证明某人确实做了某事。不可抵赖要能证明：

发生了什么

What

何时发生

When

谁干的

Who

在哪里

Where

为什么

Why —— 最难，通常要关联一段时间内的多个事件

怎么做到的

How —— 同样困难

审计 API 服务器事件能帮你回答这些问题（可能需要先在 API 服务器上启用审计）：

{
  "kind": "Event",
  "apiVersion": "audit.k8s.io/v1",
  "level": "Metadata",
  "timestamp": "2022-11-11T10:10:00Z",
  "auditID": "7e0cbccf-8d8a-4f5f-aefb-60b8af2d2ad5",
  "stage": "RequestReceived",
  "requestURI": "/api/v1/namespaces/default/persistentvolumeclaims",
  "verb": "list",
  "user": {
    "username": "fname.lname@example.com",
    "groups": [ "system:authenticated" ]
  },
  "sourceIPs": [ "123.45.67.123" ],
  "objectRef": {
    "resource": "persistentvolumeclaims",
    "namespace": "default",
    "apiVersion": "v1"
  }
}

前面启用了对 docker 二进制的审计后，执行 docker run 会产生类似这样的事件，和 Kubernetes 的审计关联起来，就构成了无法抵赖的完整证据链：

type=SYSCALL msg=audit(1234567890.123:12345): arch=abc123 syscall=59 success=yes \
  exit=0 ... uid=0 gid=0 euid=0 ... comm="docker" exe="/usr/bin/docker" \
  key="audit-docker" type=CWD msg=audit(1234567890.123:12345): cwd="/home/firstname" \
type=PATH msg=audit(1234567890.123:12345): item=0 name="/usr/bin/docker" ...

I · 信息泄露（Information Disclosure）

信息泄露指敏感数据外流，常见的有数据存储被攻破、API 无意中暴露敏感数据。

保护集群数据

集群的全部配置都在集群存储（etcd）里：网络和存储配置、密码、集群 CA……这让它成为信息泄露攻击的首要目标。至少应该限制并审计对 etcd 所在节点的访问。

Kubernetes 1.7 引入了 Secret 加密，但默认不开启；而且即使开启，数据加密密钥（DEK）和 Secret 存在同一节点上，拿到节点就能绕过加密。 1.11 引入了 KMS v1（beta），允许把密钥加密密钥（KEK）存在集群之外，这叫信封加密（envelope encryption）。 之后 KMS 被彻底重新设计为 KMS v2，自 v1.29 起 GA：

  • 每次写操作生成新的 DEK，并用 KEK 加密后静态存储；
  • 插件缓存大小只受控制平面节点资源限制，旧 DEK 可缓存在内存中加快加解密；
  • 密钥轮换后重新加密 Secret 不需要 API 服务器停机或重启 Pod；
  • KMS 插件运行在控制平面节点上，通过 Unix socket 与 API 服务器通信，再连接外部 KMS 提供方处理 DEK 的加解密。

建议把 KEK 存放在硬件安全模块（HSM）或云 KMS 中；同时遵循「信任但要验证」，确认加密真的在工作，并为 KEK 丢失或与外部 KMS 断连做好预案。

保护 Pod 里的数据

Secret 是存放和共享密码等敏感数据的首选方式。例如前端容器访问加密的后端数据库时，把解密密钥以 Secret 挂载进去，远比放在明文文件或环境变量里好。 数据和配置也常存放在 PV 和 ConfigMap 中，如果它们是加密的，解密密钥应放在 Secret 里——但别忘了上一节关于 Secret 加密密钥存放位置的告诫：不要辛辛苦苦锁好门，却把钥匙插在门上。

D · 拒绝服务（Denial of Service）

DoS 就是让东西不可用，最常见的是把系统压垮到无法响应。在 Kubernetes 中，压垮 API 服务器会让整个集群的运作陷入停顿（连内部组件都靠它通信）。

保护集群资源

  • 生产环境运行多个控制平面节点（HA），并跨可用区分布——攻击者需要同时攻击多个节点或可用区才有效果；工作节点同理。
  • 为内存、CPU、存储配置合理的限制，防止关键系统资源被耗尽。
  • 限制 Namespace 中对象的数量（ReplicaSet、Pod、Service、Secret、ConfigMap……）：
apiVersion: v1
kind: ResourceQuota
metadata:
  name: pod-quota
  namespace: skippy
spec:
  hard:
    pods: "100"          # skippy 里最多 100 个 Pod
💡 podPidsLimit：防 fork 炸弹

fork 炸弹指恶意进程不断创建子进程直到耗尽系统资源。podPidsLimit 限制一个 Pod 能创建的进程数，把攻击影响限制在这个 Pod 内， 也防止单个 Pod 用光节点的 PID 范围（包括 kubelet 的）。Pod 耗尽限额时 Kubernetes 通常会重启它。设置合适的值需要大致估计每个节点会同时运行多少 Pod。

保护 API 服务器

API 服务器通过 TCP 暴露 REST 接口，是僵尸网络 DoS 攻击的目标。对策：高可用控制平面（多副本、多节点、多可用区）；基于合理阈值监控和告警 API 请求；用防火墙等手段限制它在互联网上的暴露。攻击者也可能仿冒用户或控制平面服务来制造过载，所以即使有健全的 RBAC，也必须严格保护高权限账号。

保护集群存储（etcd）

  • 配置 3 或 5 个节点的高可用 etcd 集群；
  • 监控 etcd 请求并告警（从监控 etcd 日志开始）；
  • 在网络层隔离 etcd，只允许控制平面成员访问；
  • 大型生产集群应考虑独立的 etcd 集群：etcd 是大集群最常见的性能瓶颈，性能差的 etcd 和遭受持续 DoS 的 etcd 一样糟糕；独立部署还能防止被控制平面其他被攻破的部分波及。

E · 权限提升（Elevation of Privilege）

权限提升是获得超出授予范围的访问权，目的是造成破坏或未授权访问。

保护 API 服务器：多种授权模式

模式说明
RBAC把 API 操作限制给特定用户或系统服务（见第 13 章）。例如 Mia 能创建 Pod 吗？
Webhook把授权交给外部基于 REST 的策略引擎。要额外构建和维护，而且外部引擎会成为每个请求的单点故障——它挂了，你可能完全无法访问 API 服务器
Node专门授权 kubelet（节点）发出的 API 请求

应同时运行多个授权器，常见组合是 RBAC + Node。

保护 Pod

不要以 root 运行

root（UID 0）是 Linux 上最强大的用户。以 root 运行应用进程几乎总是坏主意——它对容器拥有完全访问权，更糟的是，容器里的 root 有时对宿主机也有不受限的 root 权限。 Kubernetes 可以强制容器以非特权用户运行： 

apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  securityContext:          # 作用于 Pod 里所有容器
    runAsUser: 1000         # 非 root 用户
  containers:
  - name: demo
    image: example.io/simple:1.0
    securityContext:
      runAsUser: 2000       # 容器级设置覆盖 Pod 级

runAsUser 属于 PodSecurityContext（spec.securityContext）。如果多个不同的 Pod 用了相同的 UID，它们就有相同的安全上下文， 可能读写同一个卷导致数据损坏，或让被攻破的容器篡改本不该碰的数据。可以在容器级覆盖 UID，或者使用用户命名空间（user namespaces）： 进程在容器内是 root（UID 0），映射到宿主机上却是 UID 1000——适合确实需要在容器内以 root 运行的进程，但要确认你的 Kubernetes 版本和运行时完全支持。也可以维护一张 UID 使用映射表。

丢弃 capabilities

大多数应用不需要完整的 root 能力，但又比普通用户需要的多。很多运行时提供了一套合理的默认 capabilities，但通常不足以用于生产。 找出最小集合的常见方法：在测试环境里丢弃全部 capabilities运行应用，根据报错日志找出缺少的权限，映射成 capabilities 加回去，反复直到应用正常运行。 注意要充分测试（生产中遇到没测到的边缘情况会导致崩溃），而且每个新版本都要重新测试。 

apiVersion: v1
kind: Pod
metadata:
  name: capability-test
spec:
  containers:
  - name: demo
    image: example.io/simple:1.0
    securityContext:
      capabilities:
        add: ["NET_ADMIN", "CHOWN"]

过滤系统调用：seccomp

seccomp（secure computing）概念上和 capabilities 类似，但过滤的是系统调用——应用请求 Linux 内核执行操作的方式。它在 Kubernetes 1.19 GA，有四种配置文件：

配置文件行为用途
Non-blocking允许运行，但把每个 syscall 记录到审计日志在测试环境收集应用需要的 syscall，用来制作自定义配置
Blocking阻止所有 syscall极其安全，但 Pod 什么也干不了
Runtime Default使用容器运行时自带的配置好的起点：在可用和安全之间取得平衡，并经过充分测试
Custom只允许应用需要的 syscall，其余全部阻止最小权限，安全角度的首选；风险是测试漏掉的边缘情况会在生产中失败

强制访问控制：AppArmor 与 SELinux

这是仅限 Linux 的技术，在节点级配置，再通过 Pod 的安全上下文应用到 Pod。它们控制进程如何与其他系统资源交互，配置较难（有工具可以读取审计日志生成配置文件）。 与 seccomp 和 capabilities 的「自愿」不同，它们一旦启用就是强制的。有些运行时会给所有容器应用默认的 SELinux 配置。配错会让应用无法工作，务必充分测试。

防止容器提权

Linux 中创建新进程的唯一方式是一个进程克隆自己（父进程 → 子进程）。默认情况下，Linux 允许子进程获得比父进程更多的权限，这通常是坏事—— 容器的安全配置是针对初始配置定义的，而不是针对可能被提升后的权限。用 allowPrivilegeEscalation 禁止它： 

apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  containers:
  - name: demo
    image: example.io/simple:1.0
    securityContext:
      allowPrivilegeEscalation: false    # ← 就是这一行

用 PSS 与 PSA 统一 Pod 安全

  • Pod Security Standards（PSS）：规定 Pod 必须满足哪些安全设置的策略；
  • Pod Security Admission（PSA）：在创建 Pod 时执行这些策略。

你选择要应用哪些 PSS 策略，由 PSA 负责执行。

★ 推荐的推进路线
  1. 给每个 Namespace 至少配上 baseline 策略的 warn 或 audit，开始收集哪些 Pod 不合规、为什么；
  2. 然后 enforce baseline，同时对 restricted 开启 warn 和 audit；
  3. 没有任何 Pod 安全配置的 Namespace 就是安全缺口，哪怕只是 warn 和 audit，也要尽快补上。

动手：PSA 实验

命令在仓库的 psa 目录下执行。先创建 Namespace 并强制执行 baseline 策略：

$ kubectl create ns psa-test

$ kubectl label --overwrite ns psa-test \
  pod-security.kubernetes.io/enforce=baseline

$ kubectl describe ns psa-test
Name:         psa-test
Labels:       kubernetes.io/metadata.name=psa-test
              pod-security.kubernetes.io/enforce=baseline    # 标签已正确应用
Status:       Active

apiVersion: v1
kind: Pod
metadata:
  name: psa-pod
  namespace: psa-test        # 部署到新的 psa-test Namespace
spec:
  containers:
  - name: psa-ctr
    image: nginx
    securityContext:
      privileged: true       # 违反 baseline 策略

$ kubectl apply -f psa-pod.yml
Error from server (Forbidden): error when creating "psa-pod.yml": pods "psa-pod" is
forbidden: violates PodSecurity "baseline:latest": privileged (container "psa-ctr"
must not set securityContext.privileged=true)

把 privileged 改成 false 再部署，就能通过 baseline：

$ kubectl apply -f psa-pod.yml
pod/psa-pod created

用 --dry-run=server 预演切换到 restricted 的影响（不会真的应用）：

$ kubectl label --dry-run=server --overwrite ns psa-test \
  pod-security.kubernetes.io/enforce=restricted
Warning: existing pods in namespace "psa-test" violate the new PodSecurity enforce
level "restricted:latest"
Warning: psa-pod: allowPrivilegeEscalation != false, unrestricted capabilities,
runAsNonRoot != true, seccompProfile

psa-pod 有四项不满足 restricted：allowPrivilegeEscalation 没设为 false；capabilities 不受限；runAsNonRoot 没设为 true；没有通过 seccompProfile 检查。真的应用后看看已在运行的 Pod：

$ kubectl label --overwrite ns psa-test \
  pod-security.kubernetes.io/enforce=restricted
Warning: existing pods in namespace "psa-test" violate the new PodSecurity enforce level
"restricted:latest"
namespace/psa-test labeled

$ kubectl get pods --namespace psa-test
NAME      READY   STATUS    RESTARTS   AGE
psa-pod   1/1     Running   0          3m9s
ⓘ 已有 Pod 不受影响

PSA 是验证型准入控制器，只作用于 Pod 的创建和修改，不能修改 Pod，也不会终止已经在运行的 Pod。

一个 Namespace 可以同时配置多个策略和模式，这也是常见做法——强制 baseline，同时对 restricted 做警告和审计，为升级做准备：

$ kubectl label --overwrite ns psa-test \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

PSA 的替代方案

PSS 和 PSA 有局限：只是验证型准入控制器，不能修改、导入或自建策略。需要更多能力时，可以考虑第三方方案：OPA Gatekeeper、Kubewarden、Kyverno 等。

清理

$ kubectl delete ns psa-test
namespace "psa-test" deleted

小结

  • STRIDE 把威胁分为仿冒、篡改、抵赖、信息泄露、拒绝服务、权限提升六类，是给 Kubernetes 做威胁建模的结构化方法。
  • 一种威胁常常引出另一种，而一种威胁也有多种缓解手段——纵深防御是关键策略。
  • Pod 安全的常用手段：非 root、丢弃 capabilities、seccomp、AppArmor/SELinux、禁止提权、只读文件系统。
  • Pod Security Admission 是实施 Pod 安全默认值的首选方式。

动手练习

  1. 挑一个你正在运行的应用，按 STRIDE 六类各写出一条它可能面临的威胁和一条缓解措施。
  2. 修改 psa-pod.yml，补全 restricted 要求的四项设置（allowPrivilegeEscalation: false、capabilities.drop: ["ALL"]、runAsNonRoot: true、seccompProfile.type: RuntimeDefault），让它能在 enforce=restricted 的 Namespace 里成功创建。（提示：nginx 官方镜像默认以 root 运行，可以换成 nginxinc/nginx-unprivileged。）
  3. 运行 kubectl get ns --show-labels，检查你集群里哪些 Namespace 还没有任何 pod-security 标签。
