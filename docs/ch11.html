第 11 章

ConfigMap 与 Secret：把配置从镜像里拿出来

大多数业务应用由两部分组成：应用本身和配置。NGINX、Apache 这类 Web 服务器不加配置几乎没用。 过去我们把应用和配置打包在一起，但这是一个反模式（看起来是好主意、实际是坏主意）。 这一章讲 Kubernetes 如何用 ConfigMap 和 Secret 把二者解耦，并在运行时再组合起来。

本章目标

  • 理解应用与配置解耦的好处：复用、更易开发测试、变更更简单、干扰更小
  • 掌握 ConfigMap 的结构，以及命令式 / 声明式两种创建方式
  • 掌握三种注入方式：环境变量、启动命令参数、卷，知道哪种能接收更新
  • 理解 Secret 的真实安全性：base64 不是加密
  • 用 Secret 卷把敏感数据挂载进容器

为什么要解耦

假设公司有开发（dev）、测试（test）、生产（prod）三套环境，每套都有自己的网络、安全策略、凭据和证书。

ConfigMap 的原理

ConfigMap（CM）是一种 API 资源，用于在 Pod 之外保存配置数据，并在运行时注入进去。它是核心 API 组里的 v1 一等对象，这说明： 它很稳定、存在已久、可以用 YAML 定义部署、可以用 kubectl 管理。

✓ 适合放进 ConfigMap
  • 环境变量
  • Web 服务器、数据库的配置文件
  • 主机名、Service 名与端口
  • 账户名
✗ 不要放进 ConfigMap
  • 证书
  • 密码
  • 任何敏感数据

Kubernetes 完全不保护 ConfigMap 的内容。敏感数据用 Secret，并纳入完整的密钥管理方案。

ConfigMap 就是一张键值表

  • 键：任意名字，可含字母数字、短横线、点和下划线；
  • 值：可以是任何东西，包括带多行和换行的完整配置文件；
  • 大小上限 1MiB（1,048,576 字节）。
三个简单条目
kind: ConfigMap
apiVersion: v1
metadata:
  name: epl
data:                        # 3 个键值对
  Competition: Premier League
  Season: 2024-2025
  Champions: Liverpool
值是一个完整的配置文件
kind: ConfigMap
apiVersion: v1
metadata:
  name: cm2
data:
  test.conf: |               # 键
    env = plex-test          # ┐
    endpoint = 0.0.0.0:31001 # │ 值
    char = utf8              # │
    vault = PLEX/test        # │
    log-size = 512M          # ┘

三种注入方式

🔮 Kubernetes 原生应用

知道自己跑在 Kubernetes 上、能直接和 API 服务器对话的应用，可以直接通过 API 读取 ConfigMap，还能实时看到更新。 但这样的应用只能在 Kubernetes 上跑，会造成锁定。本章示例都用环境变量和卷，让现有应用无需改写就能使用。

动手：创建 ConfigMap

以下命令在仓库的 configmaps 目录执行。configmap 可简写为 cm。

命令式

kubectl create configmap 接受两种数据来源：命令行字面量（--from-literal）和文件（--from-file）。

$ kubectl create configmap testmap1 \
  --from-literal shortname=SAFC \
  --from-literal longname="Sunderland Association Football Club"

$ kubectl describe cm testmap1
Name:         testmap1
Namespace:    default
Data
====
shortname:
----
SAFC
longname:
----
Sunderland Association Football Club

$ kubectl create cm testmap2 --from-file cmfile.txt
configmap/testmap2 created

$ kubectl describe cm testmap2
Data
====
cmfile.txt:          # ← 键 = 文件名
----
Kubernetes FTW!      # ← 值 = 文件内容

$ kubectl get cm testmap2 -o yaml
apiVersion: v1
data:
  cmfile.txt: |
    Kubernetes FTW!
kind: ConfigMap
metadata:
  name: testmap2
  namespace: default
★ 没有 spec 和 status

ConfigMap 没有「期望状态 vs 观测状态」的概念，所以没有 spec 和 status，取而代之的是 data。它只是一个打扮成 Kubernetes 对象的键值表。

声明式

fullname.yml：两个条目
kind: ConfigMap
apiVersion: v1
metadata:
  name: multimap
data:
  firstname: Nigel
  lastname: Poulton
singlemap.yml：一个条目，值是整个文件
kind: ConfigMap
apiVersion: v1
metadata:
  name: test-config
data:
  test.conf: |
    env = plex-test
    endpoint = 0.0.0.0:31001
    char = utf8
    vault = PLEX/test
    log-size = 512M

键后面的竖线 | 告诉 Kubernetes：把后面缩进的所有内容当成一个值。

$ kubectl apply -f fullname.yml
configmap/multimap created
$ kubectl apply -f singlemap.yml
configmap/test-config created

注入方式 ①：环境变量

apiVersion: v1
kind: Pod
metadata:
  labels:
    chapter: configmaps
  name: envpod
spec:
  containers:
    - name: ctr1
      image: busybox
      command: ["sleep"]
      args: ["infinity"]
      env:
        - name: FIRSTNAME            # 名为 FIRSTNAME 的环境变量
          valueFrom:                 # 取值来自
            configMapKeyRef:         # 一个 ConfigMap
              name: multimap         # 名叫 multimap
              key: firstname         # 中 firstname 字段的值
        - name: LASTNAME
          valueFrom:
            configMapKeyRef:
              name: multimap
              key: lastname

环境变量名用大写只是为了和 ConfigMap 里的键区分开，实际可以随便起。

$ kubectl apply -f podenv.yml
pod/envpod created

$ kubectl exec envpod -- env | grep NAME
HOSTNAME=envpod
FIRSTNAME=Nigel
LASTNAME=Poulton

Windows 用户把 grep NAME 换成 Select-String -Pattern 'NAME'。

注入方式 ②：启动命令参数

在 Pod 模板里写好容器的启动命令，把环境变量当参数传进去：

apiVersion: v1
kind: Pod
metadata:
  name: startup-pod
  labels:
    chapter: configmaps
spec:
  restartPolicy: OnFailure
  containers:
    - name: args1
      image: busybox
      command: [ "/bin/sh", "-c", "echo First name $(FIRSTNAME) last name $(LASTNAME)", "wait" ]
      env:                           # 和上例相同的环境变量映射，
        - name: FIRSTNAME            # 只是这次被上面的启动命令引用
          valueFrom:
            configMapKeyRef:
              name: multimap
              key: firstname
        - name: LASTNAME
          valueFrom:
            configMapKeyRef:
              name: multimap
              key: lastname

$ kubectl apply -f podstartup.yml
pod/startup-pod created

$ kubectl logs startup-pod -c args1
First name Nigel last name Poulton

$ kubectl describe pod startup-pod
...
    Environment:
      FIRSTNAME:  <set to the key 'firstname' of config map 'multimap'>  Optional: false
      LASTNAME:   <set to the key 'lastname' of config map 'multimap'>   Optional: false

$ kubectl delete pod startup-pod     # 它打印完就结束了（Completed）

这种方式本质上还是环境变量，所以有同样的局限：ConfigMap 的更新不会推送到已有的变量。

注入方式 ③：卷（推荐）

卷是最灵活的方式：可以引用完整的配置文件，而且能收到更新（可能要等一两分钟才出现在容器里）。步骤：

  1. 创建 ConfigMap
  2. 在 Pod 模板里定义一个 ConfigMap 卷
  3. 把这个卷挂载进容器
  4. ConfigMap 的每个条目都会以文件形式出现在容器里
apiVersion: v1
kind: Pod
metadata:
  name: cmvol
spec:
  volumes:
    - name: volmap             # 创建名为 volmap 的卷
      configMap:               # 基于 ConfigMap
        name: multimap         # 名叫 multimap
  containers:
    - name: ctr
      image: nginx
      volumeMounts:
        - name: volmap         # 把 volmap 卷
          mountPath: /etc/name # 挂载到容器的 /etc/name

$ kubectl apply -f podvol.yml
pod/cmvol created

$ kubectl exec cmvol -- ls /etc/name
firstname
lastname

现在证明更新会推送到运行中的容器。用 kubectl edit cm multimap 修改 data 块（不习惯 vi 的话，也可以改 YAML 文件再 kubectl apply）：

apiVersion: v1
data:
  City: Macclesfield      # 改了
  Country: UK             # 改了
kind: ConfigMap

# 等一分钟左右
$ kubectl exec cmvol -- ls /etc/name
City
Country

$ kubectl exec cmvol -- cat /etc/name/Country
UK
方式能用完整配置文件吗运行中能收到更新吗
环境变量不方便✗
启动命令参数不方便✗
卷✓✓（有一两分钟延迟）

Secret

Secret 和 ConfigMap 的用法一样：保存配置数据，运行时注入容器。区别在于它设计用来存放敏感数据——密码、证书、OAuth 令牌——并作为更完整的密钥管理方案的一部分。

Kubernetes Secret 安全吗？

简短的回答是：不安全。稍长的回答是：一个安全的密钥管理系统远不止 Secret 对象本身，你需要考虑：

🗃

静态加密

在集群存储（etcd）里加密存放。

📡

传输加密

在网络上传输时加密。

📦

节点/容器内保护

在节点、Pod、容器中呈现时的保护。

🔑

最小权限 RBAC

控制谁能通过 API 访问 Secret。

🔒

etcd 节点访问

限制对控制平面和 etcd 节点的访问。

⚠

特权容器

防止特权容器读取 Secret。

📁

代码仓库

防止通过 GitHub 等代码仓库泄露。

🗑

安全删除

不再使用时安全地删除。

大多数新集群一样都没做：Secret 在 etcd 里明文存储、在网络上明文传输、以明文挂载进容器！ 不过你可以配置 EncryptionConfiguration 对象来做静态加密，部署服务网格加密所有网络流量，配置严格的 RBAC 等等。 在真实环境中，很多生产集群用服务网格保护网络流量，并把密钥存放在 Kubernetes 之外的第三方保险库（如 HashiCorp Vault 或云厂商的类似服务）里；Kubernetes 甚至有原生的 Secrets Store CSI Driver 来对接外部保险库。

只用 Kubernetes Secret 时的典型流程

一个典型用例是 TLS 终止代理：同一个镜像，在三个环境里分别加载三个不同的 Secret（各环境自己的 TLS 证书）。

动手：创建和使用 Secret

$ kubectl create secret generic creds \
  --from-literal user=nigelpoulton \
  --from-literal pwd=Password123

$ kubectl get secret creds -o yaml
apiVersion: v1
kind: Secret
data:
  pwd: UGFzc3dvcmQxMjM=
  user: bmlnZWxwb3VsdG9u

$ echo UGFzc3dvcmQxMjM= | base64 -d
Password123

声明式创建（把 data 改成 stringData 就可以直接写明文条目，但同样不能放到 GitHub 上）：

apiVersion: v1
kind: Secret
metadata:
  name: tkb-secret
  labels:
    chapter: configmaps
type: Opaque
data:                          # 改成 stringData 可写明文
  username: bmlnZWxwb3VsdG9u
  password: UGFzc3dvcmQxMjM=

$ kubectl apply -f tkb-secret.yml
secret/tkb-secret created

在 Pod 中通过卷使用 Secret

Secret 同样支持环境变量、命令参数和卷三种方式，最灵活的依然是卷：

apiVersion: v1
kind: Pod
metadata:
  name: secret-pod
  labels:
    topic: secrets
spec:
  volumes:
  - name: secret-vol             # 卷名
    secret:                      # 卷类型
      secretName: tkb-secret     # 用这个 Secret 填充卷
  containers:
  - name: secret-ctr
    image: nginx
    volumeMounts:
    - name: secret-vol           # 挂载上面定义的卷
      mountPath: "/etc/tkb"      # 到这个路径
      readOnly: true

$ kubectl apply -f secretpod.yml
pod/secret-pod created

$ kubectl exec secret-pod -- ls /etc/tkb
password
username

$ kubectl exec secret-pod -- cat /etc/tkb/password
Password123

部署 Pod 时，Kubernetes 把未加密的 Secret 通过网络发给节点上的 kubelet，运行时再用 tmpfs 挂载进容器。Secret 卷会被自动以只读方式挂载，防止应用意外修改。 文件内容是明文，方便应用直接使用。因为用的是卷，更新 Secret 后应用也能看到。

清理

$ kubectl get cm
NAME               DATA   AGE
kube-root-ca.crt   1      71m      # ← 系统的，不要删
multimap           2      19m
test-config        1      17m
testmap1           2      24m
testmap2           1      22m

$ kubectl delete pods cmvol envpod secret-pod
$ kubectl delete cm multimap test-config testmap1 testmap2
$ kubectl delete secrets creds tkb-secret

小结

  • ConfigMap 和 Secret 用于把应用和配置数据解耦，都是 API 一等对象，可以命令式或声明式创建，用 kubectl 查看。
  • ConfigMap 存放应用配置参数甚至整个配置文件；Secret 存放敏感数据，应作为更完整密钥管理方案的一部分。
  • 两者都可以通过环境变量、启动命令、卷注入容器；卷是首选，因为它会把变更推送到运行中的容器。
  • Kubernetes 默认不会加密 etcd 中的 Secret，也不会加密传输中的 Secret；base64 只是编码。

动手练习

  1. 用 kubectl create cm nginx-conf --from-file=default.conf 把一个 NGINX 配置文件做成 ConfigMap，挂载到 nginx 容器的 /etc/nginx/conf.d，让它返回一段自定义文本。
  2. 修改 multimap 后，对比 envpod（环境变量）和 cmvol（卷）里看到的值有什么不同。
  3. 用 stringData 重写 tkb-secret.yml，apply 后再 kubectl get secret -o yaml，看看存进去的是什么形式。
