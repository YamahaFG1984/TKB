第 14 章

Kubernetes API

想精通 Kubernetes，就得理解它的 API。它庞大而复杂，如果你对 API、RESTful 这些词不熟，很容易被绕晕。 这一章用一个网购的比喻打底，再亲手用 curl 直接和 API 服务器对话，最后创建一个属于你自己的 API 资源。

本章目标

  • 理解「以 API 为中心」的含义，以及序列化（JSON / Protobuf）
  • 理解 RESTful、CRUD、动词与 HTTP 方法的对应
  • 用 kubectl proxy + curl 直接调用 API
  • 分清核心 API 组（/api/v1）和命名 API 组（/apis/<group>/<version>）
  • 理解 alpha → beta → GA 的演进和弃用策略
  • 用 CRD 扩展 API
ⓘ 资源还是对象？

Pod、Service、StatefulSet、StorageClass 等都是 API 里的资源（resource），部署到集群后常被称为对象（object）。本章两个词混用。

以 API 为中心

Kubernetes 以 API 为中心：所有资源都定义在 API 里，所有配置和查询都通过 API 服务器。管理员和客户端可以用 kubectl、自己写的代码或 API 测试工具发请求， 但无论怎么发，请求都会到达 API 服务器，经过认证和授权后才被接受。如果是创建请求，Kubernetes 会把对象定义以序列化的形式持久化到集群存储，然后调度到集群上。

JSON 序列化

序列化就是把对象转换成字符串或字节流，以便通过网络发送或持久化到数据存储；反过来叫反序列化。 Kubernetes 把 Pod、Service 这些对象序列化成 JSON 字符串，通过 HTTP 传输：kubectl 提交对象时序列化，API 服务器返回响应时也序列化。存入集群存储时同样要序列化。

📄

JSON

人类可读，便于检查和排错。Kubernetes 通常用它与外部客户端通信。

⚡

Protobuf

更快、更高效、扩展性更好，但难以直接查看。通常用于集群内部组件之间通信。

客户端通过请求头声明自己支持的序列化格式，比如只支持 JSON 的客户端会带上 Content-Type: application/json，Kubernetes 就会用 JSON 回应。

一个网购的比喻

  1. 商品存在仓库，通过网站展示 ↔ 资源定义在 API 里，通过 API 服务器暴露；
  2. 你用浏览器搜索下单 ↔ 你用 kubectl 请求资源；
  3. 第三方卖家也在亚马逊卖货，你用同一个网站购买 ↔ 第三方定义自己的资源（CRD），你用同一个 kubectl 请求；
  4. 买东西时选颜色、长度、接口 ↔ 配置资源的属性（metadata、重启策略、容器、卷……）；
  5. 可以跟踪物流 ↔ 可以 watch 对象的创建和部署；
  6. 可以再下单或退货 ↔ 可以继续创建或删除对象。

API 服务器

$ kubectl cluster-info
Kubernetes control plane is running at https://kubernetes.docker.internal:6443

API 服务器是一个控制平面服务，有些集群把它作为一组 Pod 跑在 kube-system 里。自己管理集群时，要确保控制平面高可用且性能足够， 否则 API 响应会变慢甚至完全无法访问；用托管 Kubernetes 时，这些由云厂商负责并对你隐藏。它用 TLS 加密客户端连接，内外部请求都要经过同样的认证和授权。

REST、CRUD 与动词

REST（REpresentational State Transfer）是与 Web API 通信的业界标准，使用 REST 的系统被称为 RESTful。 一个 REST 请求由动词和资源路径组成。CRUD 是 Create、Read、Update、Delete 四个基本操作，对应标准的 HTTP 方法：

K8s CRUD 动词HTTP 方法kubectl 示例
createPOSTkubectl create -f <文件>
get、list、watchGETkubectl get pods
updatePUT / PATCHkubectl edit deployment <名字>
deleteDELETEkubectl delete service <名字>

注意三者的名字不总是一致，比如 kubectl edit 用的是 update 动词和 HTTP PATCH 方法。

加上 -v 看收发的请求头。以 > 开头的是 curl 发出的，以 < 开头的是 API 服务器返回的：

$ curl -v -X GET http://localhost:9000/api/v1/namespaces/shield/pods
> GET /api/v1/namespaces/shield/pods HTTP/1.1     # 对 Pod 的 REST 路径发 GET
> Accept: */*                                     # 接受任何序列化格式
< HTTP/1.1 200 OK                                 # 接受请求，开始响应
< Content-Type: application/json                  # 用 JSON 序列化响应
< X-Kubernetes-Pf-Flowschema-Uid: d50...          # Kubernetes 的优先级与公平性设置
< X-Kubernetes-Pf-Prioritylevel-Uid: 828...
{                                                 # 响应体（序列化后的对象）
  "kind": "PodList",
  ...
}

curl 参数作用
-X POST强制使用 HTTP POST 方法
-H "Content-Type: application/json"告诉 API 服务器请求体是序列化的 JSON
--data-binary @ns.json指定清单文件作为请求体
URIproxy 暴露的地址 + 资源的 REST 路径

API 的结构：API 组

Kubernetes 刚诞生时 API 是单体的，所有资源都在一个全局命名空间里。随着项目壮大，API 被拆分成更小、更易管理的组，叫命名组（named groups）或子组（sub-groups）。

核心组

资源REST 路径
Pods/api/v1/namespaces/{namespace}/pods/
Services/api/v1/namespaces/{namespace}/services/
Nodes/api/v1/nodes/
Namespaces/api/v1/namespaces/

命名空间级的对象路径更长，要多带 …/namespaces/{namespace}/ 两段；Node 这类集群级对象路径就短得多。读请求的预期响应是 200 OK 或 401 Unauthorized。

命名组

资源REST 路径
Gateway/apis/networking.k8s.io/v1/namespaces/{namespace}/gateways/
ClusterRole/apis/rbac.authorization.k8s.io/v1/clusterroles/
StorageClass/apis/storage.k8s.io/v1/storageclasses/
🔮 历史遗留

Pod 和 Service 都在核心组，这是因为它们诞生于命名组出现之前。如果今天才发明它们，Service 大概会放进 networking.k8s.io，Pod 会放进 apps。 有些地方会用空的双引号 "" 表示核心组——因为当初设计 API 时根本没考虑过分组，一切都「就在 API 里」。

alpha、beta 与 GA

真实世界中稳定资源的路径示例：/apis/networking.k8s.io/v1/gateways、/apis/batch/v1/cronjobs、/apis/autoscaling/v2/horizontalpodautoscalers。

资源弃用

⏳

Beta：9 个月

beta 资源有 9 个月窗口期，要么发布新的 beta 版本，要么升级为 GA，防止停滞。（Ingress 曾在 beta 里待了超过 15 个版本！）

🛡

GA：12 个月或 3 个版本

GA 资源被弃用后仍会继续提供支持 12 个月或 3 个版本（取较长者），然后才移除。而且只有在新的稳定版（如 v2）发布后，才会弃用旧的 v1。

近期版本在你使用已弃用资源时会做三件事：

  1. 在命令行返回弃用警告；
  2. 在该请求的审计记录上加 k8s.io/deprecated:true 注解；
  3. 设置 apiserver_requested_deprecated_apis 指标。

后两项可以帮你查询审计日志和指标，在升级 Kubernetes 之前弄清自己是否在用即将移除的 API。

扩展 API：CRD

Kubernetes 自带一组内置控制器来部署和管理内置资源，但你也可以加入自己的资源和控制器。网络和存储厂商常用这种方式通过 Kubernetes API 暴露高级功能， 比如快照计划、IP 地址管理：卷通过 CSI 驱动呈现，Pod 通过 StorageClass 和 PVC 使用它们，而快照计划这类高级功能则通过自定义资源和控制器管理。 这样大家都能用熟悉的 kubectl 和 YAML 管理一切。 

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: books.nigelpoulton.com
spec:
  group: nigelpoulton.com        # API 子组（即命名 API 组）
  scope: Cluster                 # 可以是 Namespaced 或 Cluster
  names:
    plural: books                # 所有资源都需要复数名和单数名
    singular: book               # 单数名用于命令行和输出
    kind: Book                   # YAML 里的 kind 字段
    shortNames:
    - bk                         # kubectl 可用的简称
  versions:                      # 资源可以由多个 API 版本提供
    - name: v1
      served: true               # 设为 false 则不提供 v1
      storage: true              # 以这个版本存储对象实例
      schema:
        openAPIV3Schema:         # 定义资源的属性
          type: object
          properties:
            spec:
              type: object
              properties:
                bookTitle:
                  type: string
                subTitle:
                  type: string
                topic:
                  type: string
                edition:
                  type: integer
                salesUrl:
                  type: string
      additionalPrinterColumns:  # kubectl get 时额外显示的列
      - name: Title
        type: string
        jsonPath: .spec.bookTitle
      - name: Subtitle
        type: string
        jsonPath: .spec.subTitle
      - name: Edition
        type: integer
        jsonPath: .spec.edition
      - name: URL
        type: string
        jsonPath: .spec.salesUrl

小结

  • Kubernetes 是 API 驱动的平台，API 通过 API 服务器对内对外暴露；控制平面必须高可用、高性能。
  • API 是基于资源的 RESTful API，通过 POST、GET、PUT、PATCH、DELETE 等 HTTP 方法接受 CRUD 操作；对外通常用 JSON，对内常用 Protobuf。
  • API 分组：早期资源在核心组（/api/v1），新资源都在命名组（如 /apis/networking.k8s.io/v1/）。
  • 新资源经历 alpha → beta → GA，GA 资源有长期支持承诺和明确的弃用策略。
  • CRD 让你添加看起来、用起来都像原生资源的自定义资源；配合自定义控制器才能真正「做事」。
