第 7 章

Service：给会变的 Pod 一个不变的入口

Pod 不可靠：缩容、滚动更新、回滚、节点维护、故障……都会让 Pod 消失、IP 改变。 所以永远不要直接连 Pod，而要通过 Service 连。这一章讲 Service 怎么工作、有哪几种，以及怎么创建它们。

本章目标

  • 理解 Service 的「前端 + 后端」模型
  • 理解标签选择器如何把 Service 和 Pod 松耦合地连接起来
  • 知道 EndpointSlice 在幕后做什么
  • 分清 ClusterIP、NodePort、LoadBalancer 三种类型及它们的叠加关系
  • 分清 port、targetPort、nodePort 三个端口
  • 用命令式和声明式两种方法创建 Service

Service 的原理

Service 对象站在一个或多个相同 Pod 的前面，通过可靠的 DNS 名、IP 地址和端口把它们暴露出去。 （Service 是 Kubernetes API 资源，所以首字母大写，以区别于泛指的「服务」。）

每个 Service 都有前端和后端：前端包括 DNS 名、IP 地址和端口，Kubernetes 保证它们在 Service 的整个生命周期内永不改变； 后端是一个标签选择器，把流量发给标签匹配的健康 Pod。无论扩缩、发布、回滚还是 Pod 故障，Service 始终维护着一份最新的健康 Pod 列表。

标签与松耦合

Service 用标签和选择器决定把流量发给谁——和 Deployment 决定管理哪些 Pod 用的是同一套机制。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: tkb-2026
spec:
  replicas: 10
  template:
    metadata:
      labels:            # ┐ 创建带这些
        project: tkb     # │ 标签的 Pod
        zone: prod       # ┘
    spec:
      containers: ...
---
apiVersion: v1
kind: Service
metadata:
  name: tkb
spec:
  ports:
  - port: 8080
  selector:          # ┐ 把流量发给
    project: tkb     # │ 带这些标签的 Pod
    zone: prod       # ┘

幕后：EndpointSlice

每创建一个 Service，EndpointSlice 控制器就会自动创建对应的 EndpointSlice 对象，并持续把匹配选择器的 Pod 加进去或移出来。 应用把流量发往 Service 名，容器通过集群 DNS 把名字解析成 Service IP，Service 再把流量转发给 EndpointSlice 列表中的某个 Pod。 老版本用的是 Endpoints 对象，功能相同，但 EndpointSlice 在大型繁忙集群上性能更好。

三种 Service 类型

ClusterIP：集群内部访问

ClusterIP 是默认类型。它得到一个只在内部 Pod 网络上可路由的 IP，名字自动注册到集群内部 DNS，而所有容器都预先配置好使用这个 DNS。 例如你创建一个叫 skippy 的 ClusterIP Service，集群上的所有应用就都能用 skippy 这个名字访问它。 但它在集群外部不可用（第 9 章会深入讲服务发现）。

NodePort：从集群外部访问

apiVersion: v1
kind: Service
metadata:
  name: skippy           # 注册到集群内部 DNS（ClusterIP）
spec:
  type: NodePort         # Service 类型
  ports:
  - port: 8080           # 集群内部 ClusterIP 的端口
    targetPort: 9000     # 容器里应用监听的端口
    nodePort: 30050      # 每个集群节点上对外开放的端口
  selector:
    app: hello-world
⚠ NodePort 的两大局限
  • 只能用 30000–32767 之间的高位端口；
  • 客户端得知道节点的名字或 IP，还要知道哪些节点是健康的。

所以大多数人会用 LoadBalancer。

LoadBalancer：通过云负载均衡器访问

apiVersion: v1
kind: Service
metadata:
  name: lb               # 注册到集群 DNS
spec:
  type: LoadBalancer
  ports:
  - port: 8080           # 负载均衡器端口
    targetPort: 9000     # 容器里应用的端口
  selector:
    project: tkb

三个端口，一张图看懂

动手：命令式创建 Service

在仓库的 services 目录下，先部署一个有 10 个副本、带 chapter=services 标签、监听 8080 的应用：

apiVersion: apps/v1
kind: Deployment
metadata:
  name: svc-test
spec:
  replicas: 10
  selector:
    matchLabels:
      chapter: services
  template:
    metadata:
      labels:
        chapter: services
    spec:
      containers:
      - name: hello-ctr
        image: nigelpoulton/k8sbook:1.0
        ports:
        - containerPort: 8080

$ kubectl apply -f deploy.yml
deployment.apps/svc-test created

$ kubectl expose deployment svc-test --type=LoadBalancer
service/svc-test exposed

$ kubectl get svc -o wide
NAME         TYPE           CLUSTER-IP    EXTERNAL-IP     PORT(S)          SELECTOR
kubernetes   ClusterIP      10.96.0.1     <none>          443/TCP          <none>
svc-test     LoadBalancer   10.10.19.33   212.2.245.220   8080:31755/TCP   chapter=services

kubectl expose 会检查正在运行的 Deployment，自动推断出端口映射和标签选择器。逐列解读：

列含义
第一行 kubernetes系统自带的 Service，把 Kubernetes API 暴露给集群内所有 Pod
NAME默认和它前面的 Deployment 同名
EXTERNAL-IP云上是公网 IP 或 DNS 名；Docker Desktop 上是 localhost（显示 172.x.x.x 时也用 localhost）
CLUSTER-IP内部 IP，只在集群网络内可路由
PORT(S)负载均衡器端口 8080 和随机分配的 NodePort 31755
SELECTOR与 Pod 标签匹配
$ kubectl describe svc svc-test

Type:                     LoadBalancer
IP:                       10.10.19.33
LoadBalancer Ingress:     212.2.245.220
Port:                     <unset>  8080/TCP     # 负载均衡器端口
TargetPort:               8080/TCP              # 容器里应用的端口

External Traffic Policy:  Cluster

两个值得了解的设置

🔗

Session Affinity（会话亲和）

默认 None：同一个客户端的多次连接可能去不同 Pod。ClientIP 能让它总去同一个 Pod——但这是反模式，微服务应该设计成连哪个 Pod 都行。

🚦

External Traffic Policy

Cluster（默认）：可以转发到任意节点上的 Pod，但会隐藏客户端源 IP。Local：只转发给流量到达的那个节点上的 Pod，但保留源 IP。

浏览器访问 EXTERNAL-IP:8080 就能看到应用。然后删掉它，准备用正确的方式再来一次：

$ kubectl delete svc svc-test
service "svc-test" deleted

动手：声明式创建 Service

apiVersion: v1
kind: Service
metadata:
  name: svc-lb             # 名字会注册到集群 DNS
spec:
  type: LoadBalancer
  ports:
  - port: 9000             # 负载均衡器端口
    targetPort: 8080       # 容器里应用的端口
  selector:
    chapter: services

$ kubectl apply -f lb.yml
service/svc-lb created

$ kubectl get svc svc-lb
NAME     TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)
svc-lb   LoadBalancer   10.43.191.202   212.2.247.202   9000:30202/TCP

在云上，EXTERNAL-IP 一开始会显示 <pending>，等云平台创建好负载均衡器后再刷新。然后访问 EXTERNAL-IP:9000（Docker Desktop 用 localhost:9000）。

查看 EndpointSlice

示例集群运行的是 IPv4/IPv6 双栈网络，所以有两个 EndpointSlice；你的集群可能只有 IPv4 的。一个 Service 后面超过 100 个 Pod 时，会有多个 EndpointSlice。

清理

$ kubectl delete -f deploy.yml -f lb.yml     # EndpointSlice 会随 Service 自动删除

小结

  • Service 为 Pod 提供可靠的网络：前端的 DNS 名、IP、端口永不改变；后端通过标签选择器把流量发给健康 Pod。
  • EndpointSlice 自动维护健康 Pod 列表。
  • ClusterIP 用于集群内部，NodePort 在每个节点上开端口，LoadBalancer 对接云负载均衡器——三者层层叠加。
  • 记清 port → nodePort → targetPort 的顺序。
  • Service 是 Kubernetes API 的一等对象，应该用版本控制的 YAML 文件声明式管理。

动手练习

  1. 部署 deploy.yml 和 lb.yml 后，执行 kubectl scale deploy svc-test --replicas 3，再看 kubectl get endpointslices，端点数量变了吗？
  2. 把 lb.yml 的 type 改成 NodePort 并加上 nodePort: 30080，重新 apply，用 localhost:30080 访问。
  3. 故意把 lb.yml 的选择器写错（例如 chapter: service），apply 后看看 kubectl describe svc 的 Endpoints 一行。这是排查「Service 不通」时最常见的原因之一。
